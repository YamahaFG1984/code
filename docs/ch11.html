第 11 章

全书总结

到这里，你已经学完了作者多年来赖以工作的所有测试技术。最后一章不再引入新技术，而是说几句关于「现实中的有效测试」的心里话， 强调几件应该始终放在心上的事，并给出一张三种语言的工具速查表，方便你带着走。

模型看起来是线性的，但迭代才是根本

这张图和本书的章节顺序可能给你一种线性的感觉（先做规格测试，再做结构化测试……），但事实并非如此。别把它看成测试的瀑布流程。 软件开发是迭代的：你可能先做规格测试，再做结构化测试，然后觉得需要回到规格测试；也可能因为 TDD 时产生的测试已经足够好，直接从结构化测试开始。针对具体情况定制流程完全没问题。 随着经验增长，你会逐渐找到应用这些技术的最佳顺序。只要你掌握了所有技术、理解了每种技术的目标和产出，这会自然而然地到来。

无 Bug 的软件：现实还是神话？

这些技术从多个不同角度审视源代码，可能给你一种印象：全都用上，就再也不会有 Bug 了。可惜并非如此。 从越多角度测试代码，发现之前没看到的 Bug 的机会就越大；但今天的软件系统非常复杂，Bug 可能出现在涉及几十个组件协同工作的边角情况里。 领域知识能帮你看到这些情况 —— 所以，深入理解你所测系统背后的业务，是预见可能导致崩溃或 Bug 的复杂交互的根本。

押注智能测试

作者说他把所有筹码都押在智能测试（intelligent testing）上：让计算机替我们探索软件系统。本书自动化的是测试的执行，而测试用例的设计 —— 想出好的测试 —— 是人的活动；智能测试系统则会为我们提出测试用例。 这在学术界已不新鲜，有些技术已经成熟到可以部署在生产中：Facebook 部署了 Sapienz，用基于搜索的算法自动探索移动应用、寻找崩溃；Google 大规模运行模糊测试（生成意外输入看程序会不会崩溃），在开源系统中找 Bug。 而研究的美妙之处在于，这些工具并不是随机生成数据 —— 它们越来越聪明了。

让最终用户参与进来

本书聚焦于验证：确保代码按我们的预期工作。另一个角度是确认：软件是否做了用户想要或需要的事（还记得第 1 章的「无错误谬论」吗？）。 交付最有价值的软件，和交付能工作的软件同样重要。确保你的流程里有机制保证你在构建对的软件。

现实中单元测试很难

作者的立场很明确：尽可能多做单元测试，把集成测试留给真正需要它的部分。为此你需要容易测试、为可测试性而设计的代码。 然而大多数读者并不处于这种理想状态 —— 软件系统很少是这样设计的。当你写新代码、对它有更多控制权时，确保写成可单元测试的样子。 这意味着要把新代码和难以测试的遗留代码整合在一起。一个在大多数情况下都管用的简单建议： 

class LegacyClass {
  public void complexMethod() {
    // ……
    // 大量代码……
    // ……
    new BeautifullyDesignedClass().cleanMethod();   // 在遗留类里调用新类中的行为
    // ……
    // 大量代码……
    // ……
  }
}

class BeautifullyDesignedClass {                     // 这个类也可能复杂，但它是可测试的
  public void cleanMethod() {
    // ……
  }
}

class LegacyClass:
    def complex_method(self) -> None:
        # ……
        # 大量代码……
        # ……
        BeautifullyDesignedClass().clean_method()    # 在遗留类里调用新类中的行为
        # ……
        # 大量代码……
        # ……

class BeautifullyDesignedClass:                      # 这个类也可能复杂，但它是可测试的
    def clean_method(self) -> None:
        ...

class LegacyClass {
  complexMethod(): void {
    // ……
    // 大量代码……
    // ……
    new BeautifullyDesignedClass().cleanMethod();    // 在遗留类里调用新类中的行为
    // ……
    // 大量代码……
    // ……
  }
}

class BeautifullyDesignedClass {                     // 这个类也可能复杂，但它是可测试的
  cleanMethod(): void {
    // ……
  }
}

需要给遗留类加新行为时，不要把它写进这个类，而是新建一个类，把新行为放进去并单元测试它；然后在遗留类里实例化新类、调用它的方法。 这样就免去了为一个几乎不可能测试的类写测试的麻烦。（Feathers 在《修改代码的艺术》中称之为「萌芽类（Sprout Class）」。）你的具体情况也许需要不同的做法，但思路相同。 推荐阅读 Feathers 的书（2004），以及 Evans（2004）提出的防腐层（anti-corruption layer）。

投资监控

你尽了最大努力在部署前抓住所有 Bug，但实践中你知道那是不可能的。那能做什么？确保 Bug 一在生产环境出现就能被发现。 软件监控和测试同样重要，这比你想的更复杂：

  • 要记录什么？日志太多会压垮基础设施，太少又没有足够信息调试。确保团队有好的指南：记录什么、用什么日志级别……（作者团队的一篇论文表明，机器学习可以向开发者推荐在哪里打日志 —— Cândido 等，2021。）
  • 如何从海量日志中发现异常？系统每月可能产生数百万甚至数十亿行日志。有些异常软件自己就能处理，开发者照样记下来，但它们往往不重要。投资于识别真正重要的异常，是一个务实的挑战。

非功能测试

性能、可伸缩性、安全性这类非功能需求也可以测。Gayathri Mohan 的《Full Stack Testing》（2022）覆盖得不错。

🏗

特定架构和上下文的测试

不同技术需要不同的测试模式：写 API 就写 API 测试，写 Vue 应用就写 Vue 测试。推荐《Testing Web APIs》、《Exploring Testing Java Microservices》、《Testing Vue.js Applications》等。

你所用语言的可测试性设计

本书主要讲面向对象语言的原则。函数式语言的原则可能有所不同，比如 Clojure 里的 TDD。

🔍

静态分析工具

SonarQube、SpotBugs（Java），Ruff、mypy、Bandit（Python），ESLint、typescript-eslint（TS）。它们基于静态分析寻找特定的 Bug 模式，速度很快，可以放进持续集成。强烈建议熟悉它们。

📈

软件监控

A/B 测试、蓝绿部署等技术，能让漏过测试的 Bug 更难到达生产。入门推荐 Rouan Wilsenach 的博文《QA in Production》（martinfowler.com）。

🔑 如果只记住一件事

工具会变，思考方式不会。本书的核心不是 JUnit、Mockito 或 jqwik，而是：从需求推导分区和边界，用代码结构补漏，用契约和属性表达规律， 用替身隔离复杂依赖，为可测试性而设计，并让测试代码本身保持整洁。换任何语言、任何框架，这些都带得走。

Have fun testing! 祝你测试愉快！

✎ 结业练习

  1. 从你自己的项目里挑一个真实的方法，把第 2～5 章的技术完整走一遍：规格测试 → 结构化测试（看覆盖率）→ 契约 → 属性测试 → 变异测试。记录每一步新发现了什么。
  2. 找一个难测的遗留类，用本章的「萌芽类」手法加一个新功能，并为新类写单元测试。
  3. 试一个智能测试工具（EvoSuite、Pynguin 或 Jazzer.js），看它自动生成的测试和你手写的有什么不同。
