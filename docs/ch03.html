第 3 章

结构化测试与代码覆盖率

规格测试做完了，接下来打开源代码。代码里有需求没写的实现细节，也藏着你分区时漏掉的情况。 覆盖率工具能一眼告诉你「哪些代码还没被测试执行过」。这一章教你正确地使用覆盖率： 把它当成找漏洞的放大镜，而不是一个需要刷的 KPI。最后还会介绍更狠的一招 —— 变异测试。

本章目标

  • 用覆盖率报告找出测试没有执行到的代码，并思考「为什么漏了」
  • 分清行覆盖、分支覆盖、条件+分支覆盖、路径覆盖和 MC/DC
  • 学会为复杂条件手工推导 MC/DC 测试集
  • 理解为什么只靠结构化测试不够，也理解为什么有人（错误地）讨厌覆盖率
  • 用变异测试检验测试的「杀伤力」

正确使用覆盖率

为什么在规格测试之后还要看代码？两个原因：

  • 分析需求时可能漏掉了一两个分区，看代码时会发现；
  • 实现时会用到语言特性、算法和数据结构，这些实现细节在文档里看不到，同样需要测。

先看一个小程序：统计一句话里有多少个单词以 "s" 或 "r" 结尾（改编自 CodingBat）：

📋 需求：CountWords

给定一个句子，统计以 "s" 或 "r" 结尾的单词个数。遇到非字母字符时，一个单词结束。返回单词数。

public class CountWords {
  public int count(String str) {
    int words = 0;
    char last = ' ';

    for (int i = 0; i < str.length(); i++) {
      // 当前是非字母，且上一个字符是 s 或 r → 一个单词结束了
      if (!Character.isLetter(str.charAt(i)) &&
          (last == 's' || last == 'r')) {
        words++;
      }
      last = str.charAt(i);   // 记住当前字符
    }

    // 字符串以 r 或 s 结尾，最后一个单词也要算上
    if (last == 'r' || last == 's')
      words++;

    return words;
  }
}

def count_words(s: str) -> int:
    words = 0
    last = " "

    for ch in s:
        # 当前是非字母，且上一个字符是 s 或 r → 一个单词结束了
        if not ch.isalpha() and (last == "s" or last == "r"):
            words += 1
        last = ch                 # 记住当前字符

    # 字符串以 r 或 s 结尾，最后一个单词也要算上
    if last == "r" or last == "s":
        words += 1

    return words

const isLetter = (ch: string) => /\p{L}/u.test(ch);

export function countWords(str: string): number {
  let words = 0;
  let last = " ";

  for (const ch of str) {
    // 当前是非字母，且上一个字符是 s 或 r → 一个单词结束了
    if (!isLetter(ch) && (last === "s" || last === "r")) {
      words++;
    }
    last = ch;                    // 记住当前字符
  }

  // 字符串以 r 或 s 结尾，最后一个单词也要算上
  if (last === "r" || last === "s") words++;

  return words;
}

ⓘ 为什么会漏掉一个用例？
  • 开发者（测试者）犯错了。规格写得很清楚，只是没想到。
  • 规格没提到，也不清楚这个行为是否符合预期。要决定是否去问需求方 —— 这是实现上的错误吗？
  • 规格没提到，但代码有理由存在。比如性能、持久化等实现细节，功能需求里不会写。应该补一个测试，因为这些实现细节同样可能出 Bug。

结构化测试的流程

最重要的一点：结构化测试是对规格测试的补充。覆盖率工具只是一个自动找出「哪里没测到」的手段。和上一章一样，这个流程是迭代的，回头去规格里再挖几个用例是常有的事。

覆盖准则：要测得多彻底？

发现一行没覆盖时，要决定覆盖得多彻底。还是那行 if：

if (!Character.isLetter(str.charAt(i)) && (last == 's' || last == 'r'))

行覆盖（line coverage）

只要有一个测试执行到这一行，就算覆盖。哪怕它是一个塞满条件的复杂 if。

分支覆盖（branch coverage）

if、for、while 这类分支语句会让程序走向不同的路。对 if (a && b)，有一个测试让它为真、一个让它为假，就算分支覆盖。 用控制流图（CFG）来看：每个判断节点引出「真」和「假」两条边，覆盖图里所有的边 = 100% 分支覆盖。

条件 + 分支覆盖（condition + branch coverage）

不仅看分支，还看每个分支语句里的每个条件。第一个 if 有三个条件：!isLetter(...)、last == 's'、last == 'r'。 目标是让每个条件各为真、为假至少一次，并且整个判断也为真、为假至少一次。

⚠ 为什么不能只看条件？

看 if (A || B)：T1 = (A 真, B 假)，T2 = (A 假, B 真)。两个条件都真假各一次 ——「条件覆盖」达成了。 但两次整个 if 都是真，else 分支根本没走过！所以我们总是把条件覆盖和分支覆盖一起用。

把复合条件拆开，每个判断节点只放一个条件，得到「扩展控制流图」。覆盖扩展图里所有的边 = 100% 条件 + 分支覆盖：

路径覆盖（path coverage）

覆盖程序所有可能的执行路径。理论上最强，实际上往往做不到或太贵：3 个独立条件就有 2³ = 8 条路径，10 个条件就是 2¹⁰ = 1024 条。 有循环时更麻烦 —— 无界循环可能跑几百次，严格的路径覆盖要求把循环跑 1 次、2 次、3 次……都测一遍。

复杂条件与 MC/DC

碰到又长又复杂的 if，怎么在「测得彻底」和「用例不爆炸」之间取舍？答案是修正条件/判定覆盖（MC/DC，Modified Condition/Decision Coverage）。 它像路径覆盖一样看条件组合，但只挑重要的组合：确保每个条件都能独立地影响整个判断的结果。

抽象例子：A && (B || C)

对条件 A，MC/DC 要求：

  • 有一个测试 A = 真（记为 T1），一个测试 A = 假（记为 T2）；
  • T1 和 T2 的整体结果不同；
  • T1 和 T2 中，B 和 C 的取值完全相同。

这样的 T1、T2 叫做 A 的独立性对（independence pair）：只变 A，结果就变了，说明 A 独立地影响了结果。对 B 和 C 同理。

🔑 N + 1 规则

如果每个条件都只有真/假两种结果，达到 100% MC/DC 通常只需要 N + 1 个测试（N 为条件个数），远少于路径覆盖的 2N。

然后逐个条件找独立性对：找两行，只有这个条件不同、其余条件相同，而且结果不同。

  1. 非字母：T1 和 T5 只差这一列，结果 T→F，✔ 是一对。同理 {T2, T6}、{T3, T7} 也是。{T4, T8} 结果都是 F，✘ 不算。
  2. last == s：T1 和 T3 只差这一列，但结果都是 T，✘。找遍全表，只有 {T2, T4} 成立。
  3. last == r：同样只有 {T3, T4} 成立。
  4. 挑最少的组合：后两个条件没得选，必须要 T2、T3、T4。第一个条件从 {T1,T5}、{T2,T6}、{T3,T7} 里挑一对 —— 选 {T2,T6} 或 {T3,T7} 只需再加一个测试（另一半已经在集合里了）。

最后把这 4 个抽象用例落到具体输入上。T2：非字母、last 是 s → 比如 "cats " 读到空格时；T3：非字母、last 是 r；T4：非字母、last 既非 s 也非 r；T6：是字母、last 是 s。

循环怎么测

循环体可能执行任意多次。while(true) 可能永不结束；带 break 的 for (i = 0; i < 10; i++) 可能执行 0 到 10 次。穷举不现实，所以用循环边界充分性准则（loop boundary adequacy criterion）：

实践中最难的是「多次」：该让它跑 2 次、5 次还是 10 次？这需要你真正理解程序和需求。别怕为「多次」写两个甚至更多测试 —— 做你需要做的，确保循环按预期工作。

准则之间的包含关系

准则 X 包含（subsume）准则 Y，意思是：Y 覆盖到的一切，X 也都覆盖到。

  • 100% 分支覆盖一定意味着 100% 行覆盖；反之不成立。
  • 条件 + 分支覆盖同时包含分支覆盖和（基本）条件覆盖。
  • MC/DC 比条件 + 分支覆盖更强，因为它保证每个条件的独立影响。
  • 路径覆盖包含所有其他准则 —— 它本来就走遍了所有路径。
  • 注意：基本条件覆盖不一定包含行覆盖，原因见图 3-5：else 分支里的行可能一次都没执行。

弱的准则便宜但可能漏掉很多，强的准则彻底但成本高。选哪个，由你决定。

实战：规格测试 + 结构化测试一起用

来看 Apache Commons Lang 里真实的 leftPad()：

📋 需求：leftPad(str, size, padStr)

用 padStr 在 str 左边填充，直到长度达到 size。

  • str —— 要填充的字符串，可以为 null。
  • size —— 目标长度。
  • padStr —— 用来填充的字符串。null 或空视为一个空格。

返回左填充后的字符串；如果不需要填充，返回原字符串；str 为 null 则返回 null。
例：leftPad("abc", 5, "-") → "--abc"。

public static String leftPad(final String str, final int size, String padStr) {
  if (str == null) {
    return null;
  }
  if (isEmpty(padStr)) {
    padStr = SPACE;                   // null 或空 → 一个空格
  }
  final int padLen = padStr.length();
  final int strLen = str.length();
  final int pads = size - strLen;     // 需要填充几个字符
  if (pads <= 0) {
    return str;                       // 不需要填充时返回原字符串
  }

  if (pads == padLen) {
    return padStr.concat(str);        // 恰好填一整个 padStr
  } else if (pads < padLen) {
    return padStr.substring(0, pads).concat(str);   // 只用 padStr 的前一部分
  } else {
    // 需要重复 padStr 多次，一个字符一个字符地填
    final char[] padding = new char[pads];
    final char[] padChars = padStr.toCharArray();
    for (int i = 0; i < pads; i++) {
      padding[i] = padChars[i % padLen];
    }
    return new String(padding).concat(str);
  }
}

def left_pad(s: str | None, size: int, pad_str: str | None) -> str | None:
    if s is None:
        return None
    if not pad_str:
        pad_str = " "                    # None 或空 → 一个空格
    pad_len = len(pad_str)
    pads = size - len(s)                 # 需要填充几个字符
    if pads <= 0:
        return s                         # 不需要填充时返回原字符串

    if pads == pad_len:
        return pad_str + s               # 恰好填一整个 pad_str
    elif pads < pad_len:
        return pad_str[:pads] + s        # 只用 pad_str 的前一部分
    else:
        # 需要重复 pad_str 多次，一个字符一个字符地填
        padding = "".join(pad_str[i % pad_len] for i in range(pads))
        return padding + s

export function leftPad(str: string | null, size: number, padStr: string | null): string | null {
  if (str == null) {
    return null;
  }
  if (!padStr) {
    padStr = " ";                        // null 或空 → 一个空格
  }
  const padLen = padStr.length;
  const pads = size - str.length;        // 需要填充几个字符
  if (pads <= 0) {
    return str;                          // 不需要填充时返回原字符串
  }

  if (pads === padLen) {
    return padStr + str;                 // 恰好填一整个 padStr
  } else if (pads < padLen) {
    return padStr.substring(0, pads) + str;   // 只用 padStr 的前一部分
  } else {
    // 需要重复 padStr 多次，一个字符一个字符地填
    let padding = "";
    for (let i = 0; i < pads; i++) {
      padding += padStr[i % padLen];
    }
    return padding + str;
  }
}

// 这个承诺在 JS 里无法、也无需测试 —— 语言特性决定了测试的边界。
test("returns the original string when no padding is needed", () => {
  expect(leftPad("sometext", 5, "-")).toBe("sometext");
});

边界测试与结构化测试

规格测试里最难的是找边界，因为规格是用自然语言写的，很模糊。而代码必须精确，所以边界在代码里一目了然。 上一章的 on/off 点分析可以直接套在 if 语句上：

只做结构化测试是不够的

既然代码是一切的真相，为什么不只做结构化测试？看一个「数团块」的例子（改编自 CodingBat）：

📋 需求：countClumps(nums)

统计数组中「团块」的个数。团块是长度至少为 2 的、由相同元素组成的连续序列。数组必须非 null 且长度 > 0，违反前置条件时返回 0。

public static int countClumps(int[] nums) {
  if (nums == null || nums.length == 0) {
    return 0;
  }
  int count = 0;
  int prev = nums[0];
  boolean inClump = false;
  for (int i = 1; i < nums.length; i++) {
    if (nums[i] == prev && !inClump) {   // 和前一个相同 → 发现一个团块
      inClump = true;
      count += 1;
    }
    if (nums[i] != prev) {               // 和前一个不同 → 离开团块
      prev = nums[i];
      inClump = false;
    }
  }
  return count;
}

def count_clumps(nums: list[int] | None) -> int:
    if not nums:                          # None 或空
        return 0
    count = 0
    prev = nums[0]
    in_clump = False
    for n in nums[1:]:
        if n == prev and not in_clump:    # 和前一个相同 → 发现一个团块
            in_clump = True
            count += 1
        if n != prev:                     # 和前一个不同 → 离开团块
            prev = n
            in_clump = False
    return count

export function countClumps(nums: number[] | null): number {
  if (nums == null || nums.length === 0) {
    return 0;
  }
  let count = 0;
  let prev = nums[0];
  let inClump = false;
  for (let i = 1; i < nums.length; i++) {
    if (nums[i] === prev && !inClump) {  // 和前一个相同 → 发现一个团块
      inClump = true;
      count += 1;
    }
    if (nums[i] !== prev) {               // 和前一个不同 → 离开团块
      prev = nums[i];
      inClump = false;
    }
  }
  return count;
}

[1,1,2,3,3] → 2

团块在开头

[2,2,1] → 1

团块在结尾

[1,2,2] → 1

这些情况都会重复经过已经覆盖过的行和分支，所以覆盖率完全不会提醒你。结构化测试的价值，只有和规格知识结合时才能体现。这又是一个不能盲目依赖覆盖率的理由。

现实中的结构化测试

为什么有人讨厌覆盖率？

流行的说法是：「写一个没有断言的测试也能 100% 覆盖，但什么都没测！」没错。可这个论点假设了最糟糕、最不现实的情况 —— 如果你的测试连断言都没有，那你在享受结构化测试的好处之前，有更大的问题要解决。

这句话背后真正的意思是：不要盲目看覆盖率数字。这一点作者完全同意。问题出在人们如何看待覆盖率： 如果它只是一个要达成的数字，你就会写出没用的测试来「刷指标」。本章的用法是：补充规格测试、快速找出没执行到的代码、发现分区时漏掉的情况。 高覆盖率可能是这么做的结果，但不是目的。如果某行没覆盖，那应该是因为你想过并决定不覆盖它。

🔎 实证研究怎么说
  • Hutchins 等（1994）：覆盖率超过 90% 的测试集，通常比同样大小的随机测试集发现缺陷的能力显著更强；覆盖率从 90% 提到 100% 时效果常有明显提升。但单独的 100% 覆盖并不是可靠的有效性指标。
  • Namin 和 Andrews（2009）：控制测试集大小后，覆盖率有时与有效性相关；同时考虑大小和覆盖率比只看大小预测得更准。
  • Inozemtseva 和 Holmes（2014）：控制用例数后，覆盖率与有效性只有低到中度相关；更强的覆盖形式也没提供更多洞察。覆盖率适合找出测试不足的部分，但不应当作质量目标。
  • Gopinath 等（2020）：在数百个 Java 程序中，语句、块、分支、路径覆盖都与变异杀死率相关，其中语句覆盖是最好的预测指标。

作者的解读：用规格测试覆盖所有分区，往往也覆盖了大部分代码；反过来，覆盖了大部分代码，通常也覆盖了大部分分区。 100% 覆盖不代表测好了，但 10% 覆盖一定代表没测好。推荐阅读 Google 的《Code Coverage Best Practices》（2020）。

覆盖率怎么算

指标公式
行覆盖率被覆盖的行数 ÷ 总行数 × 100%
分支覆盖率被覆盖的分支数 ÷ 总分支数 × 100%
条件+分支覆盖率(被覆盖的分支数 + 被覆盖的条件取值数) ÷ (总分支数 + 总条件取值数) × 100%

例：if (x || y) 有 2 个分支、4 个条件取值（x 真/假、y 真/假）。两个测试 T1=(真,真)、T2=(假,真)：两次整个 if 都为真，只覆盖了 1 个分支； x 真假都有，y 只有真 —— 覆盖了 3 个条件取值。所以是 (1 + 3) / (2 + 4) = 66.6%。

用哪个准则？

看情况：你正在测什么、要多严格。深入代码时，你可能对这个 if 用分支覆盖，对那个 if 用 MC/DC。这让方法不那么「系统」，但这是作者所知最务实的做法。 作者的经验法则：至少覆盖所有分支；遇到较复杂的表达式，考虑条件+分支覆盖；遇到更复杂的，考虑 MC/DC。

MC/DC 的高光时刻

表达式越复杂，MC/DC 越有价值。Chilenski 2001 年的论文里有一个来自 A 级飞行模拟程序的条件，包含 76 个条件。 路径覆盖需要 2⁷⁶ ≈ 7.5 × 10²² 个测试 —— 不可能。能拆就拆成小块；实在拆不了，MC/DC 就派上用场了。

💡 SQLite 的故事

SQLite 作者 Richard Hipp 在播客里说：他决定把测试做到 100% MC/DC，花了整整一年、每周 60 小时。 「达到 90% 或 95% 很容易，最后那 5% 真的非常非常难……但做到之后，我们再也没收到来自 Android 的 Bug 报告。」

🔎 MC/DC 的几个补充
  • 唯一原因 MC/DC vs 掩码 MC/DC：本章用的是唯一原因（unique-cause）版本：独立性对中只有一个条件和结果改变。但像 (A && B) || (A && C)，没法只改第一个 A 而不改第二个 A。这时允许 A 一起变、固定其余变量，叫掩码（masked）MC/DC。
  • 有些表达式做不到 MC/DC：比如 (A && B) || (A && !B)，找不到 B 的独立性对 —— 因为 B 根本不影响结果，表达式可以简化为 A。遇到这种情况，回头审视表达式的设计。
  • N + 1 是理论下限：有些表达式需要更多测试，但 Chilenski 的研究表明，实践中大多数表达式恰好需要 N + 1 个。

其他覆盖准则

本章一直用控制流推导测试。另一种思路是看数据流：一个变量被定义、被修改了一两三次、然后被使用，你可能想确保覆盖它被「触碰」的所有方式。本书不展开，推荐 Pezzè 和 Young（2008）的讲解。

什么不该覆盖？

public static String resourceFolder(String path) {
  try {
    return Paths.get(ResourceUtils.class
        .getResource("/").toURI()).toString() + path;
  } catch (URISyntaxException e) {
    throw new RuntimeException(e);   // 要覆盖这行，得想办法让 toURI() 抛异常
  }
}

def resource_folder(path: str) -> str:
    try:
        return str(Path(importlib.resources.files("myapp"))) + path
    except OSError as e:               # 要覆盖这行，得想办法让标准库抛异常
        raise RuntimeError(e) from e

export function resourceFolder(path: string): string {
  try {
    return fileURLToPath(new URL("./", import.meta.url)) + path;
  } catch (e) {                        // 要覆盖这行，得想办法让 URL 解析抛异常
    throw new Error("cannot resolve resource folder", { cause: e });
  }
}

要覆盖 catch 块，得用 Mock 之类的手段强迫底层 API 抛异常。作者看不出这么做有什么好处。 更重要的是测试系统其他部分在 resourceFolder 抛异常时会怎样 —— 那更容易，因为我们对 resourceFolder 的控制远比对标准库强。 作者也通常不为 equals、hashCode 和简单的 getter/setter 写专门的测试，它们会被使用它们的其他测试间接覆盖。

🔑 默认所有代码都该覆盖，除非证明不需要

作者从「应该 100% 覆盖」出发；发现某段代码不需要覆盖时，再做例外。但要小心 —— 经验表明，Bug 往往出现在你覆盖得不好的地方。

变异测试：测试的杀伤力够吗？

所有覆盖准则都只关心「生产代码被执行了多少」，没人检查断言够不够强。 如果我在一行被测试覆盖的代码里故意放一个 Bug，测试会失败吗？这就是变异测试（mutation testing）的思路。

变异体（mutant）
对原程序做一个微小改动后得到的「有 Bug 的版本」。
杀死（kill）/ 存活（survive）
测试集在变异体上失败 = 杀死它；全部通过 = 它存活。
称职程序员假设（competent programmer hypothesis）
程序由称职的程序员编写，要么是对的，要么和正确版本只差几个简单错误。
耦合效应（coupling effect）
复杂的 Bug 是由许多小 Bug 组合而成的。所以能抓住简单 Bug 的测试集，也能抓住复杂的。

分析存活的变异体

变异工具不理解你的代码，它只是机械地改代码，所以会产生一些没意义的变异体。 比如 Pitest 把 int pads = size - strLen 里的 size 变成了 size++（先用后加）。测试没抓住它 —— 但这不是有用的变异体：size 在这一行之后再也没被用过，加不加 1 对程序毫无影响。这种和原程序行为完全等价的变异体叫等价变异体。 所以，要逐个分析存活的变异体，而不是盲目追求 100%。

🔎 一个有趣的存活者：pads <= 0 → pads < 0

当 size 恰好等于 str 的长度（T7：leftPad("abc", 3, "-")）时，pads = 0。变异后不再直接返回，而是落进 pads < padLen 分支， 返回 "".concat("abc") —— 内容还是 "abc"。T7 只比较内容，杀不死它；sameInstance 用的是 size=5 < 8，pads 为负，也碰不到 pads == 0。 所以在 Java 里这个变异体会存活，而且它暴露了一个真实的漏洞：「不需要填充时返回原对象」这个承诺在 pads == 0 时被打破了，我们却没发现。 要杀死它，就补一个 assertThat(leftPad(str, str.length(), "-")).isSameAs(str)。

同一个变异放到别的语言里意义就不同了：TypeScript 的字符串是原始值，根本没有「同一个对象」的说法；CPython 里 "" + s 直接返回 s 本身。 在这两种语言里它是等价变异体，永远杀不死，也不需要杀。这正是「存活的变异体必须人工逐个分析」的原因。

代价与收益

变异测试最大的问题是成本：要生成大量变异体，每个都跑一遍完整测试。研究者在努力降低成本：减少变异体数量、自动识别等价变异体、减少要执行的测试。 但收益很可观：Parsai 和 Demeyer（2020）表明，变异覆盖能揭示分支覆盖发现不了的测试弱点，而且构建时的性能开销可以接受；Google 也在自己的系统中投资变异测试。 变异的思想还被用到了 HTML DOM（检验 Web 测试是否够强）和 SQL 查询上。

建议：对整个系统跑变异测试可能太贵，但对系统中敏感的一小部分类跑一跑是可行的，常常能告诉你还该测什么。

本章小结

  • 结构化测试利用源代码，来增强通过规格测试设计出的测试集。
  • 核心思路：分析哪些代码还没被覆盖，思考它们该不该被覆盖。
  • 有些准则不那么严格也更便宜（如行覆盖），有些更严格也更贵（如 MC/DC）。选哪个由开发者决定。
  • 覆盖率不应该被当成要达成的数字，而应该用来辅助结构化测试：理解哪些部分没覆盖、为什么。
  • 变异测试检验测试集是否足够强，也就是能否抓住尽可能多的 Bug。

3.9　关于规格测试与结构化测试的关系，哪项正确？（A 应该优先结构化测试，更便宜更有效　B 规格测试需要正式模型，用户故事不够　C 边界分析只能在有源代码时做，属于结构化技术　D 以上都不对）

D。没有研究支持结构化测试应优先于规格测试；规格测试需要好的需求，但不需要正式模型；边界分析既可以基于规格也可以基于代码。
