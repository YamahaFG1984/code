第 2 章

基于规格说明的测试

需求文档是测试最宝贵的原材料：它精确地告诉你软件该做什么、不该做什么。 这一章教你一套七步法，把一段需求系统地拆解成一组测试用例 —— 不靠灵感，靠方法。 你会看到，这套方法能在一段「看起来没问题、覆盖率也 100%」的代码里揪出两个 Bug。

本章目标

  • 掌握从需求推导测试的七个步骤
  • 学会把输入空间划分成等价类（分区），每类只测一个代表
  • 学会找边界，理解 on 点、off 点、in 点、out 点
  • 学会在组合爆炸时务实地削减用例数量
  • 用参数化测试（JUnit / pytest / Vitest）把用例落成代码

它在测试流程里的位置

回顾第 1 章的流程：开发者拿到需求，用 TDD 写好实现，确保代码可测试。所有类都准备好之后，切换到「测试模式」，开始系统地找 Bug。 基于规格说明的测试（specification-based testing）就是进入测试模式后第一个该用的技术。

它的核心思想是：从需求本身推导测试，而不是从代码推导。具体实现怎么写不太重要（下一章的结构化测试才看代码）。 所以它也常被称为黑盒测试。

例子：substringsBetween

假设你要实现一个方法：在字符串里找出所有被「开始标签」和「结束标签」夹住的子串。 这是真实开源库 Apache Commons Lang 里的方法。需求如下：

📋 需求：substringsBetween(str, open, close)

在字符串中查找以 open 开头、以 close 结尾的子串，把所有匹配的子串放进数组返回。

  • str —— 包含子串的字符串。null 返回 null；空字符串返回空数组。
  • open —— 标识子串开始的字符串。空字符串返回 null。
  • close —— 标识子串结束的字符串。空字符串返回 null。

返回子串数组；如果没有任何匹配，返回 null。
例：str = "axcaycazc"，open = "a"，close = "c"，输出 ["x", "y", "z"]。

下面是实现。先别急着找 Bug —— 这次代码来自一群非常优秀的开发者，我们的重点是学习如何推导测试。

public static String[] substringsBetween(final String str,
    final String open, final String close) {
  // 前置条件不满足，直接返回 null
  if (str == null || isEmpty(open) || isEmpty(close)) {
    return null;
  }
  final int strLen = str.length();
  if (strLen == 0) {
    return EMPTY_STRING_ARRAY;          // 空字符串 → 空数组
  }
  final int closeLen = close.length();
  final int openLen = open.length();
  final List<String> list = new ArrayList<>();
  int pos = 0;                          // 当前扫描到的位置

  while (pos < strLen - closeLen) {
    int start = str.indexOf(open, pos); // 找下一个 open
    if (start < 0) {
      break;                            // 再也没有 open 了
    }
    start += openLen;
    final int end = str.indexOf(close, start);  // 在 open 之后找 close
    if (end < 0) {
      break;                            // 再也没有 close 了
    }
    list.add(str.substring(start, end));
    pos = end + closeLen;               // 指针移到这个 close 之后
  }
  if (list.isEmpty()) {
    return null;                        // 一个都没找到 → null
  }
  return list.toArray(EMPTY_STRING_ARRAY);
}

def substrings_between(s: str | None, open_: str | None, close: str | None) -> list[str] | None:
    # 前置条件不满足，直接返回 None（not open_ 同时覆盖 None 和 ""）
    if s is None or not open_ or not close:
        return None
    if len(s) == 0:
        return []                       # 空字符串 → 空列表

    result = []
    pos = 0                             # 当前扫描到的位置
    while pos < len(s) - len(close):
        start = s.find(open_, pos)      # 找下一个 open，找不到返回 -1
        if start < 0:
            break
        start += len(open_)
        end = s.find(close, start)      # 在 open 之后找 close
        if end < 0:
            break
        result.append(s[start:end])
        pos = end + len(close)          # 指针移到这个 close 之后

    return result if result else None   # 一个都没找到 → None

export function substringsBetween(
  str: string | null, open: string | null, close: string | null,
): string[] | null {
  // 前置条件不满足，直接返回 null
  if (str == null || !open || !close) {
    return null;
  }
  if (str.length === 0) {
    return [];                          // 空字符串 → 空数组
  }

  const result: string[] = [];
  let pos = 0;                          // 当前扫描到的位置
  while (pos < str.length - close.length) {
    let start = str.indexOf(open, pos); // 找下一个 open，找不到返回 -1
    if (start < 0) break;
    start += open.length;
    const end = str.indexOf(close, start);  // 在 open 之后找 close
    if (end < 0) break;
    result.push(str.substring(start, end));
    pos = end + close.length;           // 指针移到这个 close 之后
  }
  return result.length > 0 ? result : null;  // 一个都没找到 → null
}

七步法

最理想的测试方法是把所有可能的输入组合都试一遍 —— 但三个字符串参数的组合是无穷的。我们需要务实。作者提出的七步法结合了 Ostrand 和 Balcer 1988 年的类别划分法（category-partition）与 Kaner 等人的《领域测试手册》：

第 1 步：理解需求、输入和输出

不管需求怎么写（甚至只在你脑子里），它都包含三部分：业务规则（程序要做什么）、输入（我们正是通过它们来测试不同情况）、输出（帮助理解输入如何变成结果）。对 substringsBetween：

  1. 目标：收集字符串中所有被 open 和 close 夹住的子串。
  2. 输入三个参数：str（源字符串）、open（开始标签）、close（结束标签）。
  3. 输出：由找到的所有子串组成的数组。

第 2 步：探索程序

如果代码不是你写的，随手调用几次能快速建立心智模型。作者在一项观察职业开发者的研究中发现，大家面对陌生方法时都会这么做。 这一步不需要系统，目的是加深理解，而不是测试：

第 3 步：划分分区（等价类）

输入几乎无穷，但很多输入会让程序以同样的方式工作。比如 ("abcd", "a", "d") 返回 "bc"， 和 ("xyzw", "x", "w") 返回 "yz"，对测试来说没有区别 —— 只是换了字母。 这两个输入是等价的，属于同一个分区（partition）。每个分区测一个代表就够了。

如何系统地找出所有分区？分三个角度想：

  1. 每个输入单独看：「这个参数可能有哪几类取值？」
  2. 输入之间的组合：「open 和 close 之间能怎么搭配？」
  3. 输出有哪几类：「会返回数组吗？会返回空数组吗？会返回 null 吗？」
ⓘ null 和空字符串几乎总是值得一测

需求明确提到了 str 的 null 和空，而作者即便需求没提也会测它们 —— 它们是经典的异常用例。对 open 和 close 也一样，因为从 str 身上已经学到：在这个程序里它们是特殊的。字符串本质上是字符列表，所以还要测「长度为 1」的情况。

第 4 步：分析边界

边界附近的 Bug 极其常见。我们都犯过把 >= 写成 > 的错误 —— 这种 Bug 对大多数输入都表现正常，只在边界附近才会失败。 看一个简单例子：输入小于 10 打印 "hiphip"，大于等于 10 打印 "hooray"。

Jeng 和 Weyuker（1994）提出：每遇到一个边界，就测两个点。四个术语要分清：

on 点（on point）
恰好在边界上的点。它通常就是规格里写的那个数（input >= 10 里的 10），也很可能是开发者写进 if 里的那个数。
off 点（off point）
离边界最近、但属于另一个分区的点。这里是 9。
in 点（in point）
让条件为真的点，有无穷多个：11、12、25、42……
out 点（out point）
让条件为假的点：8、7、2、-42……

找边界的诀窍：看所有分区，想一想它们之间的输入。对 substringsBetween，一个明显的边界是 str 从空变成非空 —— 已经被分区覆盖了。更值得注意的是：open 和 close 都在字符串里，但它们之间什么都没有。

边界两侧各一个测试：「open 和 close 之间没有字符」与「之间有字符」。后者已被其他用例覆盖，可以省掉。

第 5 步：设计测试用例

理想情况下，把每个类别的所有分区两两组合。可是算一下：

为什么异常情况只测一次？把「str 为 null」和 open 的四种情况、close 的四种情况逐一组合，能多发现什么吗？几乎不能。 另外，除非有理由怀疑程序对不同长度的 open/close 处理方式不同，否则 (1,1)、(>1,1)、(1,>1)、(>1,>1) 四种组合只需要测两种。 （看代码也能帮你判断哪些组合不必测 —— 那是第 3 章的事。）

第 6 步：自动化

把用例变成代码基本上是机械劳动，创造性的部分在于：为每个分区挑出具体的输入值，并想清楚正确的输出。 作者把 21 个用例分到了几个测试方法里，每个方法对应一组：

import static ch2.StringUtils.substringsBetween;

public class StringUtilsTest {

  @Test

    assertThat(substringsBetween(null, "a", "b")).isEqualTo(null);            // T1
    assertThat(substringsBetween("", "a", "b")).isEqualTo(new String[]{});    // T2

  @Test

  }

  @Test

    assertThat(substringsBetween("abc", "a", null)).isEqualTo(null);          // T5

  }

  @Test
  void strOfLength1() {
    assertThat(substringsBetween("a", "a", "b")).isEqualTo(null);             // T7
    assertThat(substringsBetween("a", "b", "a")).isEqualTo(null);             // T8
    assertThat(substringsBetween("a", "b", "b")).isEqualTo(null);             // T9

    assertThat(substringsBetween("abc", "x", "y")).isEqualTo(null);           // T11

ⓘ 一个方法放几个断言？

有人主张一个用例一个测试方法（21 个方法），好处是方法名就能清楚描述用例。也可以用参数化测试（Python 和 TypeScript 标签页里就是这样写的）。 作者在复杂业务系统里偏爱「一个方法只测一件事」；但这里输入很多、而且大多是同一分区的变体，所以分组写更合适。这件事很主观，第 10 章再讨论测试代码质量。

另外，像 T1 这种「str 为 null」的用例，open 和 close 传什么都无所谓。作者的习惯是：给不关心的参数传合理的值，不要让它们干扰测试。

🔎 四只眼睛比两只好

一位审稿人问：输入 "aabcddaabeddaab"、open 为 "aa"、close 为 "d" 呢？ "bc" 和 "be" 是答案，但 "bcddaabed" 似乎也可以算一个子串。作者起初以为漏了用例，其实它和 T15、T20 是同一类 —— 只是思考角度不同：作者想的是「多个标签会不会让程序出错」，审稿人想的是「程序会不会错误地去匹配更长的子串」。 我们尽量系统化，但很多东西取决于你如何建模问题。想到新用例，就加进去！（仓库里的 closeTagAppearingMultipleTimes 测试就是它。）

用规格测试抓 Bug：两数相加

Apache Commons 的开发者太优秀了，我们没找到 Bug。来看一个作者自己写的例子 —— 他说自己是「时不时会犯错的普通开发者」。 这道题来自 LeetCode 风格的编程挑战，试着在揭晓前找出 Bug：

📋 需求：add(left, right)

接收两个用数字列表表示的数 left 和 right，把它们相加，结果也用数字列表返回。 每个元素必须是 [0–9] 之间的数，否则抛出 IllegalArgumentException。

  • left —— 左边的数。null 返回 null；空列表表示 0。
  • right —— 右边的数。null 返回 null；空列表表示 0。

例：23 + 42 → [2,3] + [4,2] = [6,5]。

public List<Integer> add(List<Integer> left, List<Integer> right) {
  if (left == null || right == null)
    return null;

  // 反转，让最低位在最前面，方便循环
  Collections.reverse(left);
  Collections.reverse(right);

  LinkedList<Integer> result = new LinkedList<>();
  int carry = 0;
  for (int i = 0; i < max(left.size(), right.size()); i++) {
    int leftDigit = left.size() > i ? left.get(i) : 0;
    int rightDigit = right.size() > i ? right.get(i) : 0;

    if (leftDigit < 0 || leftDigit > 9 || rightDigit < 0 || rightDigit > 9)
      throw new IllegalArgumentException();

    int sum = leftDigit + rightDigit + carry;
    result.addFirst(sum % 10);   // 当前位
    carry = sum / 10;            // 进位
  }
  return result;
}

def add(left: list[int] | None, right: list[int] | None) -> list[int] | None:
    if left is None or right is None:
        return None

    # 反转，让最低位在最前面，方便循环
    l, r = left[::-1], right[::-1]

    result = []
    carry = 0
    for i in range(max(len(l), len(r))):
        left_digit = l[i] if i < len(l) else 0
        right_digit = r[i] if i < len(r) else 0

        if not (0 <= left_digit <= 9) or not (0 <= right_digit <= 9):
            raise ValueError("digits must be in [0, 9]")

        s = left_digit + right_digit + carry
        result.insert(0, s % 10)   # 当前位
        carry = s // 10            # 进位
    return result

export function add(left: number[] | null, right: number[] | null): number[] | null {
  if (left == null || right == null) return null;

  // 反转，让最低位在最前面，方便循环
  const l = [...left].reverse();
  const r = [...right].reverse();

  const result: number[] = [];
  let carry = 0;
  for (let i = 0; i < Math.max(l.length, r.length); i++) {
    const leftDigit = i < l.length ? l[i] : 0;
    const rightDigit = i < r.length ? r[i] : 0;

    if (leftDigit < 0 || leftDigit > 9 || rightDigit < 0 || rightDigit > 9)
      throw new RangeError("digits must be in [0, 9]");

    const sum = leftDigit + rightDigit + carry;
    result.unshift(sum % 10);           // 当前位
    carry = Math.floor(sum / 10);       // 进位
  }
  return result;
}

分析分区

left（单独看）

它是列表：null、空、一位数、多位数。它表示一个数，所以再加上左边有前导零（没用，但要看程序能否处理）。

right（单独看）

和 left 完全一样的五个分区。

(left, right) 组合

长度可以不同：left 更长、right 更长、一样长。加法交换律告诉我们，谁大谁小放哪边结果都一样。

然后是进位。需求里根本没提进位，但任何懂加法的人都知道它是这个问题的核心：

  • 没有进位
  • 有进位：一次，发生在最低位
  • 有进位：一次，发生在中间
  • 有进位：多次连续
  • 有进位：多次但不连续
  • 有进位：进位产生了一个新的最高位
⚠ 领域知识仍然是关键

读到这里你可能觉得：只要分析每个参数，就能推导出所有需要的用例。要是那么简单就好了！ 分析参数能帮你找到很多 Bug，但深入理解需求依然至关重要。这里需求没提进位，我们围绕它设计了一堆测试，是因为我们懂加法。 系统的方法能帮你发现很多常见 Bug，但学习你所在系统的业务领域，是你自己的功课。

唯一值得单独测的边界：像 99 + 1 这样，进位一路传到一个新的最高位。

设计用例并自动化

策略：null 和空只测一次；一位数只测一次；多位数分「等长」和「不等长」两组，每组都覆盖全部进位情况，不等长时 left 长和 right 长各测一遍；前导零测几个就够；最后测边界。

🔑 缺失的代码也是 Bug

这两个 Bug 不是因为代码写错了，而是因为少写了代码。这类 Bug 很常见，而结构化测试（看代码）很难发现它 —— 你没法覆盖一行不存在的代码！只有从需求出发才能想到「进位要放到新的最高位」。 拿不准时，就写个测试。自动化单元测试写起来很快，多一两个没用的测试也无伤大雅。

🔎 细心的读者：Java 版会修改传入的列表

书中 Java 实现用 Collections.reverse(left) 就地反转了调用者传进来的列表 —— 这是一个副作用，调用者之后会发现自己的列表被倒过来了。 Python 和 TypeScript 标签页里我们改为先复制再反转（left[::-1]、[...left].reverse()）。 这类「方法对输入做了什么承诺」的问题，正是第 4 章「契约」要讨论的。

实战经验

🔄

迭代，而非线性

写用例时常会发现漏了某个分区或边界，回头补上就好。

⚖

测到什么程度？

看失败的代价。代价高就多投入、多试几种技术；代价低，不那么彻底也行。作者的标准：把所有步骤走两遍，想不出还有什么没测。

🤔

是分区还是边界？无所谓！

一个用例是在「分区」步骤还是「边界」步骤冒出来的不重要，重要的是它冒出来了。

🎯

on/off 点就够了

它们本身就属于各自的分区。但加几个 in/out 点也无妨 —— 更贴近真实输入，也帮助理解。

🌱

用同一个「种子」输入

所有用例都基于 "abc" 做微调：一个失败时，很容易和相邻的通过用例对比。

💥

组合爆炸时要务实

异常情况单独测；用领域知识削减；如果一个方法组合太多，考虑把它拆成两个方法。

📏

拿不准就选最简单的输入

能用小整数就别用大整数，能用 5 个字符就别用 100 个。失败时更容易调试。

🧹

不关心的输入也给合理值

某个参数和当前测的逻辑无关？传一个贴近真实的值，别让它干扰测试。

🚫

null 要测，但要有意义

离 UI 近的代码多测 null、空串、怪异数字；如果架构已保证数据在到达前被清洗过，可以省略。只写可能抓到 Bug 的测试。

📋

骨架相同就参数化

一点重复没关系，大量重复就是问题。21 个几乎一样的方法 × 5 行 = 105 行，参数化能大幅压缩。

📐

需求可以是任意粒度

七步法同样适用于跨多个类的大需求，第 9 章会用在更大的测试上。

🧠

经验和创造力仍然重要

老手可能知道空格无关紧要而跳过，新手可能多写一个「没用」的测试。流程帮你记住该想什么，但思考还得你自己来。

有状态的类怎么测？

前两个方法都没有状态，只需考虑输入输出。但面向对象系统里，类是有状态的。比如购物车的 totalPrice() 需要先往车里放商品才能工作：

  • 需求是生成测试最重要的原材料。
  • 规格测试帮助我们系统地探索需求：考察每个输入变量的取值空间，以及它们之间如何相互作用。
  • 七步法：理解需求 → 探索程序 → 划分分区 → 分析边界 → 设计用例 → 自动化 → 用创造力和经验增补。
  • Bug 爱边界。但找出边界可能是规格测试中最难的部分。
  • 即使是简单程序，用例数量也可能太多，你必须决定测什么、不测什么。

自测练习

2.1　对一个 Map 的 put(key, value) 方法（文档：key 为 null 抛 RuntimeException；已有 key 则替换并返回旧值，否则返回 null）做规格测试，下列哪项说法是错误的？（A 规格没说 value 的细节，要靠经验分区　B 组合数增长快，但对 put 不是问题　C 面向对象中还要考虑对象内部状态　D 没有源代码就无法完成类别划分法）

D 是错的。规格测试是黑盒技术，不需要源代码。

2.2　find <pattern> <file> 的分区组合太多了（模式长度、引号、文件名、文件中出现次数、单行出现次数），怎么削减？
  • 把「文件不存在」和「省略文件名」视为异常情况，只测一次；
  • 把「模式为空」视为异常，只测一次；
  • 把「引号不正确」视为异常，只测一次；
  • 「单行出现次数」只在「文件中出现次数」为一次或多次时才组合 —— 文件里一次都没出现，谈不上单行出现几次。
2.3　邮编由 4 位数字（[1000, 4000]）和 2 个字母（[C, M]）组成，例如 2628CD。除了显而易见的边界，你还能想到哪些值得测的情况？

没有标准答案，关键是说明理由。例如：负数要不要单独测？末尾零？Integer.MAX_VALUE 这种极端值？只有 1 个或多于 2 个字母？小写字母（程序能否区分大小写）？可能的非法分区：[Integer.MIN_VALUE, 999]、[4001, Integer.MAX_VALUE]、[A, B]、[N, Z]、[0, 999]、[AAA, ZZZ]。

2.4　FizzBuzz 的测试 T1=15、T2=30、T3=8、T4=6、T5=25，哪个可以删？依据什么概念？

按分区（等价类）分组：能被 3 和 5 整除 —— T1、T2；只被 3 整除 —— T4；只被 5 整除 —— T5；都不能 —— T3。只有第一个分区有两个用例，所以可以删掉 T1 或 T2 中的一个。

2.5　条件 numberOfPoints <= 570 的 on 点和 off 点是？

on 点 = 570，off 点 = 571。on 点直接从条件读出，它让条件为真；off 点是离它最近、让条件为假的点。

2.6　等式 x == 10 的 on 点和 off 点是？

on 点是 10。等式两边都可以让条件变假，所以有两个 off 点：9 和 11。
