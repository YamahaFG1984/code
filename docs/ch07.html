第 7 章

为可测试性而设计

任何系统都能测，只是有的好测、有的难测。如果为了一个测试用例，要先搭三个 Web 服务、在不同目录建五个文件、把数据库调到特定状态， 测完还要逐一检查它们 —— 能做到，但真的必须这么复杂吗？ 可测试性（testability）就是为一个系统、类或方法写自动化测试有多容易。这一章从架构、类、方法三个层面讲怎么让代码好测。

本章目标

  • 把基础设施代码和领域代码分开：六边形架构（端口与适配器）
  • 通过依赖注入和依赖倒置提升可控性
  • 通过合适的方法和返回值提升可观察性
  • 权衡「依赖从构造函数传入」还是「值从参数传入」
  • 学会「倾听测试」：从难写的测试中读出设计问题
🔑 什么时候考虑可测试性？

一直都要。大部分发生在实现功能的过程中，所以在第 1 章的流程图里它属于左边「用测试引导开发」。有时写代码时没发现不可测的地方，到了测试阶段才冒出来，那就回去重构。 有人说为可测试性设计更难、代码更多 —— 也许是真的，写意大利面条式代码确实更容易。但好的、可测的代码虽然更贵，却是保证质量的唯一途径。

把基础设施与领域分开

如果只能给一条建议，作者会说：把基础设施代码和领域代码分开。

领域（domain）
系统的核心：业务规则、逻辑、实体、服务。例如 Invoice、ChristmasDiscount。
基础设施（infrastructure）
处理外部依赖的代码：数据库查询、Web 服务调用、文件读写。前面所有的 DAO 都属于这一类。

两者混在一起时，系统就难测了。看这个把 SQL 直接写在里面的 InvoiceFilter：

public class InvoiceFilter {

  private List<Invoice> all() {           // 直接从数据库取所有发票
    try {
      Connection connection = DriverManager.getConnection("db", "root", "");
      PreparedStatement ps = connection.prepareStatement("select * from invoice");
      ResultSet rs = ps.executeQuery();

      List<Invoice> allInvoices = new ArrayList<>();
      while (rs.next()) {
        allInvoices.add(new Invoice(rs.getString("name"), rs.getInt("value")));
      }
      ps.close();
      connection.close();
      return allInvoices;
    } catch (Exception e) {
      // 处理异常：数据库 API 总要处理一堆异常
    }
  }

  public List<Invoice> lowValueInvoices() {
    List<Invoice> issuedInvoices = all();  // 业务规则调用同一个类里的数据库代码
    return issuedInvoices.stream()
        .filter(invoice -> invoice.getValue() < 100)
        .collect(toList());
  }
}

import sqlite3

class InvoiceFilter:

    def _all(self) -> list[Invoice]:        # 直接从数据库取所有发票
        connection = sqlite3.connect("invoices.db")
        try:
            rows = connection.execute("select name, value from invoice").fetchall()
            return [Invoice(name, value) for name, value in rows]
        finally:
            connection.close()

    def low_value_invoices(self) -> list[Invoice]:
        issued = self._all()                # 业务规则调用同一个类里的数据库代码
        return [inv for inv in issued if inv.value < 100]

import { DatabaseSync } from "node:sqlite";

export class InvoiceFilter {
  private all(): Invoice[] {                // 直接从数据库取所有发票
    const db = new DatabaseSync("invoices.db");
    try {
      return db.prepare("select name, value from invoice").all()
        .map((r) => ({ customer: String(r.name), value: Number(r.value) }));
    } finally {
      db.close();
    }
  }

  lowValueInvoices(): Invoice[] {
    const issued = this.all();              // 业务规则调用同一个类里的数据库代码
    return issued.filter((invoice) => invoice.value < 100);
  }
}
  • 领域和基础设施混在一起。测「低金额发票」规则时绕不开数据库 —— 你怎么在调用公有方法时 Stub 掉一个私有方法？
  • 职责越多，越复杂，Bug 越多。内聚性差的类代码更多，这个类可能同时有 SQL 的 Bug 和业务逻辑的 Bug。实证研究表明，更长的方法和类更容易有缺陷（Shatnawi 和 Li，2006）。
  • 设计用例也更费脑。简单的代码可探索的情况也少；职责越多，越要考虑功能之间的相互作用。

基础设施并不是唯一的外部影响。用户界面也常常和领域代码混在一起，这同样不利于测试 —— 检验业务规则时不应该需要用户界面。

六边形架构：端口与适配器

最简单的解释方式是 Alistair Cockburn（2005）提出的端口与适配器（Ports and Adapters）模式，也叫六边形架构： 领域（业务逻辑）依赖的是端口，而不是直接依赖基础设施。端口是接口，定义了基础设施能做什么，与基础设施的具体实现完全分离； 适配器是端口的实现，紧贴基础设施，知道如何与数据库、Web 服务等通信。

例子：处理已付款的购物车

📋 需求

对今天所有已付款的购物车，系统应该：

  • 把购物车状态设为「待发货」，并把新状态持久化到数据库；
  • 通知配送中心，让他们给客户发货；
  • 通知 SAP 系统；
  • 给客户发一封确认付款成功的邮件，附上预计送达日期（该信息由配送中心 API 提供）。

第一步：分清什么属于应用（六边形内部），什么不属于。与 ShoppingCart 相关的业务规则（比如改变状态）以及付款后的整个流程，属于内部； 发邮件、与 SAP 通信、与配送中心 API 通信、访问数据库，都由外部系统处理，需要为它们设计端口和适配器：

领域类 PaidShoppingCartsBatch 的自然实现里，没有一丁点基础设施细节：

public class PaidShoppingCartsBatch {
  private ShoppingCartRepository db;
  private DeliveryCenter deliveryCenter;
  private CustomerNotifier notifier;
  private SAP sap;

  // 所有依赖都注入：测试时可以传入 Stub 和 Mock
  public PaidShoppingCartsBatch(ShoppingCartRepository db, DeliveryCenter deliveryCenter,
                                CustomerNotifier notifier, SAP sap) {
    this.db = db;
    this.deliveryCenter = deliveryCenter;
    this.notifier = notifier;
    this.sap = sap;
  }

  public void processAll() {
    List<ShoppingCart> paidShoppingCarts = db.cartsPaidToday();
    for (ShoppingCart cart : paidShoppingCarts) {
      LocalDate estimatedDayOfDelivery = deliveryCenter.deliver(cart);  // 通知配送中心
      cart.markAsReadyForDelivery(estimatedDayOfDelivery);             // 标记待发货
      db.persist(cart);                                                // 持久化
      notifier.sendEstimatedDeliveryNotification(cart);                // 通知客户
      sap.cartReadyForDelivery(cart);                                  // 通知 SAP
    }
  }
}

为什么这能提升可测试性？领域类只依赖端口，所以 Stub 和 Mock 端口，就能检验领域逻辑的全部行为。配送中心适配器是否正确工作？这里不关心，那由它自己的测试负责：

ⓘ 每个端口都要一个接口吗？

「分离基础设施与领域」不仅出现在六边形架构中，也出现在 Evans 的《领域驱动设计》（2004）和 Martin 的《整洁架构》（2018）里。 初学者常问：每个端口都必须建接口吗？当然不必。作者只在看到不止一种实现时才建接口。即使没有接口，也要保证具体实现不泄露实现细节。上下文和务实才是王道。

⚠ 别被「就一行 SQL 而已」诱惑

「只是一个简单的数据库调用，直接写这儿多方便！」—— 写出不可测的代码总是更容易，但它迟早会反咬你一口。

依赖注入与可控性

在类的层面，最重要的建议是：确保类可控（你能轻松控制被测类做什么）且可观察（你能看到它做了什么、检查它的结果）。

实现可控性最常用的策略就是第 6 章的做法：如果一个类依赖另一个类，就让这个依赖可以被 Mock、Fake 或 Stub 轻松替换。看看同样的逻辑，写得很差的版本：

几乎一模一样的实现，却难测得多。写出不可测的代码就是这么容易。让依赖可以被注入（通过构造函数，复杂情况下通过 setter）会在很多方面改善代码：

能 Mock

测试时可以 Mock 或 Stub 依赖，提高测试阶段的效率。

依赖显式化

所有依赖都必须被注入，一眼就能看出这个类需要什么。

关注点分离

类不必操心如何构造它的依赖。

更易扩展

与测试无关，但调用方可以通过构造函数传入任何实现。

ⓘ 依赖注入框架

Java 有 Spring、Google Guice；Python 有 dependency-injector、FastAPI 的 Depends；TypeScript 有 NestJS、InversifyJS、tsyringe。只要类允许注入依赖，这些框架就能在生产环境自动帮你构建类及其依赖树。测试时通常不需要它们 —— 手动把 Mock 传进去就行。

依赖倒置原则

为领域与基础设施之间的交互设计抽象的接口（端口），能更好地分离关注点、降低层与层之间的耦合。依赖倒置原则（注意是 inversion 倒置，不是 injection 注入）把这些概念形式化：

  1. 高层模块（如业务类）不应该依赖低层模块，两者都应该依赖抽象（如接口）。
  2. 抽象不应该依赖细节，细节（具体实现）应该依赖抽象。

规律是：尽量依赖抽象，尽量少依赖细节。抽象不那么脆弱，也不那么容易变；你不会希望每次低层细节一变，代码就得跟着改。 当然，给所有东西建接口工作量太大。作者更在意的是：每个类都对使用者提供清晰的接口，不泄露内部细节 —— 也就是良好的封装。

这和测试有什么关系？单元测试时你会 Mock 依赖，而 Mock 时自然要依赖被 Mock 类提供的契约。被 Mock 的类越复杂，测试越难写。 按端口与适配器、依赖倒置的思路设计，端口的接口自然简单、内聚、直截了当。比如 cartsPaidToday()，一看就知道干什么，Mock 它轻而易举； 而它的适配器实现可能满是数据库代码和 SQL。把端口设计得简单，代码也就更容易测。

让类和方法可观察

可观察性是指断言功能行为是否符合预期有多容易。建议：让类为开发者提供简单的方式来断言它的状态。 类生成了一个对象列表要逐一断言？提供一个 getListOfSomething。类调用了别的类？确保这些依赖可以被 Mock。类内部改了很多属性但没法（或不该）提供 getter？提供一个简单的 isValid()。 不要害怕为了方便测试引入简单的 getter 或简单的方案。

例 1：增加方法来方便断言

例 2：观察 void 方法的行为

方法有返回值时，断言返回值很自然。可 void 方法什么都不返回，断言什么？如果要断言的东西还留在方法内部，就更麻烦了。下面这个方法根据购物车生成分期付款：

import calendar
from dataclasses import dataclass
from datetime import date

def add_months(d: date, n: int) -> date:
    """和 Java 的 plusMonths 一样：目标月份没有这一天时，取该月最后一天。"""
    m = d.month - 1 + n
    y, m = d.year + m // 12, m % 12 + 1
    return d.replace(year=y, month=m, day=min(d.day, calendar.monthrange(y, m)[1]))

class Installment:
    date: date
    value: float

/** 和 Java 的 plusMonths 一样：目标月份没有这一天时，取该月最后一天。 */
export function addMonths(d: Date, n: number): Date {
  const target = new Date(d.getFullYear(), d.getMonth() + n, 1);
  const lastDay = new Date(target.getFullYear(), target.getMonth() + 1, 0).getDate();
  return new Date(target.getFullYear(), target.getMonth(), Math.min(d.getDate(), lastDay));
}

🔎 真实发现：这个测试每年会莫名失败约 25 天

仔细看：生成器是一个月一个月地累加（next = next.plusMonths(1)），测试却是从今天直接加 k 个月（now().plusMonths(k)）。 两者在月末会分道扬镳：如果今天是 1 月 31 日，生成器得到 2 月 28 日 → 3 月 28 日 → …，测试却期望 3 月 31 日。 我们用 Java 把 2026 年每一天都模拟了一遍：有 25 天，仓库里的 InstallmentGeneratorTest 会失败（比如从 1 月 29–31 日、3 月 31 日、5 月 29–31 日开始的日子）。 Python 和 TypeScript 版本用了同样的「月末取最后一天」规则，行为完全一致。

这是一个典型的不稳定测试（flaky test）：它不依赖你改了什么代码，而依赖你在哪天运行它。根源有两个： ① 生产代码和测试代码都偷偷调用了「今天」，测试无法控制它 —— 缺乏可控性； ② 需求本身有歧义：1 月 31 日开始的分期，第二期该是 3 月 28 日还是 3 月 31 日？这要问产品负责人。 修复方法正是本章的内容：把「今天」变成可注入的依赖（或参数），然后用 1 月 31 日这样的边界日期写一个确定的测试。

🔑 作者的经验法则

构造函数接收依赖，让类和它的测试稍复杂，但简化了调用者；参数接收数据，让类和它的测试更简单，但让调用者稍复杂。软件工程就是权衡。作者总是选择简化调用者的工作 —— 宁可 ChristmasDiscount 复杂一点、依赖 Clock，也不让所有调用者都去拿今天的日期。

倾听你的测试

如果你留心（很多开发者说「倾听」）你的测试，它们会给你关于代码设计的提示。因为测试代码做的全部事情，就是使用生产类：

下面是作者写测试时会留意的信号（它们只是症状，最终由你判断；也只基于作者的经验，并未经过科学验证）：

被测类的内聚性

内聚是指一个模块、类或方法只有一个职责。多职责的类天生更复杂、更难理解。

  • 非内聚的类有非常大的测试集。留意你为一个类或方法写了多少测试。如果超出了你认为合理的程度，也许该重新审视它的职责了。常见的重构是一分为二。
  • 非内聚的类的测试集永远在增长。你期望类在某个时候趋于稳定。如果总是回到同一个测试类加新测试，可能是设计不好，通常是缺少合适的抽象 —— 这同时违反了 SOLID 的单一职责原则（SRP）和开闭原则（OCP）。常见的重构是建一个抽象代表不同的角色，把每条计算规则移到自己的类里（可以搜一搜策略模式）。

被测类的耦合度

  • 测试代码里要实例化很多依赖，可能是个信号。考虑重新设计，比如把这个类实现的大行为拆成两步。有时耦合不可避免，我们能做的只是更好地管理它。
  • ATest（本应测 A）失败了，调试后发现问题出在 B。这是依赖问题的明显信号：B 的问题泄漏到了 A。该重新评估这些类如何耦合、如何交互了。

复杂条件与可测试性

非常复杂的条件（由多个布尔运算组成的 if）要求测试者付出大量努力：做了边界测试或条件+分支覆盖后，用例可能多得惊人。把它们拆成多个更小的条件不会减少问题的总复杂度，但至少能把它分散开。

私有方法与可测试性

要不要测私有方法？原则上只通过公有方法测它。但测试者常常忍不住想单独测某个私有方法 —— 常见原因是缺乏内聚，或者这个私有方法太复杂。 这正是测试在对你说话：这个私有方法可能不属于它现在的位置。常见的重构是把它提取出来，也许放进一个全新的类。在那里，原来的私有方法变成公有方法，可以正常测试；原来的类则依赖这个新类。

静态方法、单例与可测试性

静态方法不利于可测试性，所以尽量避免创建它们（工具方法除外，它们通常不会被 Mock）。如果系统必须依赖某个静态方法（比如来自框架），在它之上加一层抽象 —— 就像上一章对 LocalDate 做的那样 —— 可能是个好决定。 外部依赖同理：别怕创建这些额外的层，看似增加了设计的复杂度，但提升的可测试性是值得的。

单例（Singleton）模式也损害可测试性。它保证整个系统中某个类只有一个实例，就像一个贯穿程序整个生命周期的全局变量。 测试使用单例的系统时，常常要在测试集里额外写代码，在不同用例之间重置或替换这个单例。

六边形架构与「把 Mock 当作设计技术」

了解了端口和适配器，我们就能理解「Mock 派」（mockist）如何把 Mock 当作设计技术：开发一个功能时，发现需要某个外部的东西，就让一个端口浮现出来。 端口是一个接口，让你不必被适配器的具体实现打扰，继续开发功能的其余部分。Mock 派把这当作设计活动：思考端口应该向应用核心提供什么契约，建模出最好的接口。 作者也是这样：写一个类时发现需要别的东西，就让一个接口浮现出来代表它，想清楚需要什么，继续写；具体的适配器以后再实现。这让他能专注于手头的类。

本章小结

  • 写测试可能容易也可能很难，不可测的代码让我们的生活更艰难。努力写出容易（至少更容易）测试的代码。
  • 把基础设施和领域代码分开。基础设施让测试更难写；分开后，领域逻辑的单元测试就便宜得多。
  • 确保类容易控制、容易观察。可控性通常靠控制被测类的依赖来实现；可观察性靠类提供简便的方式让测试断言预期行为。
  • 不要以你不认同的方式修改代码，但也要务实。作者完全支持为了方便测试而修改生产代码。

自测练习

7.1　三位开发者分别说：A「我没法断言被测方法是否正确工作」；B「我需要确保这个类以 false 的布尔值开始，但做不到」；C「我创建了 Mock，但没办法把它注入类中」。分别是可观察性还是可控性问题？

A：可观察性；B：可控性；C：可控性。

7.2　一个移动 App 团队说写单元测试「很难」，列出了问题：A 很多类混合了基础设施和业务规则；B 数据库表很大且没有索引；C 大量调用库和外部 API；D 有些类的属性/字段太多。预算只够先解决两个，该优先哪两个？

A 和 C。领域与基础设施分离对可测试性至关重要 —— 一段既有业务规则又访问数据库或外部 API 的代码，你怎么给它写单元测试？至于 B，单元测试里数据库会被 Mock，表多大无所谓；D 意味着测试要多做一些准备工作，但并不妨碍写测试。

7.3　如何提升下面这个 OrderDeliveryBatch 的可测试性？ 
public class OrderDeliveryBatch {
  public void runBatch() {
    OrderDao dao = new OrderDao();                          // 访问数据库
    DeliveryStartProcess delivery = new DeliveryStartProcess();   // 调第三方 Web 服务
    List<Order> orders = dao.paidButNotDelivered();
    for (Order order : orders) {
      delivery.start(order);
      if (order.isInternational()) {
        order.setDeliveryDate("5 days from now");
      } else {
        order.setDeliveryDate("2 days from now");
      }
    }
  }
}

要对 runBatch 做单元测试，至少需要能对 dao 和 delivery 使用 Mock 或 Stub。当前实现做不到，因为无法从类外部替换它们 —— 需要提升可控性。让依赖可以被注入（依赖注入），就能使用 Mock 和 Stub。

7.4　怎样让 KingsDayDiscount（4 月 27 日国王节打折，内部调用 Calendar.getInstance()）更可测？

当前实现缺乏可控性：getInstance 是静态方法，无法改变它给出的值。虽然新版 Mockito 可以 Mock 静态方法，但应尽量避免。解决办法：要么把日期作为方法参数传入，要么注入一个 Clock（Calendar 或任何日期类之上的一层包装）。
