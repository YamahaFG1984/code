第 4 章

契约式设计

类和类之间互相调用，就像签合同：调用方保证传进来的东西合规，被调用方保证交出去的东西靠谱。 把这份「合同」—— 前置条件、后置条件、不变式 —— 明明白白写进代码里，Bug 就会在第一时间、在离根源最近的地方暴露出来。 这一章讲怎么设计契约、怎么改契约不翻车，以及契约和输入校验到底有什么区别。

本章目标

  • 为方法设计前置条件和后置条件，为类设计不变式
  • 理解强契约与弱契约的取舍
  • 判断修改契约是否会破坏调用方，理解里氏替换原则
  • 分清输入校验和契约，知道断言和异常各该用在哪

三种应对「非法输入」的方式

想象一个处理复杂金融流程的系统：一长串类依次调用，前一个的结果传给下一个。数据来自数据库、外部服务和用户。 流程中某处会调用 TaxCalculator，而根据需求，税款计算只对正数有意义。这个限制该怎么建模？

契约是在写代码的时候就要思考的，所以在第 1 章的流程图里，契约式设计位于左边「用测试引导开发」那一侧，而不是右边的「测试找 Bug」。

前置条件与后置条件

对 TaxCalculator：前置条件是「不接受负数」，一个合理的后置条件是「也不返回负数」。把它们写进代码，最简单的方式就是 if：

public class TaxCalculator {

  /**
   * 按照（某某规则）计算税款。
   *
   * @param value 计税基数。必须是正数。
   * @return 计算出的税款。永远是正数。
   */
  public double calculateTax(double value) {
    // 前置条件
    if (value < 0) {
      throw new RuntimeException("Value has to be positive");
    }

    double taxValue = 0;
    // 这里是一些复杂的业务规则……
    // 最终结果放进 taxValue

    // 后置条件
    if (taxValue < 0) {
      throw new RuntimeException("Calculated tax cannot be negative");
    }
    return taxValue;
  }
}

class TaxCalculator:

    def calculate_tax(self, value: float) -> float:

        :param value: 计税基数。必须是正数。
        :return: 计算出的税款。永远是正数。
        """

        if value < 0:

        tax_value = 0.0

        # 最终结果放进 tax_value

        # 后置条件
        if tax_value < 0:

    }

}
ⓘ 后置条件是我自己实现的，怎么会违反？

你当然希望实现永远不返回负数。但在复杂的实现里，Bug 总会溜进来 —— 如果 Bug 不存在，这本书也就没必要写了。 后置条件检查保证：一旦实现有 Bug，方法会抛异常，而不是悄悄返回一个错误的值。程序停下来，往往比带着错误值继续跑要好得多。 另外，别忘了把契约写进文档注释（上面的 Javadoc / docstring / JSDoc）。

用断言表达契约

很多语言提供了原生的断言机制。用断言改写上面的方法：

public double calculateTax(double value) {
  assert value >= 0 : "Value cannot be negative";        // 前置条件

  double taxValue = 0;
  // 这里是一些复杂的业务规则……

  assert taxValue >= 0 : "Calculated tax value cannot be negative.";   // 后置条件
  return taxValue;
}
// 注意：Java 的 assert 默认是关闭的，要用 java -ea（enable assertions）启动才会检查

def calculate_tax(self, value: float) -> float:
    assert value >= 0, "value cannot be negative"          # 前置条件

    tax_value = 0.0
    # 这里是一些复杂的业务规则……

    assert tax_value >= 0, "calculated tax cannot be negative"   # 后置条件
    return tax_value
# 注意：Python 的 assert 默认开启，但用 python -O 运行时会被整体移除

// TS/JS 没有 assert 关键字。可以用 node:assert，或者自己写一个断言函数。
// "asserts cond" 是 TypeScript 的断言签名：调用之后，编译器会认为 cond 为真。
export function invariant(cond: unknown, msg: string): asserts cond {
  if (!cond) throw new Error(`Contract violated: ${msg}`);
}

calculateTax(value: number): number {
  invariant(value >= 0, "value cannot be negative");            // 前置条件

  let taxValue = 0;
  // 这里是一些复杂的业务规则……

  invariant(taxValue >= 0, "calculated tax cannot be negative"); // 后置条件
  return taxValue;
}
// 注意：自己写的断言永远会执行，没有「关掉」的开关（除非构建时专门剥离）
断言（assert）if + 抛异常
能被关掉吗Java 默认关，需 -ea；Python 用 -O 会移除永远执行
抛出什么通用的 AssertionError可以抛更具体、调用方能处理的异常
适合你能完全控制运行环境、数据已被清洗过的内部代码库、工具类，或者不确定生产环境是否开启断言时

用哪个需要团队讨论（后面 「断言还是异常」一节有作者的经验法则）。本章剩下的部分为了简洁使用断言。

强契约与弱契约

设计契约时的一个重要决定是：条件要多强？上面我们对负数的处理很强：负数进来就违反前置条件，程序停止。 另一种选择是削弱前置条件 —— 接受任何值，由方法自己想办法处理负数：

弱前置条件让别的类更容易调用这个方法。没有标准答案，取决于你在开发什么系统、对调用方有什么期望。 作者偏爱更强的条件，因为它们缩小了可能出错的范围 —— 代价是要花更多时间把条件写成断言，代码更复杂。

后置条件也能削弱吗？作者说他想不起来自己这么做过哪怕一次。对税款来说，负数意味着实现有 Bug，你肯定不希望有人因此少交税。

有时候前置条件不能削弱（税款就是不能算负数），但又不想让程序停下来。务实的做法是返回一个错误值：

public double calculateTax(double value) {
  if (value < 0) {
    return 0;       // 调用方不用处理异常了，但它得知道「0 可能意味着输入非法」
  }
  // ……
}

def calculate_tax(self, value: float) -> float:
    if value < 0:
        return 0.0  # 调用方不用处理异常了，但它得知道「0 可能意味着输入非法」
    # ……

calculateTax(value: number): number {
  if (value < 0) {
    return 0;       // 调用方不用处理异常了，但它得知道「0 可能意味着输入非法」
  }
  // ……
}

调用方现在必须知道：收到 0 可能是因为输入非法。也许返回 -1 更好，能和「税款恰好为 0」区分开。这又是一个需要权衡的决定。

🔎 和经典理论的区别

熟悉 Meyer 1992 年原始契约式设计理论的读者请注意：这里返回错误码并不是削弱前置条件，而是选择用错误码代替异常。 作者对契约的理解比原始论文更务实：重要的是认真思考类和方法能处理什么、不能处理什么，以及违反时该怎么办。

不变式

前置条件在方法执行前成立，后置条件在方法执行后成立。还有一类条件，在方法执行前后都必须成立 —— 这叫不变式（invariant）： 在对象整个生命周期中始终为真的条件。

来看一个购物车 Basket：add(product, qty) 加入商品，remove(product) 把某商品整个移除。先设计每个方法的前后置条件：

方法前置条件后置条件
addproduct 不为 null；qty > 0商品已在购物车中；新总价 > 旧总价
removeproduct 不为 null；商品必须已在购物车中商品不再在购物车中
不变式：totalValue ≥ 0 —— 它既不是前置也不是后置条件，而是整个类负责维护的承诺

下面是完整实现（本仓库 ch5/Basket.java，下一章会用属性测试狠狠地测它）：

public class Basket {
  // 用 BigDecimal 而不是 double，避免浮点舍入误差
  private BigDecimal totalValue = BigDecimal.ZERO;
  private Map<Product, Integer> basket = new HashMap<>();

  public void add(Product product, int qtyToAdd) {
    assert product != null : "Product is required";                  // 前置
    assert qtyToAdd > 0 : "Quantity has to be greater than zero";    // 前置
    BigDecimal oldTotalValue = totalValue;       // 为后置条件保存旧值

    int existingQuantity = basket.getOrDefault(product, 0);
    int newQuantity = existingQuantity + qtyToAdd;
    basket.put(product, newQuantity);

    BigDecimal valueAlreadyInTheCart = product.getPrice().multiply(valueOf(existingQuantity));
    BigDecimal newFinalValueForTheProduct = product.getPrice().multiply(valueOf(newQuantity));
    totalValue = totalValue
        .subtract(valueAlreadyInTheCart)
        .add(newFinalValueForTheProduct);

    assert basket.containsKey(product) : "Product was not inserted in the basket";   // 后置
    assert totalValue.compareTo(oldTotalValue) == 1 :
        "Total value should be greater than previous total value";                  // 后置
    assert invariant() : "Invariant does not hold";                                  // 不变式
  }

  public void remove(Product product) {
    assert product != null : "product can't be null";                          // 前置
    assert basket.containsKey(product) : "Product must already be in the basket";  // 前置

    int qty = basket.get(product);
    totalValue = totalValue.subtract(product.getPrice().multiply(valueOf(qty)));
    basket.remove(product);

    assert !basket.containsKey(product) : "Product is still in the basket";    // 后置
    assert invariant() : "Invariant does not hold";                            // 不变式
  }

  // 把不变式抽成一个方法，每个公有方法结尾都调用它
  private boolean invariant() {
    return totalValue.compareTo(BigDecimal.ZERO) >= 0;
  }
}

from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)          # frozen → 可哈希，能当 dict 的 key
class Product:
    name: str
    price: Decimal               # 用 Decimal 而不是 float，避免浮点舍入误差

class Basket:
    def __init__(self):
        self.total_value = Decimal("0")
        self._basket: dict[Product, int] = {}

    def add(self, product: Product, qty_to_add: int) -> None:
        assert product is not None, "product is required"                 # 前置
        assert qty_to_add > 0, "quantity has to be greater than zero"     # 前置
        old_total_value = self.total_value     # 为后置条件保存旧值

        existing = self._basket.get(product, 0)
        new_qty = existing + qty_to_add
        self._basket[product] = new_qty
        self.total_value = (self.total_value
                            - product.price * existing
                            + product.price * new_qty)

        assert product in self._basket, "product was not inserted"         # 后置
        assert self.total_value > old_total_value, "total should grow"     # 后置
        assert self._invariant(), "invariant does not hold"                # 不变式

    def remove(self, product: Product) -> None:
        assert product is not None, "product can't be None"                # 前置
        assert product in self._basket, "product must be in the basket"    # 前置

        qty = self._basket.pop(product)
        self.total_value -= product.price * qty

        assert product not in self._basket, "product is still in the basket"  # 后置
        assert self._invariant(), "invariant does not hold"                   # 不变式

    def _invariant(self) -> bool:
        return self.total_value >= 0

import { invariant } from "./contracts";

export interface Product {
  name: string;
  priceInCents: number;   // JS 没有内置十进制类型：用「分」做整数，避免浮点误差
}

export class Basket {
  totalValueInCents = 0;
  // 注意：JS 的 Map 按「引用」比较对象键，不像 Java 那样用 equals/hashCode。
  // 所以这里用商品名做键。
  private items = new Map<string, { product: Product; qty: number }>();

  add(product: Product, qtyToAdd: number): void {
    invariant(product != null, "product is required");                  // 前置
    invariant(qtyToAdd > 0, "quantity has to be greater than zero");    // 前置
    const oldTotal = this.totalValueInCents;   // 为后置条件保存旧值

    const existing = this.items.get(product.name)?.qty ?? 0;
    const newQty = existing + qtyToAdd;
    this.items.set(product.name, { product, qty: newQty });
    this.totalValueInCents += product.priceInCents * (newQty - existing);

    invariant(this.items.has(product.name), "product was not inserted");  // 后置
    invariant(this.totalValueInCents > oldTotal, "total should grow");    // 后置
    invariant(this.holds(), "invariant does not hold");                   // 不变式
  }

  remove(product: Product): void {
    invariant(product != null, "product can't be null");                  // 前置
    const entry = this.items.get(product.name);
    invariant(entry, "product must already be in the basket");             // 前置

    this.totalValueInCents -= entry.product.priceInCents * entry.qty;
    this.items.delete(product.name);

    invariant(!this.items.has(product.name), "product is still in the basket");  // 后置
    invariant(this.holds(), "invariant does not hold");                          // 不变式
  }

  private holds(): boolean {
    return this.totalValueInCents >= 0;
  }
}
💡 几个细节
  • 保存旧值：「新总价 > 旧总价」这种后置条件需要额外变量保存旧值。Eiffel 这类语言原生提供 old 关键字，不需要额外变量。
  • 钱不要用浮点数：Java 用 BigDecimal（代价是比较要写 compareTo），Python 用 Decimal，JS/TS 常用「分」为单位的整数。
  • 不变式可以暂时被打破：方法执行到一半时，作为算法的一部分，不变式可能短暂不成立；但方法结束时必须恢复。
  • 这个类怎么测？add 和 remove 可以以任意顺序、任意次数组合调用，不可能穷举。答案在第 5 章：属性测试。

修改契约与里氏替换原则

理想情况下，契约定义好就不再改。现实中，我们有时不得不改。改变可能无法避免，但我们可以理解它的影响。 最好的方法不是盯着被改的类，而是看所有使用它的类：

把规律总结成一张表（「强」= 限制更多、值域更小，「弱」= 限制更少、值域更大）：

改得更强（更严格）改得更弱（更宽松）
前置条件
调用方要满足的		 ✘ 可能破坏调用方
例：value ≥ 0 → value ≥ 100，传 50 的调用方崩溃		 ✔ 安全
例：改成接受负数，旧调用方都没问题
后置条件
方法承诺给出的		 ✔ 安全
例：承诺返回 ≥ 100，旧调用方本来就准备好接受 ≥ 0		 ✘ 可能破坏调用方
例：开始返回负数，调用方没准备好处理
🔑 一句话记住

要求可以放宽，承诺不能打折。前置条件只能变弱，后置条件只能变强。

继承与契约

在面向对象语言里，继承让这个问题更隐蔽。TaxCalculator 有几个子类，它们各自重写了 calculateTax()，并以不同方式修改了契约：

客户端在构造函数里接收一个 TaxCalculator。由于多态，传给它的可能是任何子类，而它只能假设对方遵守基类的契约。推广开来，若子类 S 继承基类 B：

  1. S 的前置条件应该等于或弱于 B 的（接受更多的值）。
  2. S 的后置条件应该等于或强于 B 的（返回更少的值）。

「子类可以替换基类而不破坏系统的预期行为」，这就是里氏替换原则（Liskov Substitution Principle，LSP）。 Barbara Liskov 在 1987 年的主题演讲中提出，后来和 Jeannette Wing 在著名论文《A behavioral notion of subtyping》（1994）中完善。 Robert Martin 推广 SOLID 原则后它更加流行 —— SOLID 里的 L 就是 LSP。

ⓘ 更简单的办法

一个众所周知的最佳实践是尽量避免继承（《Effective Java》第 16 条：组合优于继承）。不用继承，自然就没有这些问题。但如果你必须用，现在知道该注意什么了。

契约和测试有什么关系？

🚨

更早、更准地发现 Bug

契约一被违反，程序就停下，错误信息明确指出是哪个条件。没有断言的话，一个非法值可能在系统里游荡很久，在别处引发怪异行为，很难追到根源。

💡

告诉你该测什么

一看到 qty > 0 这个前置条件，你就知道它值得在单元、集成或系统测试中被检验。契约不取代测试，而是补充测试。

🤝

让调用方更轻松

只要调用方满足前置条件，服务方就保证后置条件。承诺只返回正数，调用方就不用再检查返回值是否为负。

🤖

给智能测试当「预言机」

模糊测试（fuzzing）等工具会读取代码中明确写出的契约，想方设法去打破它们。推荐阅读 The Fuzzing Book。

作者并不把契约式设计看作一种测试实践，而是一种设计技术。

现实中的契约式设计

弱还是强？

弱前置条件（比如接受 null）让方法对调用方很友好，但把处理非法输入的负担放在方法自己身上；强前置条件（只接受正数、不接受 null）则把负担放在调用方身上。 没有唯一答案，要结合整体上下文。例如 Apache Commons 的很多方法前置条件都很弱，让 API 用起来很方便 ——库的开发者通常偏爱弱前置条件，以简化用户的生活。

输入校验、契约，还是都要？

输入校验的重要性众所周知：校验出错可能导致安全漏洞。看一个添加商品的 Web 控制器：

class ProductController {
  public void add(String productName, String productDescription, double price) {
    // 参数直接来自最终用户，使用前必须校验
    String sanitizedProductName = sanitize(productName);
    String sanitizedProductDescription = sanitize(productDescription);

    if (!isValidProductName(sanitizedProductName)) {
      errorMessages.add("Invalid product name");
    }
    if (!isValidProductDescription(sanitizedProductDescription)) {
      errorMessages.add("Invalid product description");
    }
    if (!isValidPriceRange(price)) {
      errorMessages.add("Invalid price");
    }

    if (errorMessages.empty()) {      // 全部合法才创建对象
      Product newProduct = new Product(sanitizedProductName, productDescription, price);
      database.save(newProduct);
      redirectTo("productPage", newProduct.getId());
    } else {                          // 否则回到表单页，显示所有错误
      redirectTo("addProduct", errorMessages.getErrors());
    }
  }
}

def add_product(form):
    # 参数直接来自最终用户，使用前必须校验
    name = sanitize(form["name"])
    description = sanitize(form["description"])
    price = form.get("price")

    errors = []
    if not is_valid_product_name(name):
        errors.append("Invalid product name")
    if not is_valid_product_description(description):
        errors.append("Invalid product description")
    if not is_valid_price_range(price):
        errors.append("Invalid price")

    if not errors:                    # 全部合法才创建对象
        product = Product(name, description, price)
        database.save(product)
        return redirect_to("product_page", product.id)
    return redirect_to("add_product", errors=errors)   # 显示所有错误

function addProduct(req: Request, res: Response) {
  // 参数直接来自最终用户，使用前必须校验
  const name = sanitize(req.body.name);
  const description = sanitize(req.body.description);
  const price = Number(req.body.price);

  const errors: string[] = [];
  if (!isValidProductName(name)) errors.push("Invalid product name");
  if (!isValidProductDescription(description)) errors.push("Invalid product description");
  if (!isValidPriceRange(price)) errors.push("Invalid price");

  if (errors.length === 0) {          // 全部合法才创建对象
    const product = new Product(name, description, price);
    database.save(product);
    return res.redirect(`/products/${product.id}`);
  }
  return res.render("addProduct", { errors });   // 显示所有错误
}

数据在创建对象之前已经被校验过了。那还需要在类和方法里写契约吗？先看两者的区别：

输入校验（validation）
防止用户的坏数据渗入系统。预期会发生：用户随时可能在「数量」里填字母。发生时返回友好的提示，通常要一次性列出所有错误。
契约（contract）
保证类之间的通信没有问题。不预期会发生：数据已经校验过了。万一发生了，说明出现了意料之外的情况（Bug），程序停止。

两者目的不同，都应该做。问题是如何避免重复：如果校验已经检查过「描述长度大于 10 个字符」，作者就不会在 Product 构造函数里再把它作为前置条件检查一遍 —— 这意味着架构必须保证：没有经过输入校验，Product 就不会被创建。系统中要有一些「安全区」，进来的数据都已被清洗过。 反过来，如果某条契约非常重要、违反后果严重，作者也不介意多一点重复，在校验时和契约检查时各查一次。 （Arie van Deursen 在 Stack Overflow 上有一个关于两者区别的精彩回答，强烈推荐。）

断言还是异常？

Java 没有表达契约的专门机制（F# 等少数语言有）。assert 不错，但忘了在运行时开启的话，生产环境就不会检查契约，所以很多开发者更喜欢用异常。作者的经验法则：

至于输入校验，作者既不用断言也不用异常，而是用更优雅的方式建模：你很少希望第一个检查失败就停下，更常见的是给用户看一个完整的错误列表；复杂的校验也可能需要大量代码。可以参考 Eric Evans《领域驱动设计》中的规格模式（Specification pattern），以及 John Regehr 的文章《Use of Assertions》（2014）。

本章为了简单使用了 RuntimeException 这类通用异常。实践中你可能更想抛出语义化的异常，比如 NegativeValueException，方便调用方区分业务异常和真正百年一遇的异常。

🔎 术语上的严谨性

形式语义学者并不认为 if + 抛异常属于契约式设计 —— 那叫防御式编程。作者用「契约式设计」这个词，指的是「思考契约并以某种方式把它们显式写进代码」这个理念。

抛异常还是返回「软值」？

  • 如果这是不该发生的行为，调用方收到也不知道怎么办 → 抛异常。比如 calculateTax 收到负数：应该停止程序而不是算出错误结果，监控系统会捕获异常，我们去调试。
  • 如果能给调用方一个让它继续工作的软返回值 → 返回软值。比如一个 trim 字符串的工具方法，前置条件是不接受 null，但遇到 null 时返回空字符串，调用方完全能处理。

什么时候不该用契约式设计？

作者说他想不出一个不用的好理由。面向对象系统的开发，本质上就是让对象能正确地沟通协作。经验表明，把前后置条件和不变式显式写进代码并不昂贵，也不费时。 （这里说的不包括输入校验 —— 那是必须做的，无论你喜不喜欢契约。）

但契约不能取代测试：你无法只靠前置条件、后置条件和不变式来表达一段代码的全部预期行为。用契约保证类与类之间可以放心地沟通，用测试保证类的行为正确。

要为契约写测试吗？

断言、契约检查在某种意义上是从内部测试生产代码。还需要为它们写单元测试吗？ 作者通常会为输入校验写自动化测试，确保校验机制就位且正常工作；但很少为断言写测试，它们会被其他关注业务规则的测试自然覆盖。

如果你的契约是用异常实现的（比如库代码），测试它和测试任何其他行为没有区别：

@Test
void rejectsNegativeValues() {
  assertThatThrownBy(() -> new TaxCalculator().calculateTax(-1))
      .isInstanceOf(RuntimeException.class)
      .hasMessage("Value has to be positive");
}

import pytest
from tax_calculator import TaxCalculator

def test_rejects_negative_values():
    with pytest.raises(ValueError, match="has to be positive"):
        TaxCalculator().calculate_tax(-1)

import { test, expect } from "vitest";
import { TaxCalculator } from "./taxCalculator";

test("rejects negative values", () => {
  expect(() => new TaxCalculator().calculateTax(-1)).toThrow(/has to be positive/);
});

本章小结

  • 契约让类与类之间可以安全地沟通，没有意外。
  • 实践中，设计契约就是显式定义类和方法的前置条件、后置条件和不变式。
  • 选择弱契约还是强契约取决于上下文，各有利弊。
  • 契约式设计不能取代输入校验。两者目的不同，都应该做。
  • 修改契约时，要思考它对所有调用方的影响：前置条件只能变弱，后置条件只能变强。

自测练习

4.1　以下哪个是在代码中使用断言的正当理由？（A 验证有副作用的表达式　B 处理程序中的异常情况　C 做用户输入校验　D 让调试更容易）

D。断言让违反契约的地方立刻暴露，错误信息精确，调试更容易。有副作用的表达式不能放进断言（断言关掉后副作用也没了）；用户输入校验和异常情况处理不该用断言。

4.2　squareAt(x, y) 断言了 x、y 在范围内、board 不为 null，最后断言 result != null。如果删掉最后这条，现有前置条件能保证结果不为 null 吗？还能怎么保证？ 
public Square squareAt(int x, int y) {
  assert x >= 0;
  assert x < board.length;
  assert y >= 0;
  assert y < board[x].length;
  assert board != null;
  Square result = board[x][y];
  assert result != null;
  return result;
}

不能。前置条件只保证 board 本身不为 null、x 和 y 在范围内，但不保证 board 里的元素不为 null。要得到同样的保证，类需要一个不变式：board 中没有任何位置是 null。

4.3　上题中哪些断言可以变成类的不变式？（A x 的范围　B board != null　C result != null　D y 的范围）

B。board 不为 null 是对象整个生命周期都应成立的条件；x、y 是方法参数，result 是局部结果，都不属于对象状态。

4.4　开启断言运行应用，某个第三方库报告类不变式被违反。假设你的应用遵守了库的所有前置条件，该怎么办？

这说明库的实现有问题，需要修复库的代码。你遵守了前置条件，而不变式是库自己负责维护的。关掉断言只是掩盖问题；这也不是接口设计问题或你调用方式的问题。

4.5　静态方法可以有不变式吗？

不能。类不变式关乎整个对象的状态，而静态方法不属于任何对象（无状态），所以类不变式的概念不适用于静态方法。

4.6　类 C 的方法 M 有前置条件 P、后置条件 Q。子类 C' 重写 M 得到 M'，其前置条件 P'、后置条件 Q' 应该满足什么？

P' 等于或弱于 P，Q' 等于或强于 Q。这就是里氏替换原则。
