第 8 章

测试驱动开发

我们习惯了「先写代码，再测试」。为什么不反过来？先写一个测试，描述你想实现的下一个小功能 —— 它当然会失败，因为功能还不存在； 然后写代码让它通过；测试变绿后，回头重构刚写的代码。这就是测试驱动开发（TDD）。 这一章用「罗马数字转整数」完整走一遍 TDD，然后冷静地讨论：它到底好在哪里，研究怎么说，什么时候不必用它。

本章目标

  • 亲手走一遍红—绿—重构循环
  • 理解「小步前进」和「用测试控制节奏」
  • 知道 TDD 的好处、实证研究的结论，以及何时不用它
  • 了解经典派（Detroit）与伦敦派（London）两种 TDD 流派
  • 分清 TDD 和系统化测试：一个帮你开发，一个帮你找 Bug

红—绿—重构

第一次 TDD：罗马数字转换器

📋 需求

实现一个程序，接收一个罗马数字（字符串），返回它的阿拉伯数字表示（整数）。

罗马数字用七个符号：I=1，V=5，X=10，L=50，C=100，D=500，M=1000。组合规则：

  • 右边的数字小于或等于左边时，加上去：XV = 10 + 5 = 15；
  • 左边的数字小于右边时，减掉：XXIV = 10 + 10 − 1 + 5 = 24。

想出例子是 TDD 的一部分。作者想到的例子，按难度分组：

ⓘ 空字符串、null 呢？

值得测。但做 TDD 时，作者先关注正常路径和业务规则，边界和异常情况留到后面。记住：我们现在不是在测试模式，而是在开发模式 —— 想出输入输出，让它们引导实现。实现完成后，再用前几章的所有技术做严格的测试。

每一圈都这样走：

  1. 从清单里挑最简单的例子。
  2. 写一个自动化测试，用这个输入调用程序，断言期望的输出。此时代码可能连编译都过不了；就算能编译，测试也会失败，因为功能还没实现。
  3. 写刚好够让这个测试通过的生产代码。
  4. 停下来反思：可以改进生产代码吗？可以改进测试代码吗？可以往清单里加更多例子吗？
  5. 重复。

ⓘ 测试和生产代码有点重复

测试的输入输出几乎就是生产代码里那张表。用例子做测试时这很常见，写到更复杂的测试时会缓解。

第 4 圈：多个字符（II → 2）

让测试通过的最简单办法是往表里加一行 "II" → 2……但那样就得把 III、IV 等所有组合都加进去，显然不是好主意。该再次推广了：遍历每个符号，累加数值。

public class RomanNumeralConverter {
  private static Map<Character, Integer> table = new HashMap<>() {{   // 键从 String 改成 Character
    put('I', 1);
    put('V', 5);
    put('X', 10);
    put('L', 50);
    put('C', 100);
    put('D', 500);
    put('M', 1000);
  }};

  public int convert(String numberInRoman) {
    int finalNumber = 0;                             // 累加器
    for (int i = 0; i < numberInRoman.length(); i++) {
      finalNumber += table.get(numberInRoman.charAt(i));
    }
    return finalNumber;
  }
}

三个测试依然全绿。要意识到：这一圈我们只关注「多字符」，根本没去想前面的例子。这正是有测试的一大好处：每一步都是稳的，任何破坏已有行为的改动（回归 Bug）都会被测试抓住。 这里的例子是随手挑的 —— 目标不是系统化，只是给开发提供一张安全网。完成后我们再做系统化测试。

这部分算法需要多想一想。从右往左看，罗马数字的符号值是递增的；但当一个符号比它右边的邻居小时，要减掉而不是加上。 技巧：用一个 multiplier，当前符号比上一个看过的邻居小时，它就变成 -1： 

public int convert(String numberInRoman) {
  int finalNumber = 0;
  int lastNeighbor = 0;                                   // 上一个看过的数字（右邻居）
  for (int i = numberInRoman.length() - 1; i >= 0; i--) { // 从右往左
    int current = table.get(numberInRoman.charAt(i));

    int multiplier = 1;
    if (current < lastNeighbor) multiplier = -1;          // 比右邻居小 → 变成负数

    finalNumber += table.get(numberInRoman.charAt(i)) * multiplier;
    lastNeighbor = current;
  }
  return finalNumber;
}

def convert(numeral: str) -> int:
    final_number = 0
    last_neighbor = 0                                     # 上一个看过的数字（右邻居）
    for symbol in reversed(numeral):                      # 从右往左
        current = TABLE[symbol]

        multiplier = 1
        if current < last_neighbor:                       # 比右邻居小 → 变成负数
            multiplier = -1

        final_number += TABLE[symbol] * multiplier
        last_neighbor = current
    return final_number

export function convert(numeral: string): number {
  let finalNumber = 0;
  let lastNeighbor = 0;                                   // 上一个看过的数字（右邻居）
  for (let i = numeral.length - 1; i >= 0; i--) {         // 从右往左
    const current = TABLE[numeral[i]];

    let multiplier = 1;
    if (current < lastNeighbor) multiplier = -1;          // 比右邻居小 → 变成负数

    finalNumber += TABLE[numeral[i]] * multiplier;
    lastNeighbor = current;
  }
  return finalNumber;
}

第 6 圈：重构

测试全绿。有什么可以改进的吗？累加时又查了一次 table.get(...)，可这个值已经存在 current 里了；再引入一个变量表示「乘以 ±1 之后的当前数字」，算法会更好懂。重构，然后再跑一遍测试：

public int convert(String numberInRoman) {
  int finalNumber = 0;
  int lastNeighbor = 0;
  for (int i = numberInRoman.length() - 1; i >= 0; i--) {
    int current = table.get(numberInRoman.charAt(i));

    int multiplier = 1;
    if (current < lastNeighbor) multiplier = -1;

    int currentNumeralToBeAdded = current * multiplier;   // 复用 current，并给结果起个名字
    finalNumber += currentNumeralToBeAdded;

    lastNeighbor = current;
  }
  return finalNumber;
}

TABLE = {"I": 1, "V": 5, "X": 10, "L": 50, "C": 100, "D": 500, "M": 1000}

def convert(numeral: str) -> int:
    final_number = 0
    last_neighbor = 0
    for symbol in reversed(numeral):
        current = TABLE[symbol]
        multiplier = -1 if current < last_neighbor else 1
        current_numeral_to_be_added = current * multiplier   # 复用 current，并给结果起个名字
        final_number += current_numeral_to_be_added
        last_neighbor = current
    return final_number

const TABLE: Record<string, number> = { I: 1, V: 5, X: 10, L: 50, C: 100, D: 500, M: 1000 };

export function convert(numeral: string): number {
  let finalNumber = 0;
  let lastNeighbor = 0;
  for (let i = numeral.length - 1; i >= 0; i--) {
    const current = TABLE[numeral[i]];
    const multiplier = current < lastNeighbor ? -1 : 1;
    const currentNumeralToBeAdded = current * multiplier;   // 复用 current，并给结果起个名字
    finalNumber += currentNumeralToBeAdded;
    lastNeighbor = current;
  }
  return finalNumber;
}

TDD 带来了什么

📋

先看需求

TDD 里的测试基本就是可执行的需求。每写一个，都在思考程序该做什么、不该做什么。这让你只写解决问题所需的代码，也常常促使你回头找需求方问清楚没写明的情况。

🎛

完全掌控节奏

对问题有把握，就迈大步，写一个涵盖复杂情况的测试；没把握，就拆成更小的部分，先为简单的写测试。

⚡

快速反馈

不做 TDD 的开发者往往写了一大块代码才得到反馈。TDD 逼你一次走一步，每一步都停下来反思；距离上次一切尽在掌握只写了一点点代码，新问题很容易定位。

🧪

代码天生可测

先写测试，逼你从一开始就思考怎么（轻松地）测试生产代码。传统流程里，到后期才考虑测试，那时再改代码结构可能很贵。

🎨

设计反馈

测试代码往往是被开发类的第一个客户。如果实例化它、调用它、断言它很难，也许有更好的设计。TDD 让这些问题更早暴露，越早修越便宜。

ⓘ TDD 在复杂问题上最能显示优势

罗马数字只是个小例子。推荐看 James Shore 在 YouTube 上用 TDD 开发整个系统的系列视频（2014），以及 Freeman 和 Pryce 的《测试驱动的面向对象软件开发》（2009），他们也用 TDD 构建了整个系统，并深入讨论了如何用测试指导设计决策。

现实中的 TDD

有人热爱 TDD 并激烈捍卫它，有人建议别用。软件工程实践从来不是银弹。下面的观点是作者个人的，并非基于科学证据。看 TDD 适不适合你，最好的办法就是试一试。

用还是不用？

怀疑的读者可能会想：「不用 TDD 我也能得到这些好处。我可以多想想需求，只写需要的代码，从一开始就考虑可测试性。」没错。 但作者喜欢 TDD，是因为它给了他一种节奏：找到下一个最简单的功能，为它写测试，只实现所需的部分，反思刚才做了什么 —— 他完全掌控这个节奏，避免陷入困惑和沮丧的无限循环。 测试一变绿，就是一个天然的反思时刻。而且 TDD 逼他从一开始就使用正在开发的代码：设计时对一个类的感觉，和真正使用它时的感觉往往不同，两者结合才能做出最好的建模决定。

如果你先写代码后写测试，关键是让两者之间的时间足够短，才能及时得到反馈。不要写一整天代码，然后才开始测试 —— 那可能太晚了。

100% 的时间都用 TDD？

TDD 为作者创造了学习的机会：从实现角度（它做了该做的吗？）和设计角度（结构是我想要的吗？）。我们需要停下来思考的方式，TDD 是完美的方式之一，但不是唯一的。什么时候用 TDD，需要经验来判断。

TDD 适用于所有类型的应用吗？

大多数都适用，甚至有专门讲嵌入式系统 TDD 的书，比如 Grenning 的《Test Driven Development for Embedded C》（2011）。只要你能为应用写自动化测试，就能做 TDD。

研究怎么说？

很多人把 TDD 当银弹，所以作者认为你应该知道：实践者怎么想、他怎么想，以及研究目前知道什么。

研究发现
Janzen（2005）TDD 实践者写出的算法更简单，测试集覆盖更多正面
Janzen 和 Saiedian（2006）TDD 代码更好地运用了面向对象概念，职责分布更合理；其他团队的代码更「过程式」正面
George 和 Williams（2003）TDD 起初可能降低新手的生产力，但 92% 的开发者认为它提高了代码质量正面
Dogša 和 Batič（2011）类设计有所改善，源于 TDD 为过程带来的简洁性正面
Erdogmus 等（2005）24 名本科生的实验：生产力提高，但代码质量没变混合
Nagappan 等（2008）微软的三个案例研究：采用 TDD 的项目发布前缺陷密度降低 40%–90%正面
Müller 和 Hagner（2002）19 名学生：测试先行没有加快实现，代码也没有更可靠不明确
Siniaalto 和 Abrahamsson（2007）对比 5 个小项目的代码指标，好处不明显不明确
Shull 等（2010）综述 14 篇论文：TDD 对内部代码质量没有一致的影响（这篇易读，推荐）不明确
Fucci 等（2016）重要的是写测试（先写后写都行），以及 TDD 鼓励的细粒度、稳定的小步新视角

作者作为读过这个主题大部分论文的学者认为：这些研究，无论结论正面与否，都不完美 —— 有的用学生（不是软件开发或 TDD 专家），有的用玩具项目（TDD 没有发挥空间），有的用耦合、内聚等只能部分衡量代码质量的指标。 设计实验来衡量一项软件工程实践的收益本身就很难。

更新的研究认为，TDD 的效果可能不是来自「先写测试」，而是来自朝最终目标迈出的小步。Fucci 等人写道：「TDD 所声称的好处也许并非源于其独特的测试先行，而是源于类 TDD 过程所鼓励的细粒度、稳定的步伐，它们改善了专注度和心流。」 Michael Feathers（2008）也说：「这就是魔力所在，也是单元测试之所以有效的原因。当你写单元测试时，无论是 TDD 风格还是开发之后，你都在审视、在思考，常常在遇到测试失败之前就预防了问题。」

🔑 给 TDD 一个机会

看它是否适合你的工作方式和编程风格。你也许会全职采用（像作者的很多同事），也许只在某些情况下用（像作者），也许决定永远不用（也像很多同事）。由你决定。

TDD 的流派

TDD 没规定从哪儿开始、写什么测试，这种灵活性催生了不同流派：

经典派（Detroit 派、由内而外）
从组成功能的各个单元开始，通常先写承载主要业务规则的实体，再慢慢向外，连接控制器、UI、Web 服务。尽量避免 Mock：一条业务规则涉及两三个类时，把它们放在一起测。理由正是第 6 章讲的：Mock 降低测试的有效性，让测试更脆弱。
伦敦派（London 派、由外而内、Mock 派）
从外部（UI 或处理 Web 服务的控制器）开始，再慢慢走向处理功能的单元。关注不同对象如何协作，用 Mock 探索这种协作，偏爱测试隔离的单元。

两派都用测试代码来了解正在开发的代码的设计。Test Double（2018）总结得好：「在 Detroit 派看来，一个对象难测，就说明它难用；在 London 派看来，一个依赖难 Mock，就说明使用它的对象用起来难。」 作者的风格是两者的混合：从内部开始写实体和业务规则，再慢慢向外，让外层调用这些实体；但他尽量做单元测试，不喜欢单元 A 的测试因为单元 B 的 Bug 而失败，所以会用 Mock，并遵循第 6 章的所有实践。推荐 Mancuso 2018 年的演讲。

TDD 与真正的测试

有研究表明 TDD 实践者写的测试更多。但作者不认为 TDD 产生的测试集能和前几章系统化设计出的强大测试集相比 —— 理由很简单：做 TDD 时，我们关注的不是测试。 TDD 结束、代码看起来不错之后，就该开始有效而系统的测试了：把焦点转到测试上，应用规格测试、结构化测试和属性测试。TDD 时写的测试当然可以复用，这很自然。 两者都要及时：你不会想 TDD 完一个功能，一周后才正经测它。掌握所有技术之后，你会开始自如地组合它们 —— 本书的实践不是线性的流程，而是随时可用的工具。

本章小结

  • 写一个失败的测试、让它通过、然后重构 —— 这就是测试驱动开发。
  • 红—绿—重构循环为编码过程带来了好处，比如对开发节奏的更多掌控，以及快速反馈。
  • 各个 TDD 流派都有道理，应视情况使用。
  • 实证研究没有发现 TDD 的明确收益。目前的共识是：小步推进一个功能、稳定地前进，能让开发者更高效。所以 TDD 是品味问题，但短的实现循环加测试是正确的方向。
  • 是否 100% 使用 TDD 也是个人选择，你应该找出 TDD 让你更高效的场景。
  • 小步是 TDD 的关键。拿不准下一步时，别怕走慢；有信心时，也别怕走快！

8.4　用 TDD 实现保龄球计分（点开看一个参考的 TDD 过程和实现）

规则：一局 10 格，每格最多两投、共 10 个瓶。全中（strike）：一投全倒，本格得 10 分 + 接下来两投的分数；补中（spare）：两投全倒，本格得 10 分 + 接下来一投的分数。第 10 格打出全中或补中时，可以追加 1 或 2 投，但这一格总共不超过 3 投。

没有标准答案，下面是一种经典的 TDD 路线（Robert Martin 的「保龄球套路」）：先测「全部落空」得 0 分 → 「每投 1 瓶」得 20 分 → 一个补中 → 一个全中 → 完美比赛 300 分。每一步只写刚好够的代码，然后重构。

class BowlingGameTest {
  private final BowlingGame game = new BowlingGame();

  private void rollMany(int n, int pins) {
    for (int i = 0; i < n; i++) game.roll(pins);
  }

  @Test void allOnes()      { rollMany(20, 1); assertThat(game.score()).isEqualTo(20); }
  @Test void oneSpare()     { game.roll(4); game.roll(6); game.roll(3); rollMany(17, 0);
                              assertThat(game.score()).isEqualTo(16); }     // (10+3) + 3
  @Test void oneStrike()    { game.roll(10); game.roll(1); game.roll(2); rollMany(16, 0);
                              assertThat(game.score()).isEqualTo(16); }     // (10+1+2) + 3
  @Test void perfectGame()  { rollMany(12, 10); assertThat(game.score()).isEqualTo(300); }
}

class BowlingGame {
  private final List<Integer> rolls = new ArrayList<>();

  public void roll(int pins) { rolls.add(pins); }

  public int score() {
    int score = 0, i = 0;
    for (int frame = 0; frame < 10; frame++) {
      if (rolls.get(i) == 10) {                                   // 全中
        score += 10 + rolls.get(i + 1) + rolls.get(i + 2);
        i += 1;
      } else if (rolls.get(i) + rolls.get(i + 1) == 10) {         // 补中
        score += 10 + rolls.get(i + 2);
        i += 2;
      } else {
        score += rolls.get(i) + rolls.get(i + 1);
        i += 2;
      }
    }
    return score;
  }
}
