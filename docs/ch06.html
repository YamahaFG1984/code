第 6 章

测试替身与 Mock

真实的类很少孤零零地工作：它会调用数据库、Web 服务、别的类。测试它时把这些依赖全带上，往往又慢、又难、又麻烦。 测试替身就像电影里的替身演员：「看起来像 B，但它不是 B」，而且在测试里完全听你指挥。 这一章讲五种替身的区别，用 Mockito / unittest.mock / Vitest 把它们用起来，更重要的是讨论：什么该 Mock，什么不该。

本章目标

  • 分清 Dummy、Fake、Stub、Spy、Mock
  • 学会桩返回值、验证交互、捕获参数、模拟异常
  • 理解为了能注入替身，生产代码要怎么改（依赖注入）
  • 知道 Mock 的代价，掌握「该不该 Mock」的判断标准
  • 学会对付「Mock 不了」的东西：日期时间、不属于你的类型

为什么需要替身

一个开票系统里，IssuedInvoices 负责访问数据库，里面全是 SQL。别的类（比如生成新发票的 InvoiceGenerationService）依赖它来保存发票。 于是每次测试 InvoiceGenerationService，都会间接连到数据库 —— 要准备数据库、保证里面的数据正确…… 可我们测 InvoiceGenerationService 时，并不想测 SQL 对不对，那是 IssuedInvoices 自己的测试（第 9 章的集成测试）该管的事。

🎮

更可控

想让依赖抛异常？告诉替身抛就行。想让真实类抛异常或返回一个假日期，可能非常难。

⚡

更快

真实依赖要访问数据库或 Web 服务，可能要几秒；替身直接返回配置好的值，几乎不耗时。

🧠

帮助设计

作为设计技术，Mock 促使你思考类之间该如何交互、契约是什么、边界在哪。推荐 Freeman 和 Pryce 的《测试驱动的面向对象软件开发》（2009）。本书主要从测试角度讲 Mock。

ⓘ 替身也要守契约

我们把 Mock 放在单元测试这一侧，因为目标是专注于一个单元。但我们依然关心依赖的契约：替身必须和它模拟的类做同样的事、遵守同样的承诺。

💡 日常用语里的「Mock」

Mockito 的 mock()、Python 的 Mock()、Vitest 的 vi.fn() 创建的对象，既能当 Stub（配置返回值）也能当 Mock（验证调用）。 所以日常大家说「Mock 一下」往往泛指所有替身。但弄清楚你在用它的哪种能力很重要：是为了给被测代码喂数据（Stub），还是为了检查被测代码对外做了什么（Mock）。

桩：替依赖返回数据

📋 需求

返回所有金额小于 100 的已开发票。发票存在数据库里，IssuedInvoices 类已经有一个取出所有发票的方法。

先看两个基础类：Invoice 是简单的实体；IssuedInvoices 负责和数据库打交道（仓库里是一个用 HSQLDB 的朴素实现）。

public class Invoice {
  private final String customer;
  private final int value;
  // 构造函数、getter、equals/hashCode、toString……
}

public class IssuedInvoices {
  private DatabaseConnection connection;

  public IssuedInvoices(DatabaseConnection connection) {
    this.connection = connection;
  }

  public List<Invoice> all() {            // select * from invoice
    return connection.withSql(() -> {
      try (var ps = connection.getConnection().prepareStatement("select * from invoice")) {
        final var rs = ps.executeQuery();
        List<Invoice> allInvoices = new ArrayList<>();
        while (rs.next()) {
          allInvoices.add(new Invoice(rs.getString("name"), rs.getInt("value")));
        }
        return allInvoices;
      }
    });
  }

  public void save(Invoice inv) { /* insert into invoice (name, value) values (?,?) */ }
}

import sqlite3
from dataclasses import dataclass

@dataclass(frozen=True, order=True)      # frozen：可比较、可哈希；order：可排序
class Invoice:
    customer: str
    value: int

class IssuedInvoices:
    def __init__(self, connection: sqlite3.Connection):
        self._conn = connection

    def all(self) -> list[Invoice]:
        rows = self._conn.execute("select name, value from invoice").fetchall()
        return [Invoice(name, value) for name, value in rows]

    def save(self, inv: Invoice) -> None:
        self._conn.execute("insert into invoice (name, value) values (?, ?)",
                           (inv.customer, inv.value))
        self._conn.commit()

import { DatabaseSync } from "node:sqlite";   // Node 22.5+ 内置的 SQLite

export interface Invoice {
  customer: string;
  value: number;
}

export interface IssuedInvoices {              // 被测类只依赖这个接口
  all(): Invoice[];
}

export class SqlIssuedInvoices implements IssuedInvoices {
  constructor(private readonly db: DatabaseSync) {}

  all(): Invoice[] {
    return this.db.prepare("select name, value from invoice").all()
      .map((r) => ({ customer: String(r.name), value: Number(r.value) }));
  }

  save(inv: Invoice): void {
    this.db.prepare("insert into invoice (name, value) values (?, ?)").run(inv.customer, inv.value);
  }
}

第一版实现在方法内部自己创建了数据库连接和 IssuedInvoices：

public class InvoiceFilterWithDatabase {

  public List<Invoice> lowValueInvoices() {
    DatabaseConnection connection = new DatabaseConnection();         // 自己 new 依赖
    IssuedInvoices issuedInvoices = new IssuedInvoices(connection);

    try {
      List<Invoice> all = issuedInvoices.all();                        // 从数据库取所有发票
      return all.stream()
          .filter(invoice -> invoice.getValue() < 100)
          .collect(toList());
    } finally {
      connection.close();                                              // 别忘了关连接
    }
  }
}

第一步：让依赖可以被替换

当前实现在方法内部 new 了 IssuedInvoices，测试根本没机会把替身塞进去。所以我们修改生产代码来方便测试（习惯这件事吧）： 让 IssuedInvoices 通过构造函数传进来。注意 DatabaseConnection 不需要注入 —— InvoiceFilter 根本用不到它。测试里要做的越少越好。 

public class InvoiceFilter {

  private final IssuedInvoices issuedInvoices;

  public InvoiceFilter(IssuedInvoices issuedInvoices) {   // 依赖从构造函数传进来
    this.issuedInvoices = issuedInvoices;
  }

  public List<Invoice> lowValueInvoices() {
    List<Invoice> all = issuedInvoices.all();
    return all.stream()
        .filter(invoice -> invoice.getValue() < 100)
        .collect(toList());
  }
}

from invoices import Invoice, IssuedInvoices

class InvoiceFilter:

    def __init__(self, issued_invoices: IssuedInvoices):   # 依赖从构造函数传进来
        self._issued_invoices = issued_invoices

    def low_value_invoices(self) -> list[Invoice]:
        return [inv for inv in self._issued_invoices.all() if inv.value < 100]

import { Invoice, IssuedInvoices } from "./invoices";

export class InvoiceFilter {
  constructor(private readonly issuedInvoices: IssuedInvoices) {}   // 依赖从构造函数传进来

  lowValueInvoices(): Invoice[] {
    return this.issuedInvoices.all().filter((invoice) => invoice.value < 100);
  }
}
ⓘ 依赖注入（Dependency Injection）

类不自己实例化依赖、而是接收依赖，这是一种流行的设计技术。它不仅让我们能注入替身，也让生产代码更灵活。想深入可读 van Deursen 和 Seemann 的《Dependency Injection: Principles, Practices, and Patterns》（2019）。第 7 章会继续讨论。

第二步：用桩代替数据库

public class InvoiceFilterTest {

  @Test
  void filterInvoices() {
    IssuedInvoices issuedInvoices = mock(IssuedInvoices.class);   // 创建一个桩

    Invoice mauricio = new Invoice("Mauricio", 20);
    Invoice steve = new Invoice("Steve", 99);
    Invoice frank = new Invoice("Frank", 100);
    List<Invoice> listOfInvoices = Arrays.asList(mauricio, steve, frank);

    when(issuedInvoices.all()).thenReturn(listOfInvoices);        // all() 被调用时返回这个列表

    InvoiceFilter filter = new InvoiceFilter(issuedInvoices);     // 把桩注入被测类

    assertThat(filter.lowValueInvoices())
        .containsExactlyInAnyOrder(mauricio, steve);
  }
}

from invoices import Invoice, IssuedInvoices

def test_filter_invoices():

    steve = Invoice("Steve", 99)
    frank = Invoice("Frank", 100)

import { test, expect, vi } from "vitest";
import { IssuedInvoices } from "./invoices";
import { InvoiceFilter } from "./invoiceFilter";

test("filter invoices", () => {
  const mauricio = { customer: "Mauricio", value: 20 };
  const steve = { customer: "Steve", value: 99 };
  const frank = { customer: "Frank", value: 100 };

  // 在 TS 里，桩就是一个满足接口的普通对象；vi.fn() 让它还能记录调用
  const issuedInvoices: IssuedInvoices = {

});

被测方法调用 issuedInvoices.all() 时，拿到的是桩返回的三张发票，过滤后剩两张，断言通过。

桩不仅让测试更好写，还让测试更内聚：旧版测试失败，可能是 InvoiceFilter 有 Bug，也可能是 IssuedInvoices 的 SQL 有 Bug；新版只可能因为 InvoiceFilter 失败。调试时省心多了。IssuedInvoices 当然也该测，但那是另一个地方的集成测试（第 9 章）。

⚠ 用了 Mock 也要系统地测

这一章不聚焦系统化测试，但你应该照做。这里只有一个用例（顺便测了 100 的边界），你还应该测空列表、单元素列表，以及规格测试和结构化测试中冒出来的其他用例。前几章的所有技术依然适用。

🔎 现实中这条规则应该放进 SQL

真实系统里，「金额 < 100」这种过滤最好在数据库里做，一条 SQL 性能好得多。请从这个简单例子中抽象出要点：凡是测试时使用起来很贵的依赖，桩都能派上用场。

Mock：验证交互

📋 新需求

所有低金额发票都要发送给 SAP 系统（一种企业管理软件）。SAP 提供了一个接收发票的 sendInvoice Web 服务。

public interface SAP {           // 封装与 SAP 的通信，具体怎么实现无所谓
  void send(Invoice invoice);
}

public class SAPInvoiceSender {
  private final InvoiceFilter filter;
  private final SAP sap;

  public SAPInvoiceSender(InvoiceFilter filter, SAP sap) {   // 两个依赖都从构造函数注入
    this.filter = filter;
    this.sap = sap;
  }

  public void sendLowValuedInvoices() {
    List<Invoice> lowValuedInvoices = filter.lowValueInvoices();
    for (Invoice invoice : lowValuedInvoices) {
      sap.send(invoice);
    }
  }
}

from typing import Protocol
from invoices import Invoice
from invoice_filter import InvoiceFilter

class SAP(Protocol):             # 封装与 SAP 的通信，具体怎么实现无所谓
    def send(self, invoice: Invoice) -> None: ...

class SAPInvoiceSender:
    def __init__(self, invoice_filter: InvoiceFilter, sap: SAP):   # 两个依赖都注入
        self._filter = invoice_filter
        self._sap = sap

    def send_low_valued_invoices(self) -> None:
        for invoice in self._filter.low_value_invoices():
            self._sap.send(invoice)

import { Invoice } from "./invoices";
import { InvoiceFilter } from "./invoiceFilter";

export interface SAP {           // 封装与 SAP 的通信，具体怎么实现无所谓
  send(invoice: Invoice): void;
}

export class SAPInvoiceSender {
  constructor(
    // 只依赖我们用到的那部分「形状」，测试时传一个普通对象就行
    private readonly filter: Pick<InvoiceFilter, "lowValueInvoices">,
    private readonly sap: SAP,
  ) {}

  sendLowValuedInvoices(): void {
    for (const invoice of this.filter.lowValueInvoices()) {
      this.sap.send(invoice);
    }
  }
}

测试时，InvoiceFilter 是一个返回发票列表的东西，用桩。但这个测试的主要目的是确认每张低金额发票都发给了 SAP —— 没有真的 SAP，怎么断言？答案：确认 send() 被调用了。Mock 框架在背后记录了与 Mock 的所有交互，测试最后问它一句就行： 

public class SAPInvoiceSenderTest {
  // 作为字段：JUnit 每个测试方法都会新建一个测试类实例，所以每个测试都是新的 Mock
  private InvoiceFilter filter = mock(InvoiceFilter.class);
  private SAP sap = mock(SAP.class);
  private SAPInvoiceSender sender = new SAPInvoiceSender(filter, sap);

  @Test
  void sendToSap() {
    Invoice mauricio = new Invoice("Mauricio", 20);
    Invoice frank = new Invoice("Frank", 99);
    List<Invoice> invoices = Arrays.asList(mauricio, frank);

    when(filter.lowValueInvoices()).thenReturn(invoices);    // filter 是桩

    sender.sendLowValuedInvoices();

    verify(sap).send(mauricio);                              // sap 是 Mock：验证交互
    verify(sap).send(frank);
  }

  @Test
  void noLowValueInvoices() {
    List<Invoice> invoices = emptyList();
    when(filter.lowValueInvoices()).thenReturn(invoices);

    sender.sendLowValuedInvoices();

    verify(sap, never()).send(any(Invoice.class));           // 一次都不应该调用
  }
}

想看它失败？把 sap.send() 那一行注释掉。Mockito 会说：

Wanted but not invoked:
sap.send(
    Invoice{customer='Mauricio', value=20}
);
Actually, there were zero interactions with this mock.

它期望 send 以 Mauricio 的发票被调用，但没有；还贴心地补充说「这个 Mock 上一次交互都没有」，帮你调试。

Stub 和 Mock 的主要区别：Stub 是给方法调用返回写死的值；Mock 不仅定义方法做什么，还显式定义与它的交互应该是什么样的。还可以写更严格的期望：

verify(sap, times(2)).send(any(Invoice.class));   // send 恰好被调用 2 次（任意发票）
verify(sap, times(1)).send(mauricio);             // 以 mauricio 调用恰好 1 次
verify(sap, times(1)).send(frank);                // 以 frank 调用恰好 1 次

from unittest.mock import call

assert sap.send.call_count == 2                                  # 恰好 2 次
sap.send.assert_has_calls([call(mauricio), call(frank)],         # 以这两张发票各调一次
                          any_order=True)

expect(sap.send).toHaveBeenCalledTimes(2);          // 恰好 2 次
expect(sap.send).toHaveBeenNthCalledWith(1, mauricio);
expect(sap.send).toHaveBeenNthCalledWith(2, frank);

命令查询分离：什么时候 Stub，什么时候 Mock

为什么不把「发给 SAP」直接放进 InvoiceFilter？那样 lowValueInvoices 就同时是命令和查询了，会让调用它的人困惑。 把两者分开（Command-Query Separation，CQS）的一个好处是：从 Mock 的角度，你立刻知道该怎么做。

查询（Query）→ Stub 它
返回值，不改变对象状态。例如 lowValueInvoices()。你关心的是它返回什么，所以给它配置返回值。
命令（Command）→ Mock 它
改变外部世界，通常没有有意义的返回值。例如 sap.send()。你关心的是它有没有被正确调用，所以验证交互。

越写测试越会发现：代码越好，越容易测。第 7 章会讨论如何在生产代码中做出方便测试的决定。关于 Mock 和 Stub 的区别，推荐 Martin Fowler 的《Mocks Aren't Stubs》（2007）。

模拟异常

📋 需求

SAP 的 send 可能抛出 SAPException。系统应返回发送失败的发票列表。一次失败不应让程序停止，而要继续尝试发送所有发票。

public List<Invoice> sendLowValuedInvoices() {
  List<Invoice> failedInvoices = new ArrayList<>();

  List<Invoice> lowValuedInvoices = filter.lowValueInvoices();
  for (Invoice invoice : lowValuedInvoices) {

让 Mock 抛异常，能让我们测试系统在意外情况下的行为。这对与外部系统交互的软件太重要了：一个 Web 服务宕机一秒钟，你的应用还能正确工作吗？ 不用 Mock，你要怎么让真实的 Web 服务 API 抛异常？那比告诉 Mock「抛」难多了。

💡 测试代码也是代码

每次都要取当前日期、格式化成 MMddyyyy、再拼上名字前两个字母 —— 创建 SapInvoice 越来越痛苦。把这些逻辑抽成辅助方法或辅助类吧。测试代码和生产代码一样重要，写生产代码时遵循的最佳实践，写测试代码时也要遵循（第 10 章）。

Mock 的代价

有人是 Mock 的铁粉，有人坚决反对。事实是：Mock 让测试变得不那么真实。两个主要缺点：

1. 你可能在测 Mock，而不是代码

要让 Mock 在大规模下工作良好，开发者必须设计谨慎且（希望是）稳定的契约。契约设计良好且稳定，你就不必害怕 Mock。 况且，不管有没有 Mock，找到契约变化的所有依赖方、检查新契约是否被覆盖，本来就是开发者的工作。

2. 测试和实现耦合更紧

不用 Mock 的测试调用方法、断言输出，对方法的内部实现一无所知。用了 Mock 的测试则知道不少：SAPInvoiceSender 的测试知道它用了 InvoiceFilter 的 lowValueInvoices，知道每张发票都要调 SAP 的 send。 如果开发者改变了 SAPInvoiceSender 的实现方式（比如不再用 InvoiceFilter），测试可能也得跟着改。作者和同事的实证研究（Spadini 等，2019）也观察到了这一点。

能避免吗？不太能，但至少你意识到了。有趣的是，作者反而欣赏这种耦合：当他改变一个类与其他类的交互方式时，测试会坏掉，这逼他反思自己的改动。当然，不是每个小改动都会让测试坏掉，他也不是处处都用 Mock。用得恰当，这种耦合就不是大问题。

🔎 把 Mock 当作设计技术时

上面说的「耦合」是从测试角度：「代码已经写好了，来测它吧」。如果你像 Freeman 和 Pryce 那样把 Mock 当作设计代码的方式，就要换个角度看：你希望 Mock 和被测代码耦合，因为你关心的正是代码如何完成工作。代码变了，你就希望 Mock 也跟着变。

该 Mock 什么，不该 Mock 什么

用真实依赖的测试比用替身的更真实，也更可能发现真实的 Bug。所以不要 Mock 不该 Mock 的东西。作者的经验（和他后来的实证研究结论惊人地一致）：

✔ 通常 Mock / Stub

太慢的依赖：访问数据库、Web 服务的类。（这些类本身仍然要用集成测试。）

与外部基础设施通信的依赖：搭环境太慢太复杂。

难以模拟的情况：比如让依赖抛异常。

✘ 通常不 Mock

实体：Invoice、ShoppingCart 这类代表业务概念的类，直接 new 更简单。（例外：依赖十几个其他实体的「重型」实体，Mock 它可能更省事。）

语言自带的库和工具方法：为什么要 Mock ArrayList 或 String.format？

足够简单的东西：如果你觉得一个类简单到不值得 Mock，那它多半就是。

例子：书店

📋 需求

给定一组书及其数量，返回购物车总价。如果书店没有足够的库存，就把现有的全部放进购物车，并告诉用户缺了哪些。

class BookStore {
  private BookRepository bookRepository;     // 已知要 Mock，所以注入
  private BuyBookProcess process;

  public BookStore(BookRepository bookRepository, BuyBookProcess process) {
    this.bookRepository = bookRepository;
    this.process = process;
  }

  private void retrieveBook(String ISBN, int amount, Overview overview) {
    Book book = bookRepository.findByISBN(ISBN);
    if (book.getAmount() < amount) {                       // 库存不够：记下缺了多少
      overview.addUnavailable(book, amount - book.getAmount());
      amount = book.getAmount();
    }
    overview.addToTotalPrice(amount * book.getPrice());    // 能买的都算进总价
    process.buyBook(book, amount);                         // 通知购买流程
  }

  public Overview getPriceForCart(Map<String, Integer> order) {
    if (order == null)
      return null;

    Overview overview = new Overview();
    for (String ISBN : order.keySet())
      retrieveBook(ISBN, order.get(ISBN), overview);
    return overview;
  }
}

from typing import Protocol

    price: int
    amount: int

    def find_by_isbn(self, isbn: str) -> Book: ...

class BuyBookProcess(Protocol):

class BookStore:

        self._repo = book_repository             # 已知要 Mock，所以注入
        self._process = process

    def _retrieve_book(self, isbn: str, amount: int, overview: Overview) -> None:
        book = self._repo.find_by_isbn(isbn)
        if book.amount < amount:                     # 库存不够：记下缺了多少

            amount = book.amount

        self._process.buy_book(book, amount)         # 通知购买流程

        overview = Overview()
        for isbn, amount in order.items():

        return overview

不要 Mock 不属于你的类型

Mock 框架强大到可以 Mock 任何库里的任何类。问题是：你想这么做吗？最佳实践是避免 Mock 不属于你的类型。假设你用了一个很贵的库，所以测试里 100% 都 Mock 它，长期下来：

  • 库升级后行为变了，你不会有任何测试失败 —— 它的全部行为都被 Mock 掉了，只能在生产环境发现。
  • Mock 外部库本身可能很难。想想 Hibernate 这类数据库访问库，Mock 它的所有 API 调用太复杂，测试很快变得难以维护。

解决办法：在它上面建一层你自己的抽象，封装与该库的全部交互。前面的 Clock 就是一例 —— 我们不拥有时间 API，所以包了一层。

假设你把某个 XML 解析库的全部行为封装在 XmlWriter 中，只对外提供 write(Invoice)。所有依赖 XmlWriter 的类在单元测试里都 Mock 它； 而 XmlWriter 自己的测试不 Mock 库，而是真的调用它，确认 XML 按预期写出。库一变，这一个测试就会坏，由开发者决定如何应对新行为。 这会增加系统的复杂度，需要多维护一层抽象 —— 但测试上获得的便利通常足以抵消这个成本。（「只 Mock 你拥有的类型」最早由 Freeman 等人在提出 Mock 对象概念的 2004 年论文中提出，Mockito 也这样建议。）

别人怎么说：Google 的观点

《Software Engineering at Google》（2020）用一整章讨论测试替身。作者的解读和他自己的看法：

Google 的观点作者的看法
使用替身要求系统为可测试性而设计同意：用 Mock，就得保证被测类能接收 Mock。
构建忠实于真实实现的替身很难同意：Mock 与生产类契约不一致时，测试全绿，系统却在生产环境失败。
真实优于隔离：能用真实实现就用完全同意，但务实：用真实依赖太难测时，就 Mock。考虑执行时间和不确定性。
真实实现不可行时，Fake 优于 Mock不完全同意：要么用真的，要么 Mock。Fake 也有和 Mock 同样的问题 —— 你怎么保证它和真实实现行为一致？作者很少用 Fake。
过度 Mock 很危险：测试变得难懂、脆弱、低效同意。如果被测类逼你 Mock 太多，可能说明生产类设计得不好。
优先做状态测试，而非交互测试大体同意，但写得好的交互测试也有用。经验法则：类的重点在交互，就测交互；重点在处理结果，就测状态。
避免过度指定的交互测试好建议：只 Mock 该 Mock 的，只验证对这个测试有意义的交互，不要验证每一个。
好的交互测试需要严格的设计准则即使是资深开发者也很难用好 Mock。重视团队培训。

本章小结

  • 测试替身帮助我们测试那些依赖于缓慢、复杂或难以控制和观察的外部组件的类。
  • 替身有多种：Stub 在方法被调用时返回写死的值；Mock 像 Stub，但还能定义我们期望它如何与其他类交互。
  • Mock 有帮助，也有缺点：Mock 可能与真实实现不一致，导致测试通过而系统失败。
  • 用 Mock 的测试比不用的与生产代码耦合更紧，缺乏规划时这种耦合会成为问题。
  • 生产类应该允许注入 Mock，常见做法是通过构造函数接收所有依赖。
  • 即使决定用 Mock，也不必（也不应该）Mock 一切，只 Mock 必要的。

自测练习

6.1　Mock、Stub、Fake 分别是什么，有什么区别？

Fake 是被模拟类的真实可用实现，只是用简单得多的方式完成同样的任务。Stub 为测试中的调用提供写死的答案，没有可工作的实现。Mock 像 Stub，但还预先知道应该发生哪些交互，可以验证它们。

6.2　InvoiceFilter 通过构造函数接收 IssuedInvoices（访问数据库），filter() 返回金额 < 100 的发票。以下哪项是错误的？（A 只有集成测试才能达到 100% 分支覆盖　B 它的实现允许依赖注入，因而可以 Mock　C 可以用 Mock 写出完全隔离的单元测试　D IssuedInvoices 应该用集成测试来测）

A。用 Stub 替换 IssuedInvoices，单元测试就能覆盖所有分支。

6.3　一个系统根据天气相关的复杂布尔条件组合（气温、降雨量、风……）触发事件，设计良好、各类职责单一。你用规格测试并借助 Mock 来测。哪种策略有效？

用 Mock 控制外部条件，并观察被触发的事件。也就是说：天气数据的来源用 Stub 喂数据，事件的触发者用 Mock 验证交互。

6.4　类 A 依赖类 B 的一个静态方法。要正确地测 A，应该：方法 1 Mock B 以控制其方法行为；方法 2 重构 A，让 B 方法的结果作为参数传入。（只用方法 1 / 都不用 / 只用方法 2 / 都用）

只用方法 2。把静态调用的结果变成参数（或注入的依赖），A 就能直接用普通单元测试控制输入，不必依赖 Mock 静态方法这种「黑魔法」。

6.5　按本书的指导，什么类型的类该 Mock，什么不该？

与基础设施相关的、太复杂的、太慢的，适合用 Mock 替换。实体类、简单的工具函数和数据容器通常不 Mock。

6.6　了解了替身的利弊之后，你怎么看？打算用 Mock 和 Stub，还是更专注于集成测试？

没有标准答案。试着结合你的项目回答：哪些依赖慢、不确定、难控制？哪些依赖的契约稳定？团队是否有能力维护好 Mock？
