第 9 章

编写更大的测试

前面几章的代码几乎都能用单元测试搞定，碰到依赖就用 Stub 和 Mock 替掉。但不是所有东西都能（或应该）用单元测试： 硬要写，得到的测试集要么太弱找不到 Bug，要么难写，要么一改代码就碎。这一章讲三种常见的「大测试」： 一起运行多个类的组件测试、与数据库打交道的 SQL 集成测试，以及端到端的系统测试（Web 测试）。

本章目标

  • 判断什么时候该写更大的测试
  • 为多个类组成的组件写测试，并把规格测试用在更粗的粒度上
  • 为 SQL 查询设计测试用例，搭建可靠的数据库测试基础设施
  • 用 Selenium / Playwright 和页面对象模式写可维护的 Web 系统测试
  • 掌握让大测试稳定、便宜的一系列最佳实践

什么时候用更大的测试

作者认为两种情况应该用更大的测试：

🧩

整体行为由多个类组成

每个类都单独测过了，但你想看它们一起工作。比如购物车总价：规则 1 的类、规则 2 的类都测过了，你仍想看所有规则作用后的最终价格。

🔌

被测类是更大框架里的插件

面向对象让我们封装重复的复杂性，用户只需实现关键部分。比如 IDE 插件：逻辑是你写的，但很多动作只有 IntelliJ 调用插件并传参时才发生。

组件测试：多个类一起跑

📋 需求：购物车最终价格
  • 每件商品的价格 = 单价 × 数量。
  • 运费：1–3 件（含）加收 5 美元；4–10 件（含）加收 12.5 美元；超过 10 件加收 20 美元。
  • 购物车里有电子产品，额外加收 7.5 美元。

（运费规则不太现实。实际工作中发现这种不一致时，应该和需求方沟通。这里为了例子保持简单。）

动手前先想想怎么拆：最终价格是把一系列规则应用到购物车上。按照为可测试性设计的经验，每条规则一个类 —— 全塞进一个类会变得很大、需要大量测试；我们更喜欢只需少量测试的小类。

先把每条规则单元测试好

运费只和商品件数有关。这个类又小又局部，用单元测试正合适。需求的边界清晰且连续（1–3、4–10、>10），所以测每个区间的 on 点和 off 点：

public class DeliveryPrice implements PriceRule {
  @Override
  public double priceToAggregate(ShoppingCart cart) {
    int totalItems = cart.numberOfItems();
    if (totalItems == 0)
      return 0;
    if (totalItems >= 1 && totalItems <= 3)
      return 5;
    if (totalItems >= 4 && totalItems <= 10)
      return 12.5;
    return 20.0;
  }
}

🔎 为了 100% 覆盖率而重构？

这又是一个不能盲目看覆盖率的例子：生成报告，你会发现分支覆盖不到 100%！totalItems >= 1 和 totalItems >= 4 的「假」分支从未走过。 要让 totalItems >= 1 为假，需要件数小于 1 —— 我们有 0 件的测试，但它在 totalItems == 0 那里就提前返回了，根本走不到这个条件。 务实地说，所有分支都覆盖了，只是工具看不出来。可以把代码改写成等价的、让工具满意的形式： 

public double priceToAggregate(ShoppingCart cart) {
  int totalItems = cart.numberOfItems();
  if (totalItems == 0)
    return 0;
  if (totalItems <= 3)       // 走到这里一定 >= 1，不必再判断
    return 5;
  if (totalItems <= 10)      // 走到这里一定 >= 4
    return 12.5;
  return 20.0;
}

ⓘ 这里要用属性测试吗？

实现很直接，电子产品的件数对算法影响不大，作者觉得例子测试就够了。（思考：在「一件和两件电子产品」的测试里再加一件非电子商品，测试会更强吗？）

第三条规则 PriceOfItems 遍历商品，累加「单价 × 数量」，代码和测试见仓库。最后是聚合所有规则的计算器 —— 用桩替掉规则，它很容易单元测试：

public class FinalPriceCalculator {
  private final List<PriceRule> rules;

  public FinalPriceCalculator(List<PriceRule> rules) {   // 可以接收任意组合的规则
    this.rules = rules;
  }

  public double calculate(ShoppingCart cart) {
    double finalPrice = 0;
    for (PriceRule rule : rules) {
      finalPrice += rule.priceToAggregate(cart);
    }
    return finalPrice;
  }
}

public class FinalPriceCalculatorTest {
  @Test
  void callAllPriceRules() {
    PriceRule rule1 = mock(PriceRule.class);
    PriceRule rule2 = mock(PriceRule.class);
    PriceRule rule3 = mock(PriceRule.class);

    ShoppingCart cart = new ShoppingCart();              // 商品是什么无所谓，规则都是桩
    cart.add(new Item(ItemType.OTHER, "ITEM", 1, 1));

    when(rule1.priceToAggregate(cart)).thenReturn(1.0);
    when(rule2.priceToAggregate(cart)).thenReturn(0.0);  // 0 也可能出现
    when(rule3.priceToAggregate(cart)).thenReturn(2.0);

    FinalPriceCalculator calculator = new FinalPriceCalculator(Arrays.asList(rule1, rule2, rule3));
    double price = calculator.calculate(cart);

    assertThat(price).isEqualTo(3);
  }
}

class FinalPriceCalculator:
    def __init__(self, rules: list[PriceRule]):     # 可以接收任意组合的规则
        self._rules = rules

    def calculate(self, cart: ShoppingCart) -> float:
        return sum(rule.price_to_aggregate(cart) for rule in self._rules)

export class FinalPriceCalculator {
  constructor(private readonly rules: PriceRule[]) {}   // 可以接收任意组合的规则

  calculate(cart: ShoppingCart): number {
    return this.rules.reduce((total, rule) => total + rule.priceToAggregate(cart), 0);
  }
}

再把它们拼起来测一次

每条规则都单独测过，计算器也用桩测过了。怀疑的声音：「可我们还是不知道把它们插在一起能不能工作。」这是合理的怀疑。 我们的测试已经在结构上覆盖了所有需求，所以这时适合写一个更大的测试，把计算器和所有真实规则一起跑。先在生产代码里建一个工厂：

越过代码库边界的组件

上面的例子里，每个单元仍可以单独测。但有时单独测一个单元根本没有意义。作者举了两个自己写的开源项目：

CK：Java 代码度量工具

CK 依赖 Eclipse JDT 把 Java 代码解析成抽象语法树（AST），再用一个个 Visitor 访问语法树、计算度量。比如 CBO（对象间耦合度）统计一个类依赖了多少个其他类。

CBO 类的 visit(MethodInvocation)、visit(FieldDeclaration) 由 JDT 调用。Mock 掉所有 AST 节点再手动调用？离真实运行太远了。作者的做法：准备一些专门用于测试的小而真实的 Java 文件，真的启动 JDT 解析，再断言度量结果。

Andy：给学生测试打分的工具

Andy 编译学生提交的测试代码 → 运行 JUnit → 计算覆盖率 → 静态分析 → 用预先设计的变异体（元测试）检验测试集是否够强 → 给出分数。每一步一个类。

可是不先编译，怎么运行「跑 JUnit」这一步？不可能。所以测试直接运行整个 Andy 引擎，喂给它真实的 Java 文件，只针对关心的那一步做断言。

数据库与 SQL 测试

本书很多例子里都有一个 DAO 负责读写数据库，我们总是飞快地把它 Mock 掉。但总得有人测这些类：DAO 常常执行复杂的 SQL，封装了大量业务知识。

SQL 查询该测什么

把查询看成谓词的组合：

SELECT * FROM INVOICE WHERE VALUE < 50
SELECT * FROM INVOICE I JOIN CUSTOMER C ON I.CUSTOMER_ID = C.ID WHERE C.COUNTRY = 'NL'
SELECT * FROM INVOICE WHERE VALUE > 50 AND VALUE < 200

value < 50、i.customer_id = c.id、c.country = 'NL'、value > 50 AND value < 200 都是谓词。一个测试准则是：让各个谓词取不同的值，检查查询返回的结果是否符合预期。 本书的几乎所有技术都能用上：规格测试（SQL 源自需求，可以划分等价类）、边界分析（SQL 也有边界）、结构化测试（SQL 有谓词，可以从结构推导用例）。

Tuya、Suárez-Cabal 和 De La Riva 在《A practical guide to SQL white-box testing》（2006）中给出了五条设计 SQL 测试的指导：

指导含义
对 SQL 条件使用 MC/DC判断出现在三个地方：JOIN、WHERE、HAVING。可以用 MC/DC 彻底检验查询的谓词（忘了 MC/DC？回看第 3 章）。
让 MC/DC 适应 NULL数据库对 NULL 有特殊处理，覆盖准则要适应三值逻辑（真、假、NULL）：考虑值为 NULL 的可能。
对被选中的数据做类别划分 检索的行：设计一个让查询一行都选不中的状态； 合并的行：输出中出现不想要的重复行是常见故障，设计一个会选中相同行的状态； 分组的行：对每个 GROUP BY 列，至少得到两个不同的分组； 子查询的行：让每个子查询返回零行或多行，至少包含一个 NULL 和两个不同的值； 聚合函数的值：对每个聚合函数（count 除外），至少有一个状态让它算出两个相等的值、一个不同的值； 其他表达式：LIKE、日期、字符串、类型转换等，用类别划分和边界检查。
检查输出不仅检查输入域，也检查输出域：查询可能在某些列返回 NULL 或空值，让程序其余部分崩溃。
检查数据库约束确保数据库真的执行了这些约束。

为 SQL 查询写自动化测试

步骤很简单：① 建立数据库连接；② 让数据库处于正确的初始状态；③ 执行被测查询；④ 检查输出。场景：

  • invoice 表有 name（varchar 100）和 value 两列；
  • InvoiceDao 有三个方法：save() 执行 INSERT INTO invoice (name, value) VALUES (?,?)；all() 执行 SELECT * FROM invoice；allWithAtLeast() 执行 SELECT * FROM invoice WHERE value >= ?。
public class InvoiceDao {
  private final Connection connection;          // DAO 持有一个数据库连接

  public InvoiceDao(Connection connection) {
    this.connection = connection;
  }

  public List<Invoice> all() {
    try {
      PreparedStatement ps = connection.prepareStatement("select * from invoice");
      ResultSet rs = ps.executeQuery();
      List<Invoice> allInvoices = new ArrayList<>();
      while (rs.next()) {                       // 每一行变成一个 Invoice 实体
        allInvoices.add(new Invoice(rs.getString("name"), rs.getInt("value")));
      }
      return allInvoices;
    } catch (Exception e) {
      throw new RuntimeException(e);            // 把受检异常转成非受检异常
    }
  }

  public List<Invoice> allWithAtLeast(int value) {
    try {
      PreparedStatement ps = connection.prepareStatement("select * from invoice where value >= ?");
      ps.setInt(1, value);
      ResultSet rs = ps.executeQuery();
      List<Invoice> allInvoices = new ArrayList<>();
      while (rs.next()) {
        allInvoices.add(new Invoice(rs.getString("name"), rs.getInt("value")));
      }
      return allInvoices;
    } catch (Exception e) {
      throw new RuntimeException(e);
    }
  }

  public void save(Invoice inv) {
    try {
      PreparedStatement ps = connection.prepareStatement(
          "insert into invoice (name, value) values (?,?)");
      ps.setString(1, inv.customer);
      ps.setInt(2, inv.value);
      ps.execute();
      connection.commit();
    } catch (Exception e) {
      throw new RuntimeException(e);
    }
  }
}

⚠ 永远只对测试数据库跑测试

测试应该运行在专门为测试准备的数据库上。不用说，你绝不想对生产数据库跑测试。

测试基础设施该做什么

表结构一复杂，打开连接、重置状态就会变得冗长。投资测试基础设施：开发者想写集成测试时，不需要手动建连接或处理事务，这些应该由测试基类（或 fixture）直接提供。数据库逻辑集中在一处，将来改动也只需改一个地方。

打开数据库连接

JDBC、Hibernate 或你用的持久化框架的连接。有时可以整个测试集只开一个连接（@BeforeAll，或 pytest 的 scope="session"）。

开启和提交事务

常见做法是测试开始时开启事务、结束时提交；也有人从不提交，测试结束就回滚。这是集成测试，作者建议每个测试方法提交一次事务。

重置数据库状态

每个测试都从干净的状态开始：正确的表结构，表里没有意外数据。最简单的办法是每个测试开始时 truncate 所有表，手动或借助框架。

减少测试代码量的辅助方法

SQL 集成测试可能很长。能被多个测试复用的代码 —— 对象构建器、常用断言、特定数据库操作 —— 都提取出来放进基类或 fixture。

最佳实践

  • 用测试数据构建器（Test Data Builder）。真实实体远比两个字段的 Invoice 复杂，你不想为了一张发票写 15 行代码、传 20 个参数。第 10 章会讲怎么实现。
  • 用好的、可复用的断言 API。很多查询返回对象列表，断言库提供了多种断言方式。某个复杂断言被多个测试需要，就封装成辅助方法。
  • 最小化所需数据。测试只需要两张表，就只往两张表插数据；只需要 10 行，就只插 10 行。
  • 考虑 schema 的演进。真实系统的表结构变化很快，测试集要对此有韧性。如果发现一个测试会被未来的改动破坏，想办法减少需要修改的地方。数据库变了，测试数据库也要同步 —— 迁移框架可以代劳。
  • 用（或不用）内存数据库。和生产同类型的数据库更真实，测试会运行同一个 SQL 引擎；内存数据库则便宜得多。作者写 SQL 集成测试时倾向于用真实数据库。
💡 现代做法：用容器启动真实数据库

Testcontainers（Java、Python、Node 都有）可以在测试里用 Docker 临时启动一个真实的 Postgres/MySQL，测试结束自动销毁。 这样既能用和生产相同的数据库引擎，又不需要手动维护一个共享的测试数据库。CI 上也很好用。

系统测试：测整个 Web 应用

到了某个时候，你的类、业务规则、持久层等被组合成一个 Web 应用。用户访问页面、与元素交互，触发更多请求和响应。 比如宠物诊所：用户打开今天的预约列表，点「新建预约」，填写宠物和主人的名字，选一个空闲时段，回到列表页，看到新增的预约。 如果它是按照前几章的方法开发的，每个单元都已经有了（系统化的）单元测试。这一节讨论：Web 应用里还要测什么、用什么工具自动操作浏览器，以及系统测试的最佳实践。这些思想同样适用于任何类型的软件。

该测什么：用户旅程

按照测试金字塔，Web 应用的各个单元（Owner、Pet 等实体）已经有单元测试，DAO 里的查询也有集成测试了。还剩什么要测？用户旅程（user journey）。 Martin Fowler（2003）的定义：「用户旅程测试是一种面向业务的测试，模拟典型用户在系统中的旅程。它通常覆盖用户为达成某个目标而与系统的完整交互，是用例中的一条路径。」 PetClinic 里的旅程：查找主人、添加新主人、给主人添加宠物、记录宠物就诊……我们来测「查找主人」。

⚠ 再跑一次，它会失败

ⓘ 系统测试贵在前期

为一条旅程写测试，比写单元测试多得多的工作量，系统测试天生更贵。但请注意：一旦有了页面对象这套初始结构，再加新测试就容易多了。高成本发生在现在，搭建基础设施的时候。一个好练习：为应用的其他旅程写测试（这需要更多页面对象！）。

模式与最佳实践

这些模式来自作者多年写这类测试的经验，其中一些他和 Guerra、Gerosa 在 2014 年的 PLoP 会议上提出过。

🔧

提供让系统进入所需状态的方式

测试需要 10 个实体时，按顺序访问 10 个页面太慢太累。可以提供（REST）Web 服务让测试直接造数据；测试这边再写一个类（如 OwnersAPI）封装调用细节。担心安全？这些 API 只在测试环境开放。甚至可以专门为测试设计一个能一次造好复杂数据的服务。

🧹

每个测试都在干净的环境中运行

和 SQL 测试一样，否则测试可能因为 Bug 以外的原因失败。可以用同样的办法：应用提供一个重置的后门（比如清空所有表）。警告：这个后门绝不能部署到生产环境，否则后果不堪设想！

🏷

给 HTML 元素起有意义的名字

UI 变化频繁，所以 Web 测试常常很不稳定。给测试要用的元素加上唯一的 ID 或名字，即使元素本来不需要。ID 不稳定（动态生成）时，用 HTML5 的自定义属性，如 data-selenium="customer-name"。动手前先和前端负责人聊聊。

🚶

只在测这条旅程时才走完每一步

测页面 A 之前必须先经过 B、C、D、E、F？测试会又长又复杂。如果那些步骤不属于被测旅程，就用 Web 服务跳过它们；如果属于，就老老实实走一遍。

🔍

断言使用来自页面对象的数据

测试需要页面信息来断言时，由页面对象提供（如 all()）。测试方法不应自己去定位 HTML 元素，但断言留在测试代码里。

⚙

把重要配置传给测试集

应用地址、用哪个浏览器不应写死：CI 可能在别的端口运行应用，你可能想在 Chrome 上跑。作者的做法：在页面对象基类里提供 baseUrl()、browser() 方法，从配置文件或环境变量读取。

🌐

在多个浏览器上运行

作者不在自己电脑上做（太费时间），而是让 CI 分多个阶段，每次换一个浏览器跑一遍 Web 测试集。配置 CI 太麻烦？可以用 SauceLabs 这类服务。Playwright 的 projects 配置也能一次跑 Chromium、Firefox、WebKit。

关于大测试的最后几点

各种测试技术如何配合？

前几章讲的是如何系统地设计用例，这一章讨论的是一个正交的问题：测试该多大？不论层级如何，设计好的测试用例依然是重点 —— 写大测试时，照样用需求和边界、代码结构、应满足的属性来设计用例。难点在于：整个组件的需求和代码都大得多，要设计的测试也多得多。 作者的经验法则：在单元层面检验一切（在那里你能轻松覆盖整个需求和结构），在大测试里检验最重要的行为（让你更有信心拼在一起也能工作）。可以重读第 1 章的测试金字塔。

做成本收益分析

好测试写起来便宜，却能抓住重要的 Bug。单元测试便宜，不必多想；大测试写、跑、维护都可能不便宜 —— 作者见过要跑好几个小时的集成测试集，也见过开发者花好几个小时写一个集成测试。问问自己：

  • 写这个测试要花多少？跑它要花多少？
  • 它的收益是什么？能抓住什么 Bug？
  • 这个功能已经被单元测试覆盖了吗？如果是，还需要集成测试再覆盖一遍吗？

很多时候答案是「值得写」。成本太高就考虑简化：能 Stub 掉一部分而不损失太多吗？能写一个只检验系统一小部分的、更聚焦的测试吗？没有唯一的答案或金科玉律。

小心「被覆盖但没被测试」的方法

大测试同时运行更多的类和方法，一个方法被覆盖却没被真正测试的可能性也高得多。Vera-Pérez 等人（2019）称之为伪测试方法（pseudo-tested methods）： 把方法的整个实现替换成简单的 return null，测试照样通过。信不信由你，它们在真实世界里存在，甚至出现在重要的开源项目中。这是作者主张单元测试和大测试一起用的又一个理由。

合适的代码基础设施是关键

集成测试和系统测试都需要背后有像样的基础设施，否则要花太多时间搭环境、断言行为。核心建议：投资测试基础设施。它应该帮开发者搭建环境、清理环境、获取复杂数据、断言复杂数据，以及完成写测试所需的其他复杂任务。

给利益相关者用的 DSL 和工具

这一章我们用大量代码亲手写系统测试。在这个层级，更自动化的方式也很常见：Robot Framework、Cucumber 等工具甚至允许用接近自然语言的方式写测试。如果你希望（非技术的）利益相关者也能写测试，它们很有意义。

测试其他类型的系统

测试层级越高，越要考虑应用所在的框架和环境：响应式页面怎么测？Angular、React 应用怎么测？MongoDB 这类非关系数据库怎么测？这些已远超本书范围，建议去相应社区了解最前沿的工具和知识。 书中的用例设计技术，无论技术栈如何都适用。系统测试的思想也适用于任何软件：库或框架的系统测试像客户一样使用整个库；移动应用的系统测试像用户一样使用整个 App。

本章小结

  • 开发者受益于编写更大的测试：从整体测试组件，到与外部系统集成，再到整个系统。
  • 设计大测试比写单元测试更具挑战，因为被测组件可能比单个单元大得多、复杂得多。
  • 我们讨论过的所有用例设计技术 —— 规格测试、边界测试、结构化测试、属性测试 —— 都适用于大测试。
  • 为大测试投资良好的测试基础设施是必需的。没有它，你会在写单个测试用例上花太多时间。
