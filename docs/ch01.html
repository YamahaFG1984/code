第 1 章

高效而系统的软件测试

两个同样优秀的开发者，写了一模一样的代码。一个周五晚上被叫回公司修 Bug，另一个安心过了周末。 区别不在于谁更聪明，而在于谁用了系统化的方法去测试。这一章从这个故事讲起， 然后解释为什么测试天生就难，以及该把力气花在哪一层测试上。

本章目标

  • 通过一个真实感很强的例子，理解「凭感觉测」和「系统地测」的差别
  • 看清一个开发者从拿到需求到放心上线，中间会用到哪些测试技术
  • 记住软件测试的七条原则 —— 它们解释了为什么「没有 Bug 的软件」不存在
  • 分清单元测试、集成测试、系统测试，理解测试金字塔

一个故事：测试的人和不测试的人

先认识一下故事的背景。敏捷团队常用一种叫计划扑克（Planning Poker）的方式来估算工作量： 大家讨论完一个功能后，每个人同时亮出自己的估算点数。点数越大，代表觉得越费劲。 然后估得最低和估得最高的两个人要站出来讲讲理由，大家再讨论、再估，直到意见接近。

John 要实现的核心方法很简单：

方法identifyExtremes
输入一个 Estimate 列表，每个元素包含开发者名字和他的估算值
输出一个字符串列表：估得最低的人的名字 + 估得最高的人的名字

John 的版本：写完、手动点两下、上线

几分钟后，John 写出了下面的代码。逻辑很直接：遍历列表，一边走一边记录「目前见过的最高」和「目前见过的最低」。

public class PlanningPoker {
  public List<String> identifyExtremes(List<Estimate> estimates) {
    Estimate lowestEstimate = null;    // 目前见过的最低估算
    Estimate highestEstimate = null;   // 目前见过的最高估算

    for (Estimate estimate : estimates) {
      if (highestEstimate == null ||
          estimate.getEstimate() > highestEstimate.getEstimate()) {
        highestEstimate = estimate;
      }
      else if (lowestEstimate == null ||      // ← 注意这个 else
          estimate.getEstimate() < lowestEstimate.getEstimate()) {
        lowestEstimate = estimate;
      }
    }

    return Arrays.asList(
        lowestEstimate.getDeveloper(),
        highestEstimate.getDeveloper());
  }
}

@dataclass(frozen=True)
class Estimate:
    developer: str
    estimate: int

def identify_extremes(estimates: list[Estimate]) -> list[str]:

    highest = None   # 目前见过的最高估算

  developer: string;
  estimate: number;
}

export function identifyExtremes(estimates: Estimate[]): string[] {
  let lowest: Estimate | null = null;    // 目前见过的最低估算
  let highest: Estimate | null = null;   // 目前见过的最高估算

  for (const e of estimates) {
    if (highest === null || e.estimate > highest.estimate) {
      highest = e;
    } else if (lowest === null || e.estimate < lowest.estimate) {  // ← 注意这个 else
      lowest = e;
    }
  }

  return [lowest!.developer, highest!.developer];
}

你能在代码里找到问题吗？提示：试试把估算按从小到大的顺序输入。

罪魁祸首就是那个不起眼的 else。「更新最高」和「更新最低」本来是两件独立的事， 用 else 连起来，就变成了「如果更新了最高，就不许更新最低」。修复只需要把 else if 改成 if：

ⓘ 「这么简单的 Bug，我才不会犯」

也许吧。但真实代码比这复杂得多，人很难同时记住所有可能发生的情况。 Bug 出现不是因为我们是差劲的程序员，而是因为我们在写复杂的东西 —— 而计算机比人精确得多。 John 其实是个很好的开发者，他缺的是两样东西：一套系统的方法来推导测试用例（少遗漏情况）， 以及测试自动化（不用每次手动点）。

代码里已经写得很清楚了，为什么还要写测试？因为测试能防止回归： 将来某个同事看不懂这几行校验、顺手删掉时，测试会立刻变红提醒他。

💡 读懂「期待异常」的测试

这类测试是「倒过来」的：抛出了指定异常才算通过，没抛反而失败。 Java 里 () -> … 是一段 lambda（一小段待执行的代码），assertThatThrownBy 执行它并检查异常类型； Python 用 with pytest.raises(...) 包住会出错的代码；Vitest 则是把函数交给 expect(...).toThrow()。 三种写法，同一个意思。

⚠ 五个测试全绿，Bug 还在

注意：此时 Eleanor 有五个通过的测试，但那个 else 的 Bug 依然存在！ 因为她挑的输入恰好不是升序。测试全部通过 ≠ 没有 Bug，这是整本书反复出现的主题。

第三步：顺序。Eleanor 知道，只要输入是列表，元素的顺序就可能影响算法。 她不去手挑「某一种顺序」，而是写了一个基于属性的测试（property-based test）： 让框架随机生成大量列表，塞进一个已知的最低值（1）和最高值（100），打乱顺序，然后断言结果永远是这两个人。

@Property   // jqwik：默认用 100 组随机数据运行这个测试
void estimatesInAnyOrder(@ForAll("estimates") List<Estimate> estimates) {
  estimates.add(new Estimate("MrLowEstimate", 1));
  estimates.add(new Estimate("MsHighEstimate", 100));
  Collections.shuffle(estimates);            // 打乱，让顺序无关紧要

  List<String> dev = new PlanningPoker().identifyExtremes(estimates);

  assertThat(dev).containsExactlyInAnyOrder("MrLowEstimate", "MsHighEstimate");
}

@Provide     // 告诉 jqwik 如何生成随机的估算列表
Arbitrary<List<Estimate>> estimates() {
  Arbitrary<String> names = Arbitraries.strings().withCharRange('a', 'z').ofLength(5);
  Arbitrary<Integer> values = Arbitraries.integers().between(2, 99);

  Arbitrary<Estimate> estimates = Combinators.combine(names, values)
      .as((name, value) -> new Estimate(name, value));

  return estimates.list().ofMinSize(1);
}

🔎 属性测试是怎么「找到」Bug 的？

例子测试（example-based）是你挑一个具体输入；属性测试是你描述一个对所有输入都成立的规律 （这里是「不管顺序如何，最低和最高的人一定被选出」），然后框架去生成成百上千个输入来试图推翻它。 只要随机数据里出现了「升序」这种排列，Bug 就会暴露。第 5 章会专门讲这个技术。

第四步：重复值。列表里还可能有重复元素 —— 几个人给出了同样的估算。 Eleanor 和产品负责人商量后决定：返回先出现的那位。现有实现恰好已经是这样，但她仍然写了一个测试把这个行为「钉住」。

第五步：全部相同。如果每个人估的都一样呢？产品负责人也没想到这种情况，最后决定返回空列表 —— 没有分歧，就没人需要发言。Eleanor 在代码末尾加了一个判断：

public List<String> identifyExtremes(List<Estimate> estimates) {
  if (estimates == null) {
    throw new IllegalArgumentException("Estimates can't be null");
  }
  if (estimates.size() <= 1) {
    throw new IllegalArgumentException("There has to be more than 1 estimate in the list");
  }

  Estimate lowestEstimate = null;
  Estimate highestEstimate = null;

  for (Estimate estimate : estimates) {
    if (highestEstimate == null ||
        estimate.getEstimate() > highestEstimate.getEstimate()) {
      highestEstimate = estimate;
    }
    if (lowestEstimate == null ||
        estimate.getEstimate() < lowestEstimate.getEstimate()) {
      lowestEstimate = estimate;
    }
  }

  // 最低和最高是同一个对象 → 所有人估算相同
  if (lowestEstimate.equals(highestEstimate))
    return Collections.emptyList();

  return Arrays.asList(
      lowestEstimate.getDeveloper(),
      highestEstimate.getDeveloper());
}

def identify_extremes(estimates: list[Estimate]) -> list[str]:
    if estimates is None:
        raise ValueError("estimates can't be None")
    if len(estimates) <= 1:
        raise ValueError("there has to be more than 1 estimate in the list")

    lowest = None
    highest = None
    for e in estimates:
        if highest is None or e.estimate > highest.estimate:
            highest = e
        if lowest is None or e.estimate < lowest.estimate:
            lowest = e

    # 最低和最高是同一个元素 → 所有人估算相同
    if lowest is highest:
        return []

    return [lowest.developer, highest.developer]

export function identifyExtremes(estimates: Estimate[] | null): string[] {
  if (estimates == null) {
    throw new Error("estimates can't be null");
  }
  if (estimates.length <= 1) {
    throw new Error("there has to be more than 1 estimate in the list");
  }

  let lowest: Estimate | null = null;
  let highest: Estimate | null = null;
  for (const e of estimates) {
    if (highest === null || e.estimate > highest.estimate) highest = e;
    if (lowest === null || e.estimate < lowest.estimate) lowest = e;
  }

  // 最低和最高是同一个元素 → 所有人估算相同
  if (lowest === highest) return [];

  return [lowest!.developer, highest!.developer];
}

两个人的差别，一张图看清

开发者的高效测试流程

Eleanor 用到的就是作者所说的「高效而系统的软件测试」。 她先把需求拆成小块来推导测试用例（领域测试）；然后看代码本身，用覆盖率评估测试是否足够（结构化测试）； 大多数用例是挑一个具体数据点（例子测试），某个场景用了属性测试； 整个过程中她还不断思考方法的契约（前置条件、后置条件）。 下面这张图是全书的路线图：

  1. 需求分析。需求通常是自然语言，可能是用例或用户故事。先把它理解清楚，再开始写代码。
  2. 用 TDD 小步前进。用很短的「写测试 → 写代码」循环获得快速反馈，并支撑开发过程中不断发生的重构。
  3. 设计单元与契约。需求很少由一个方法完成，你会写出一组协作的类和方法，每个都有自己的契约。写出容易测试的类不容易，需要有意识地为可测试性设计。
  4. 转入测试模式。觉得功能完成了，就切换身份：对每个单元做领域测试、边界测试和结构化测试。
  5. 必要时写更大的测试。某些部分需要集成测试或系统测试，推导方法还是那三种，只是看的范围更大。
  6. 让工具帮你找人眼看不到的。测试用例生成、变异测试、静态分析……本书讲变异测试。
  7. 放心发布。
🔑 这不是瀑布流程

看起来像一步接一步，实际上是来回迭代的：测着测着发现几小时前的设计不好，回去重构； 写 TDD 时发现需求有歧义，回去问清楚；测试中发现 Bug，修完继续测；甚至功能只写了一半，就觉得先认真测一下更划算。 按你觉得最高效的顺序来。

先专心写，再专心测

作者发现把「开发」和「测试」分开很解放：写功能时不想被各种刁钻的边界情况分心， 想到了就记个笔记，稍后再测。写完之后，再像过检查清单一样逐项应用各种技术 —— 就像 Eleanor 看到列表就条件反射地想到「null、空、一个、多个」。最后才动用创造力和领域知识去补充其他情况。

几个常见误解

🧱

「设计得好就不会有 Bug」

研究确实表明简单、无坏味道的代码缺陷更少。但简单远远不够，设计良好不代表能避免所有 Bug。

💰

「认真测试太贵了」

生产环境 Bug 的代价通常远超预防成本；Bug 多的团队会陷入「写 Bug→被发现→修→又被发现」的死循环；而且熟练后设计用例会快很多。

🤖

「会写 JUnit 就会测试」

测试框架只负责执行用例、出报告。真正的难点是设计出能发现 Bug 的用例 —— 这主要是人的工作，也是本书的重点。

「高效」和「系统」分别指什么

高效（effective）
写对的测试。测试是一场权衡：用最少的力气找到最多的 Bug。 关键是知道测什么。书里每种技术都有明确的起点（测什么）和终点（什么时候停）。
系统（systematic）
对同一段代码，任何开发者都应该推导出相同的测试集。 不再依赖「谁在测、他当时想到了什么」。把能系统化的部分系统化，让人把创造力留给真正需要的地方。

为什么测试这么难：七条原则

一个天真的想法是：「不停加测试，直到够了为止。」可惜没那么简单。下面这些原则（改编自 ISTQB 教材）解释了为什么。

1. 穷举测试是不可能的

既然不可能测遍，就必须挑选要测什么。这正是本书强调「高效」的原因。

2. 知道什么时候该停

测太少，系统漏洞百出；不假思索地一个接一个加，又浪费时间和金钱。本书会介绍各种充分性准则（adequacy criteria），帮你判断什么时候可以停。

3. 多样性很重要（杀虫剂悖论）

没有银弹。只用单元测试的团队，能找到单元层面的所有 Bug，却会错过只在集成时才出现的问题。 「杀虫剂悖论」说的就是：你用来预防或发现 Bug 的每种方法，都会留下一批这种方法对付不了的、更隐蔽的 Bug。

4. Bug 扎堆出现

Bug 并不均匀分布。比如支付模块通常比营销模块需要更严格的测试。 一项对 Eclipse 项目的研究发现：导入了编译器相关包的文件中，71% 后来都需要修 Bug。 除了源代码，历史 Bug 数据等信息也能帮你决定把测试精力放在哪里。

5. 无论怎么测，都永远不够完美

Dijkstra 的名言：「程序测试可以用来证明 Bug 的存在，但永远无法证明 Bug 不存在。」 测试只能保证你测过的那些情况表现正确。所以作者也建议投资监控：Bug 一定会漏到生产环境，你要在它出现的那一刻就知道（有时也叫「在生产环境中测试」）。

6. 具体情况具体分析

给手机 App、Web 应用、火箭软件设计测试用例，方式大不相同。本书的技术尽量与场景无关，但如果你做移动端，读完后最好再读一本专门的书。

7. 验证不等于确认

验证（Verification）
把系统做对（having the system right）
给定需求，系统是否正确实现了它？本书主要讲这个。
确认（Validation）
做对的系统（having the right system）
这个系统是不是用户真正需要的？

一个完美运行却对用户毫无用处的系统，不是好系统 —— 这叫「无错误谬论」（absence-of-errors fallacy）。 正如一位审稿人所说：「代码覆盖率容易衡量，需求覆盖率可是另一回事。」 不过两者可以相辅相成：Eleanor 系统地思考时想到了「所有人估算相同」，连产品负责人都没料到这种情况。

测试的三个层级

谈务实的测试，首先要决定在哪个层级测：单元、集成还是系统。

层级测什么优点缺点
单元测试一个（或一小组）不依赖外部系统的类 快（几毫秒）；输入输出容易控制；容易写 缺乏真实性；集成才会出现的 Bug 抓不到（如前后端对接、多线程）
集成测试你的代码与外部组件（数据库、Web 服务、文件）之间的交互 能验证 SQL 是否真的能跑出想要的结果 更难写：要准备独立的测试数据库、建表、造数据、清理
系统测试整个系统，包括数据库、前端等所有组件 最真实，最能给人信心 慢；难写；容易不稳定（flaky）—— 同样的配置有时过有时不过
ⓘ 「单元」到底多大？

Roy Osherove 的定义：「单元测试是一段自动化代码，它调用系统中的一个工作单元。一个工作单元可以是一个方法、一个类， 或者多个类一起完成一个可以被验证的逻辑目的。」作者自己的理解：测试一小组不依赖外部系统（数据库、Web 服务等我无法完全控制的东西）的类。 如果类 A 依赖一个访问数据库的类，就用一个简化的「替身」代替它 —— 这是第 6 章的主题。

测试金字塔：力气该花在哪

该在哪一层多投入？标准答案是：「看情况。」作者和许多开发者一样偏爱单元测试，原因是：

  • 好写、跑得快，可以和生产代码穿插着写；
  • 开发功能本来就是一个单元一个单元地写，边写边严格测试一个小单元，比事后测一大块功能容易得多；
  • 通过清晰的契约并系统地测试它们，能大大降低「单个都对、组合起来却出错」的风险；
  • 单元层测得够狠，集成和系统测试就只需测真正要紧的部分，不用在高层把所有功能重测一遍。

每一层测什么

🧩

单元测试

算法和业务逻辑。多数业务系统都在「变换数据」（订单、发票……），这些逻辑通常不依赖外部服务，完全可控。

🔗

集成测试

和外部组件打交道的部分，典型是 DAO：你要确认 SQL 真的返回你要的数据、事务真的提交了。

🌐

系统测试

做一次简单的风险分析：哪些部分一旦出错影响最大？只在那些地方做系统测试。

👀

手动测试

偏向探索和确认。时不时自己用一用正在做的系统，常常能找到新的测试灵感。

ⓘ 如果业务逻辑只能通过整个系统才能测

那多半是之前的设计或架构决策在阻碍单元测试。类的设计方式对可测试性影响巨大 —— 第 7 章专门讨论。

💡 一个真实例子：在线教育平台的支付

支付是最关键的功能，最糟的 Bug 就是用户付不了钱。于是团队：用单元测试验证「买了什么 → 开通什么权限」等业务规则； 用集成测试真实调用两家支付网关的沙箱环境，覆盖不同用户、不同信用卡； 用系统测试启动 Firefox，模拟用户完整的购买旅程，确认付款后产品可用。三层各司其职。

不同意金字塔？也可以

很多人支持测试奖杯（testing trophy）：底部单元测试薄，中间集成测试厚。他们的理由很实在：

  • 微服务架构：复杂性主要在服务之间的集成，真实调用其他服务比用 Mock 更让人放心。
  • 以数据库为中心的信息系统：主要职责就是存、取、展示，没什么复杂算法，SQL 往往才是最复杂的部分。

作者即使在微服务场景下，也会先在每个服务里写大量单元测试并认真设计契约，然后再写很多集成测试。 但他也坦言：目前没有科学证据支持或反对金字塔 —— 2020 年一项分析了 3 万个测试的研究，没发现哪一层对哪类缺陷更有效。 具体情况具体分析，找到适合你和团队的方式。

另一种分法：按测试「大小」

Google 不按边界（单元/集成/系统），而是按运行代价来分：

大小限制特点
小型测试在单个进程内执行接触不到慢和不确定性的主要来源 → 快且稳定
中型测试可以跨进程、用线程、访问 localhost 网络更慢，也更容易不稳定
大型测试去掉 localhost 限制，可以调用多台机器留给完整的端到端测试

Google 大约 80% 的测试是单元测试。无论怎么分，目标都一样：让每个测试写起来尽量便宜、跑起来尽量快、给出尽量多的质量反馈。

🔑 本书能帮你找到所有 Bug 吗？

不能！但书里的技术能帮你找到很多 Bug —— 希望是所有重要的那些。 书中例子大多是方法、类和单元测试，但道理可以推广到更粗粒度的组件：看到一个方法时，你完全可以把它想成一个 Web 服务，推理过程相同，只是用例更多。

本章小结

  • 测试和测试代码可以引导开发，但软件测试的核心是找 Bug，这也是本书的重点。
  • 系统而高效的测试帮你设计出能触及代码每个角落的用例，尽量不给意外行为留空间。
  • 即使再系统，也无法证明程序没有 Bug；穷举测试不可能，测试者的日常就是在「测多少」上做权衡。
  • 测试可以在不同层级进行，从测一个小方法到测包含数据库和 Web 服务的整个系统，各有利弊。

自测练习

1.1　用自己的话解释：什么是系统化测试？它和非系统化测试有什么不同？

系统化测试就是用有章可循的技术（从需求、边界、源代码出发）来设计测试用例，而不是凭直觉想到什么测什么。 它让不同的人对同一段代码推导出相近的测试集。

1.2　某读书社交网站 Bug 很少，但用户抱怨「它没有兑现承诺」。这符合哪条测试原则？

无错误谬论（absence-of-errors fallacy）。验证做得好，但确认没做好：系统做对了，却不是用户要的系统。

1.3　新人发现 50% 以上的 Bug 出在国际支付模块，承诺「完整覆盖这个模块，找出所有 Bug」。为什么做不到？（A 杀虫剂悖论　B 穷举测试　C 尽早测试　D 缺陷聚集）

B。穷举测试在绝大多数情况下是不可能的。（她观察到的现象本身是「缺陷聚集」，但「找出所有 Bug」的承诺违背的是穷举测试原则。）

1.4　John 只做单元测试。以下哪条原则无法帮助说服他改变？（A 杀虫剂悖论　B 测试依赖于上下文　C 无错误谬论　D 尽早测试）

D。「尽早测试」很重要，但和「只做单元测试」的问题无关；其他原则都能说明为什么需要多种测试。

1.5　一个健身 App 团队分支覆盖率超过 95%，用户仍报告大量 Bug。顾问讲的是哪条原则？

杀虫剂悖论。覆盖率很高，但只用了一种技术，需要引入不同的测试方法。

1.6　「网店每天跑一次批处理：从外部数据库取出已付款订单，按是否国际客户设置发货日期，再发送给外部 Web 服务。」该选哪个层级？

正确说法是：集成测试虽然更难自动化，但能更好地发现与 Web 服务和数据库通信中的 Bug。「用 Mock 写单元测试适用于一切」和「只选一个层级深挖」都不对。

1.7　一个薪资系统用 Java 类向 Postgres 发送复杂 SQL。以下哪个不是发现 SQL Bug 的好选择？（单元测试 / 集成测试 / 系统测试 / 压力测试）

单元测试。要知道 SQL 对不对，最好的办法是真的发给数据库执行，这正是集成测试（或更高层级）的工作。

1.8　系统测试最主要的优点是什么？

与系统的交互更接近真实使用。（系统测试恰恰更容易不稳定，也不一定由产品负责人编写。）

1.9　金字塔里推荐的系统测试数量比单元测试少，最主要的原因是？

系统测试往往很慢，而且很难做到结果确定（不 flaky）。
