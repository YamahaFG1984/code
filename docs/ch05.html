第 5 章

基于属性的测试

到目前为止，我们都在做例子测试：把输入空间分区，从每个分区里挑一个具体例子。 如果不用挑呢？如果我们只描述「程序应该满足的规律」，让框架自己去生成几百上千个输入、拼命寻找反例呢？ 这就是基于属性的测试（property-based testing）。这一章用五个由浅入深的例子，带你学会这种「换个角度」的思考方式。

本章目标

  • 理解属性测试和例子测试的区别，读懂框架报告的反例
  • 用 jqwik（Java）、Hypothesis（Python）、fast-check（TypeScript）写属性测试
  • 学会构造复杂输入：自定义生成器、组合对象、随机操作序列
  • 避开三个常见陷阱：生成不出的数据、错误的边界、分布不均
  • 知道什么时候该用属性测试，什么时候例子测试就够了

核心思想

属性测试框架的工作流程：

Java：jqwikPython：HypothesisTypeScript：fast-check
标记属性测试@Property@given(...)fc.assert(fc.property(...))
「对所有」参数@ForAll + 约束注解策略（strategy）：st.integers()…任意值（arbitrary）：fc.integer()…
自定义生成器@Provide 返回 Arbitrary<T>组合策略 / @st.composite组合 arbitrary / .map .chain
默认运行次数1000100100
操作序列（有状态）ActionSequenceRuleBasedStateMachinefc.commands + fc.modelRun
ⓘ 框架 API 各不相同，思路完全一样

JUnit、pytest、Vitest 长得都差不多，但属性测试框架的 API 差别很大。换语言时，你要做的是去学那门语言的框架；思考和推理的方式是通用的。本章重点关注作者的思考过程，注意写属性测试需要多少创造力。

例 1：及格线

📋 需求

成绩 ≥ 5.0 为及格，低于 5.0 为不及格。成绩的有效范围是 [1.0, 10.0]。

public class PassingGrade {
  public boolean passed(float grade) {
    if (grade < 1 || grade > 10)            // 前置条件
      throw new IllegalArgumentException();
    return grade >= 5;
  }
}

def passed(grade: float) -> bool:
    if grade < 1 or grade > 10:              # 前置条件
        raise ValueError("grade must be in [1, 10]")
    return grade >= 5

export function passed(grade: number): boolean {
  if (grade < 1 || grade > 10) {           // 前置条件
    throw new RangeError("grade must be in [1, 10]");
  }
  return grade >= 5;
}

规格测试会得到「及格」「不及格」「超出范围」三个分区，每个分区一个用例。属性测试则把它们表述成对整个分区都成立的规律：

public class PassingGradePBTest {
  private final PassingGrade pg = new PassingGrade();

  @Property                      // 不是 @Test：这是一条属性
  void fail(@ForAll                                        // 由 jqwik 生成
            @FloatRange(min = 1f, max = 5f, maxIncluded = false)
            float grade) {
    assertThat(pg.passed(grade)).isFalse();
  }

  @Property
  void pass(@ForAll
            @FloatRange(min = 5f, max = 10f, maxIncluded = true)
            float grade) {
    assertThat(pg.passed(grade)).isTrue();
  }

  @Property
  void invalid(@ForAll("invalidGrades") float grade) {     // 用下面的 provider 生成
    assertThatThrownBy(() -> pg.passed(grade))
        .isInstanceOf(IllegalArgumentException.class);
  }

  @Provide
  private Arbitrary<Float> invalidGrades() {
    return Arbitraries.oneOf(                  // 二选一，两边均匀分布
        Arbitraries.floats().lessThan(1f),
        Arbitraries.floats().greaterThan(10f));
  }
}

import pytest
from hypothesis import given, strategies as st
from passing_grade import passed

@given(st.floats(min_value=1.0, max_value=5.0, exclude_max=True))
def test_fail(grade):
    assert passed(grade) is False

@given(st.floats(min_value=5.0, max_value=10.0))
def test_pass(grade):
    assert passed(grade) is True

invalid_grades = st.one_of(                    # 二选一，两边均匀分布
    st.floats(max_value=1.0, exclude_max=True),
    st.floats(min_value=10.0, exclude_min=True),
)

@given(invalid_grades)
def test_invalid(grade):
    with pytest.raises(ValueError):
        passed(grade)

import { test, expect } from "vitest";
import fc from "fast-check";
import { passed } from "./passingGrade";

test("fail", () => {
  fc.assert(fc.property(
    fc.double({ min: 1, max: 5, maxExcluded: true, noNaN: true }),
    (grade) => { expect(passed(grade)).toBe(false); }));
});

test("pass", () => {
  fc.assert(fc.property(
    fc.double({ min: 5, max: 10, noNaN: true }),
    (grade) => { expect(passed(grade)).toBe(true); }));
});

const invalidGrades = fc.oneof(               // 二选一，两边均匀分布
  fc.double({ max: 1, maxExcluded: true, noNaN: true }),
  fc.double({ min: 10, minExcluded: true, noNaN: true }));

test("invalid", () => {
  fc.assert(fc.property(invalidGrades, (grade) => {
    expect(() => passed(grade)).toThrow(RangeError);
  }));
});

写法很像普通测试，只是参数由框架生成。如果只写 @ForAll 不加约束，jqwik 会尝试任意 float；这里我们用 @FloatRange 限定在 [1.0, 5.0)。 更复杂的输入（比如「小于 1 或 大于 10」）用 provider 方法表达，返回一个 Arbitrary —— 框架表示「任意值」的方式。 jqwik 的 Arbitraries 类有几十个辅助方法，值得逛一逛它的用户指南。

💡 第一次用？打印出来看看

在测试方法里加一行打印，看看框架都生成了什么值。你会惊讶于它们有多随机、跨度有多大。

故意放一个 Bug

把 return grade >= 5 改成 return grade > 5 —— 经典的差一错误。再跑测试，pass 属性失败了。jqwik 的输出：

ⓘ 属性测试也会试边界

框架很聪明，会刻意生成边界值（edge cases）：要「小于 1.0 的 float」，它会试最接近 1.0 的数；要「任意整数」，它会试最大值、最小值、0 和负数。 jqwik 默认把边界值「混入」随机数据中（上面报告里的 edge-cases#mode = MIXIN）。

⚠ 但它终究是随机的

我们实测了这个 > 的 Bug：Hypothesis 15 次运行 15 次都在 5.0 处抓住了它；fast-check 默认每次跑 100 组，50 次运行中抓住了 39 次 —— 大约每 5 次会漏 1 次。 不同框架「偏爱边界」的程度不一样。所以，对你明确知道的关键边界（这里的 5.0），仍然值得写一个例子测试把它钉死；属性测试负责探索你没想到的地方。

🔎 一个意外的发现：NaN

注意 TypeScript 标签页里的 noNaN: true：fast-check 即使设定了 min/max，默认仍会生成 NaN（非数字）；去掉它，pass 属性马上会报出 Counterexample: [Number.NaN]。 Hypothesis 则不会在有界范围里生成 NaN，所以 Python 版三条属性都能通过 —— 可这恰恰把一个问题藏了起来。换一个更「宽」的属性试试：对任意浮点数，要么被拒绝，要么它就在 [1, 10] 之内。 

@Property
void onlyValidGradesAreAccepted(@ForAll float grade) {
  try {
    pg.passed(grade);
  } catch (IllegalArgumentException e) {
    return;                                       // 被拒绝：没问题
  }
  assertThat(grade).isBetween(1f, 10f);           // 被接受：那它必须在范围内
}

@given(st.floats())                               # 不设界：会生成 NaN、±inf

    try:
        passed(grade)
    except ValueError:
        return                                    # 被拒绝：没问题
    assert 1 <= grade <= 10                       # 被接受：那它必须在范围内

# Failing test case: test_only_valid_grades_are_accepted(
#     grade=nan,
# )

test("only valid grades are accepted", () => {
  fc.assert(fc.property(fc.double(), (grade) => {  // 不设界：会生成 NaN、±Infinity
    let accepted = true;
    try { passed(grade); } catch { accepted = false; }
    if (accepted) expect(grade >= 1 && grade <= 10).toBe(true);

// 某次运行的输出（不是每次都能抓到，见下文）：
// Property failed after 9 tests
// Counterexample: [Number.NaN]

两个框架都能报告出 NaN 这个反例（我们实测：Hypothesis 15 次运行里抓到 12 次；fast-check 默认 100 组的情况下，200 次运行里抓到 55 次，大约四分之一 —— 想更稳，就调大 numRuns，或者把 NaN 作为一个明确的例子测试写进去）。原因是：NaN < 1 和 NaN > 10 都是 false，所以 passed(NaN) 不会抛异常， 而是悄悄返回 false —— 前置条件被绕过了。按 IEEE 754 浮点规则，Java 版的比较也完全一样，也有这个洞。 这就是属性测试的魅力：它会去试你根本没想到的输入。发现之后，由你决定是修代码（显式拒绝 NaN）还是修规格。

例 2：unique 方法

📋 需求（改编自 Apache Commons 的 MathArrays.unique）

返回一个由 data 中不重复的值组成的数组，按降序排列。允许空数组；data 为 null 时抛出 NullPointerException。

public static int[] unique(int[] data) {
  TreeSet<Integer> values = new TreeSet<Integer>();   // TreeSet 自动去重并排序（升序）
  for (int i = 0; i < data.length; i++) {
    values.add(data[i]);
  }
  final int count = values.size();
  final int[] out = new int[count];
  Iterator<Integer> iterator = values.iterator();
  int i = 0;
  while (iterator.hasNext()) {
    out[count - ++i] = iterator.next();                // 从后往前填 → 降序
  }
  return out;
}

def unique(data: list[int]) -> list[int]:
    values = sorted(set(data))          # 去重并升序
    out = [0] * len(values)
    for i, v in enumerate(values):
        out[len(values) - 1 - i] = v    # 从后往前填 → 降序
    return out

export function unique(data: number[]): number[] {
  const values = [...new Set(data)].sort((a, b) => a - b);  // 去重并升序
  const out = new Array<number>(values.length);
  values.forEach((v, i) => {
    out[values.length - 1 - i] = v;                          // 从后往前填 → 降序
  });
  return out;
}

直接上属性：给定任意整数数组，返回的新数组只包含原数组中不重复的值，并且降序排列。 为了确保数组里一定有重复，我们生成长度为 100、取值在 [1, 20] 的列表 —— 100 个数只能取 20 种值，必然有重复。 

@Property
void unique(@ForAll @Size(value = 100)
            List<@IntRange(min = 1, max = 20) Integer> numbers) {

  int[] doubles = convertListToArray(numbers);
  int[] result = MathArrays.unique(doubles);

  assertThat(result)
      .contains(doubles)                                  // 包含所有元素
      .doesNotHaveDuplicates()                            // 没有重复
      .isSortedAccordingTo(Comparator.reverseOrder());    // 降序
}

private int[] convertListToArray(List<Integer> numbers) {
  return numbers.stream().mapToInt(x -> x).toArray();
}

from hypothesis import given, strategies as st
from math_arrays import unique

@given(st.lists(st.integers(min_value=1, max_value=20), min_size=100, max_size=100))

    result = unique(numbers)

    assert set(result) == set(numbers)                  # 包含所有元素（且没多出东西）
    assert len(result) == len(set(result))              # 没有重复
    assert result == sorted(result, reverse=True)       # 降序

💡 善用断言库

AssertJ 的 contains、doesNotHaveDuplicates、isSortedAccordingTo 省了大量代码。写复杂断言前，先查查断言库有没有现成的。

ⓘ 不限定范围会怎样？

作者的一个学生发现，即使不把整数限定在 [1, 20]，jqwik 生成的数组里也有约 11% 含重复元素。11% 够不够？作为测试者你应该思考这个问题。他用的是 jqwik 的统计功能来测量输入分布（Hypothesis 有 event() 和 --hypothesis-show-statistics，fast-check 有 fc.statistics）。

例 3：indexOf 方法

📋 需求（Apache Commons 的 ArrayUtils.indexOf）

从给定下标开始，在数组中查找给定值的下标。数组为 null 返回 -1；startIndex 为负数视为 0；startIndex 超过数组长度返回 -1。找不到返回 -1。

public static int indexOf(final int[] array, final int valueToFind, int startIndex) {
  if (array == null) {
    return -1;             // 弱前置条件：接受 null，返回 -1
  }
  if (startIndex < 0) {
    startIndex = 0;        // 同样很宽容：负数当作 0
  }
  for (int i = startIndex; i < array.length; i++) {
    if (valueToFind == array[i]) {
      return i;
    }
  }
  return -1;
}

def index_of(array: list[int] | None, value_to_find: int, start_index: int) -> int:
    if array is None:
        return -1          # 弱前置条件：接受 None，返回 -1
    if start_index < 0:
        start_index = 0    # 同样很宽容：负数当作 0
    for i in range(start_index, len(array)):
        if array[i] == value_to_find:
            return i
    return -1

export function indexOf(array: number[] | null, valueToFind: number, startIndex: number): number {
  if (array == null) {
    return -1;             // 弱前置条件：接受 null，返回 -1
  }
  if (startIndex < 0) {
    startIndex = 0;        // 同样很宽容：负数当作 0
  }
  for (let i = startIndex; i < array.length; i++) {
    if (array[i] === valueToFind) return i;
  }
  return -1;
}

作为对比，Apache Commons 自己的测试覆盖了我们的 T1、T4、T5、T6、T7、T8、T10、T11，但没测单元素数组，也没测「找到之后又出现一次」的情况。 两套测试都不错。现在我们用属性测试来表达这个方法的主要行为。

设计属性

思路：在一个随机数组的随机位置插入一个随机值，然后让 indexOf 去找它，断言返回的下标就是我们插入的位置。 难点在于：插入的值不能已经在数组里。比如数组 [1, 2, 3, 4]，在下标 1 插入 4，从下标 0 开始找会得到 1，从下标 3 开始找会得到 4 —— 断言就乱了。 巧妙的办法：让数组取值在 [-1000, 1000]，插入值取自 [1001, 2000]，二者绝不相交。 

@Property
void indexOfShouldFindFirstValue(
    @ForAll @Size(value = 100)
    List<@IntRange(min = -1000, max = 1000) Integer> numbers,   // 100 个随机数
    @ForAll @IntRange(min = 1001, max = 2000) int value,        // 绝不在列表中的值
    @ForAll @IntRange(max = 99) int indexToAddElement,          // 插入位置
    @ForAll @IntRange(max = 99) int startIndex) {               // 从哪开始找

  numbers.add(indexToAddElement, value);
  int[] array = convertListToArray(numbers);

  // 插在 startIndex 之后（或恰好在）→ 找得到；插在之前 → 找不到
  int expectedIndex = indexToAddElement >= startIndex ? indexToAddElement : -1;
  assertThat(ArrayUtils.indexOf(array, value, startIndex)).isEqualTo(expectedIndex);
}

    (numbers, value, indexToAdd, startIndex) => {
      numbers.splice(indexToAdd, 0, value);

      // 插在 startIndex 之后（或恰好在）→ 找得到；插在之前 → 找不到
      const expected = indexToAdd >= startIndex ? indexToAdd : -1;
      expect(indexOf(numbers, value, startIndex)).toBe(expected);
    }));
});

这个属性测试比前面的例子测试更好地检验了方法的本质。它也说明了写属性测试需要创造力：想出「生成一个绝不在列表中的值」，以及处理「插入位置可能在起点前或后」的断言。作者提醒注意两点：

  1. 你的测试有多接近真实世界？如果生成的数据和实际使用中的相差十万八千里，那可能不是个好测试。
  2. 各个分区被检验的概率一样吗？这里要找的值有时在起点前、有时在起点后。如果 95% 的输入都在起点前，测试就严重偏向了。两个下标都在 0–99 随机，大约是五五开。拿不准时，打印出来看看分布。

public class BasketPBTest {

  class AddAction implements Action<Basket> {
    private final Product product;
    private final int qty;

    public AddAction(Product product, int qty) {   // 商品和数量由 jqwik 随机生成
      this.product = product;
      this.qty = qty;
    }

    @Override
    public Basket run(Basket basket) {
      BigDecimal currentValue = basket.getTotalValue();
      basket.add(product, qty);

      BigDecimal newProductValue = product.getPrice().multiply(valueOf(qty));
      BigDecimal newValue = currentValue.add(newProductValue);
      assertThat(basket.getTotalValue()).isEqualByComparingTo(newValue);
      return basket;                               // 下一个操作从这个状态继续
    }
  }

  class RemoveAction implements Action<Basket> {
    @Override
    public Basket run(Basket basket) {
      BigDecimal currentValue = basket.getTotalValue();
      Set<Product> productsInBasket = basket.products();
      if (productsInBasket.isEmpty())              // 车是空的就跳过（序列是随机的）
        return basket;

      Product randomProduct = pickRandom(productsInBasket);
      double currentProductQty = basket.quantityOf(randomProduct);
      basket.remove(randomProduct);

      BigDecimal basketValueWithoutRandomProduct = currentValue
          .subtract(randomProduct.getPrice().multiply(valueOf(currentProductQty)));
      assertThat(basket.getTotalValue())
          .isEqualByComparingTo(basketValueWithoutRandomProduct);
      return basket;
    }
    // pickRandom(...) 见仓库源码
  }

  static List<Product> randomProducts = new ArrayList<>() {{
    add(new Product("TV", new BigDecimal("100")));
    add(new Product("Playstation", new BigDecimal("150.3")));
    add(new Product("Refrigerator", new BigDecimal("180.27")));
    add(new Product("Soda", new BigDecimal("2.69")));
  }};

  private Arbitrary<AddAction> addAction() {
    Arbitrary<Product> products = Arbitraries.oneOf(       // 从固定列表中随机挑商品
        randomProducts.stream()
            .map(product -> Arbitraries.of(product))
            .collect(Collectors.toList()));
    Arbitrary<Integer> qtys = Arbitraries.integers().between(1, 100);
    return Combinators.combine(products, qtys)
        .as((product, qty) -> new AddAction(product, qty));
  }

  private Arbitrary<RemoveAction> removeAction() {
    return Arbitraries.of(new RemoveAction());
  }

  @Provide
  Arbitrary<ActionSequence<Basket>> addsAndRemoves() {
    return Arbitraries.sequences(Arbitraries.oneOf(addAction(), removeAction()));
  }

  @Property
  void sequenceOfAddsAndRemoves(@ForAll("addsAndRemoves") ActionSequence<Basket> actions) {
    actions.run(new Basket());
  }
}

from decimal import Decimal
from hypothesis import strategies as st
from hypothesis.stateful import RuleBasedStateMachine, rule, precondition
from basket import Basket, Product

PRODUCTS = [
    Product("TV", Decimal("100")),
    Product("Playstation", Decimal("150.3")),
    Product("Refrigerator", Decimal("180.27")),
    Product("Soda", Decimal("2.69")),

class BasketMachine(RuleBasedStateMachine):
    """Hypothesis 会随机决定调用哪些 rule、调用几次、以什么顺序。"""

    def __init__(self):
        super().__init__()
        self.basket = Basket()

    @rule(product=st.sampled_from(PRODUCTS), qty=st.integers(1, 100))
    def add(self, product, qty):
        current = self.basket.total_value
        self.basket.add(product, qty)
        assert self.basket.total_value == current + product.price * qty

    @precondition(lambda self: len(self.basket.products()) > 0)   # 车是空的就不删
    @rule(data=st.data())
    def remove(self, data):
        current = self.basket.total_value
        in_basket = sorted(self.basket.products(), key=lambda p: p.name)
        product = data.draw(st.sampled_from(in_basket))   # 用框架的随机源挑，可复现
        qty = self.basket.quantity_of(product)

        self.basket.remove(product)

        assert self.basket.total_value == current - product.price * qty

🔎 随机性要交给框架

仓库里 Java 版的 pickRandom 用的是 new Random()，这意味着即使 jqwik 用同一个种子重放，挑中的商品也可能不同，失败就不一定能复现。 Python 版用 data.draw(...)、TypeScript 版把「挑第几个」也作为生成的参数，所有随机性都来自框架，失败时就能稳定重放，而且框架还能对它做收缩。

现实中的属性测试

例子测试 vs 属性测试

属性测试看起来更「高级」，对输入空间的探索也更好。那以后只写属性测试？作者在实践中两者混用。 做规格测试和结构化测试时用例子测试 —— 它更简单，自动化时需要的创造力更少，让人能专注于理解需求、设计更好的用例。 两种技术都做完、对程序理解透彻之后，再评估哪些用例更适合写成属性测试。 他并不总写属性测试：很多问题用例子测试就足够有信心了，只有当不完全确定例子测试够不够时，才会用属性测试。

三个常见陷阱

⏳

1. 要求生成昂贵甚至不可能的数据

「100 个互不相同、同时是 2、3、5、15 的倍数的数」很难靠随机找到；「10 个不重复元素，取值范围只有 2–8」根本不可能。框架生成数据要很久？换一种生成方式，或者换一种写法。

📏

2. 边界表达错了

边界是 Bug 的温床，要确保属性的边界表达正确。比如 lessThan(1f) 和 greaterThan(10f)，框架会尽力生成最接近 1 的数、最小的 float……前提是你把边界写对了。

⚖

3. 输入分布不均

框架本身会生成均匀分布的数据，但测试里对数据的加工可能破坏这一点。典型例子就是下面的三角形。

public class Triangle {
  public static boolean isTriangle(int a, int b, int c) {
    boolean hasABadSide = a >= (b + c) || c >= (b + a) || b >= (a + c);
    return !hasABadSide;
  }
}

def is_triangle(a: int, b: int, c: int) -> bool:
    has_a_bad_side = a >= b + c or c >= b + a or b >= a + c
    return not has_a_bad_side

export function isTriangle(a: number, b: number, c: number): boolean {
  const hasABadSide = a >= b + c || c >= b + a || b >= a + c;
  return !hasABadSide;
}

要表达两条属性：合法三角形和非法三角形。如果直接生成三个随机整数，它们能组成合法三角形的概率很低：

最简单的办法是拆成两个测试，一个只生成合法三角形，一个只生成非法三角形。仓库里的 Java 版用 filter 过滤；Python 和 TypeScript 版我们换一种更高效的方式 —— 直接构造，而不是生成后再筛掉大部分：

@Property
void triangleIsInvalidIfOneSideIsBiggerThanOthers(@ForAll("invalidTrianglesGenerator") ABC abc) {
  assertThat(Triangle.isTriangle(abc.a, abc.b, abc.c)).isFalse();
}

@Provide
Arbitrary<ABC> invalidTrianglesGenerator() {
  Arbitrary<Integer> normalSide1 = Arbitraries.integers();
  Arbitrary<Integer> normalSide2 = Arbitraries.integers();
  Arbitrary<Integer> biggerSide = Arbitraries.integers();
  Arbitrary<ABC> biggerA = Combinators.combine(normalSide1, normalSide2, biggerSide).as(ABC::new)
      .filter(k -> k.a >= k.b + k.c);
  Arbitrary<ABC> biggerB = Combinators.combine(normalSide1, normalSide2, biggerSide).as(ABC::new)
      .filter(k -> k.b >= k.a + k.c);
  Arbitrary<ABC> biggerC = Combinators.combine(normalSide1, normalSide2, biggerSide).as(ABC::new)
      .filter(k -> k.c >= k.a + k.b);
  return Arbitraries.oneOf(biggerA, biggerB, biggerC);    // 哪条边太长，三种情况均匀
}

@Property
void triangleIsValidOtherwise(@ForAll("validTriangleGenerator") ABC abc) {
  assertThat(Triangle.isTriangle(abc.a, abc.b, abc.c)).isTrue();
}

@Provide
Arbitrary<ABC> validTriangleGenerator() {
  Arbitrary<Integer> side = Arbitraries.integers();
  return Combinators.combine(side, side, side).as(ABC::new)
      .filter(k -> (k.a < k.b + k.c) && (k.b < k.a + k.c) && (k.c < k.a + k.b));
}

from hypothesis import given, strategies as st
from triangle import is_triangle

sides = st.integers(min_value=1, max_value=1000)

@st.composite
def invalid_triangles(draw):
    b, c = draw(sides), draw(sides)
    too_long = b + c + draw(st.integers(0, 1000))     # 这条边 ≥ 另两边之和
    a, b, c = draw(st.permutations([too_long, b, c]))  # 哪条边太长，随机
    return a, b, c

@st.composite
def valid_triangles(draw):
    b, c = draw(sides), draw(sides)
    a = draw(st.integers(abs(b - c) + 1, b + c - 1))   # 严格介于 |b-c| 和 b+c 之间
    return tuple(draw(st.permutations([a, b, c])))

@given(invalid_triangles())
def test_triangle_is_invalid_if_one_side_is_bigger_than_others(abc):
    assert is_triangle(*abc) is False

@given(valid_triangles())
def test_triangle_is_valid_otherwise(abc):
    assert is_triangle(*abc) is True

import { isTriangle } from "./triangle";

  .tuple(side, side, fc.integer({ min: 0, max: 1000 }))
  .chain(([b, c, extra]) =>                             // 这条边 ≥ 另两边之和
    fc.shuffledSubarray([b + c + extra, b, c], { minLength: 3 }));

  .tuple(side, side)
  .chain(([b, c]) => fc

    .chain((a) => fc.shuffledSubarray([a, b, c], { minLength: 3 })));

  }));
});

⚠ 过滤太多，框架会抗议

Java 版的 filter 会扔掉大量生成的数据（三个完全随机的 int 恰好满足条件的比例不高），生成就会变慢。Hypothesis 遇到这种情况会直接报 FailedHealthCheck 提醒你「过滤得太多了」。 能构造就别过滤 —— 这正是陷阱 1 的一个实例。

创造力是关键

写属性测试需要大量创造力：想办法表达属性、生成随机数据、在不知道具体输入的情况下断言期望行为 —— 都不容易。它比例子测试需要更多练习。尽早动手吧，希望本章的例子给了你一些灵感！

本章小结

  • 在属性测试中，我们不去想具体的例子，而是表达方法应该满足的属性，由框架随机生成成百上千个输入。
  • 属性测试不能取代规格测试和结构化测试，它是你工具箱里的又一件工具。有时传统的例子测试就够了。
  • 写属性测试需要创造力：巧妙地生成数据、处理断言，并确保分区被均衡地检验。

自测练习

5.1　例子测试和属性测试的主要区别是什么？

例子测试使用（通常无穷多种可能中的）一个具体实例；属性测试定义需要成立的属性，由框架生成随机输入，寻找能打破该属性的输入。

5.2　一个方法判断字符串是否为回文（正读反读都一样）。你能想到哪些属性？怎么实现？

两条属性：回文返回 true，非回文返回 false。

  • 回文：生成随机字符串 s，拼接 s + reverse(s)，应返回 true。别忘了奇数长度的回文：s + X + reverse(s)（X 为任意字符）—— 这是一个值得测的边界。
  • 非回文：生成随机字符串后，加入一些与生成它的字符不同的随机字母，确保它不是回文；否则随机生成可能碰巧造出回文，让测试误报。
@given(st.text(alphabet="abc"), st.one_of(st.just(""), st.sampled_from("abc")))
def test_palindromes(s, middle):
    assert is_palindrome(s + middle + s[::-1])

test("palindromes", () => {
  fc.assert(fc.property(
    fc.string(), fc.constantFrom("", "a", "b"),
    (s, middle) => {
      expect(isPalindrome(s + middle + [...s].reverse().join(""))).toBe(true);
    }));
});
5.3　什么是模糊测试（fuzzing）？它和属性测试有什么区别？

模糊测试用无效的、意外的、随机的数据去运行程序，看它会不会崩溃。属性测试也生成随机数据，但目标始终是检验某条属性，测试在随机数据下应该通过；而模糊测试是不断尝试随机输入，直到程序崩溃。模糊测试是一个很大的研究领域，工具越来越聪明，推荐阅读 The Fuzzing Book。
